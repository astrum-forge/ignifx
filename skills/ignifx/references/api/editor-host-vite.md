# @ignifx/editor-host

`@ignifx/editor-host/vite`: the Vite plugin that serves the ignifx editor's scene view from a
project's own dev server, and `virtual:ignifx/editor` for its play view
(`docs/architecture/17-editor-host.md` §3). It runs in Vite's Node process and imports nothing
from `@ignifx/core`.

Explicit named re-exports only, no `export *` (coding standards §4).

##### stackTraceLimit

> `static` **stackTraceLimit**: `number`

**`Beta`**

The `Error.stackTraceLimit` property specifies the number of stack frames
collected by a stack trace (whether generated by `new Error().stack` or
`Error.captureStackTrace(obj)`).

The default value is `10` but may be set to any valid JavaScript number. Changes
will affect any stack trace captured _after_ the value has been changed.

If set to a non-number value, or set to a negative number, stack traces will
not capture any frames.

###### Inherited from

`Error.stackTraceLimit`

#### Methods

##### captureStackTrace()

> `static` **captureStackTrace**(`targetObject`, `constructorOpt?`): `void`

**`Beta`**

Creates a `.stack` property on `targetObject`, which when accessed returns
a string representing the location in the code at which
`Error.captureStackTrace()` was called.

```js
const myObject = {};
Error.captureStackTrace(myObject);
myObject.stack;  // Similar to `new Error().stack`
```

The first line of the trace will be prefixed with
`${myObject.name}: ${myObject.message}`.

The optional `constructorOpt` argument accepts a function. If given, all frames
above `constructorOpt`, including `constructorOpt`, will be omitted from the
generated stack trace.

The `constructorOpt` argument is useful for hiding implementation
details of error generation from the user. For instance:

```js
function a() {
  b();
}

function b() {
  c();
}

function c() {
  // Create an error without stack trace to avoid calculating the stack trace twice.
  const { stackTraceLimit } = Error;
  Error.stackTraceLimit = 0;
  const error = new Error();
  Error.stackTraceLimit = stackTraceLimit;

  // Capture the stack trace above function b
  Error.captureStackTrace(error, b); // Neither function c, nor b is included in the stack trace
  throw error;
}

a();
```

## Functions

### editorEntryModuleSource()

> **editorEntryModuleSource**(`options`): `string`

**`Beta`**

Generates the module the scene view's page runs.

#### Parameters

##### options

[`EditorEntryModuleOptions`](#editorentrymoduleoptions)

The editor origin, the project's extensions module, and the reporting options.

#### Returns

`string`

The ES module source.

#### Remarks

The module is the only code with an import-time effect: it creates the host. The package itself
creates nothing when imported (`CONSTITUTION.md` §3.5). Every import is resolved from the
project's root, so the host, the scripts, and the extensions share the project's one copy of
`@ignifx/core`. It hands every `ignifx:asset-changed` event to `host.assetChanged`, which
reloads the asset in place; the `import.meta.hot` calls are written out literally, because Vite
finds them by reading the source.

***

### editorHostPlugin()

> **editorHostPlugin**(`options`): `Plugin`\<`any`\>[]

**`Beta`**

The editor host's Vite plugin.

#### Parameters

##### options

[`EditorHostPluginOptions`](#editorhostpluginoptions)

The editor's origin and the scene view's options.

#### Returns

`Plugin`\<`any`\>[]

The plugins, to be listed in `vite.config.ts`.

#### Remarks

It is two plugins, because the two halves run under different commands:

- `ignifx-editor-host` (`vite dev` only) serves the scene view at `/__ignifx_editor__/` with
  `Content-Security-Policy: frame-ancestors <editorOrigin>`, and adds the same header to every
  page a browser navigates to, so the game's own `index.html` (the play view) can be framed by the
  editor and by nothing else. A `Content-Security-Policy` in `server.headers` replaces it. The page's module imports the host,
  `virtual:ignifx/scripts`, `virtual:ignifx/manifest` and the project's extensions module from
  the project's own graph, and calls `startEditorHost`. It adds the extensions module to
  `optimizeDeps.entries` (keeping Vite's default crawl) and keeps `@ignifx/editor-host` out of
  pre-bundling, so the host reaches the same pre-bundled `@ignifx/core` as the game.
- `ignifx-editor-host:play-controls` (every command) serves `virtual:ignifx/editor`: the play
  controls under `vite dev`, an empty function under `vite build`.

List it after `ignifx()` from `@ignifx/vite-plugin`, which serves the two modules the scene
view imports.

#### Throws

EditorHostPluginError `IGX-1801` for a malformed `editorOrigin`, `IGX-1803` for a bad
`extensions` path or `heartbeatIntervalMs`.

#### Example

```ts
// vite.config.ts
import { ignifx } from "@ignifx/vite-plugin";
import { editorHostPlugin } from "@ignifx/editor-host/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [ignifx(), editorHostPlugin({ editorOrigin: "ignifx://app" })],
});
```

### isEditorOrigin()

> **isEditorOrigin**(`value`): `boolean`

**`Beta`**

Tells whether a string is an origin the editor can be served from.

#### Parameters

##### value

`string`

The candidate, for example `"ignifx://app"` or `"http://localhost:5173"`.

#### Returns

`boolean`

`true` when the value is a scheme, `://`, and a host with an optional port.

#### Remarks

`new URL(value).origin` is not usable here: for a scheme Node does not know, such as the
editor's `ignifx://app`, it answers `"null"`, while Chromium reports `ignifx://app` as
`event.origin` because Electron registers the scheme as standard.

### playControlsModuleSource()

> **playControlsModuleSource**(`options`): `string`

**`Beta`**

Generates `virtual:ignifx/editor`.

#### Parameters

##### options

[`PlayControlsModuleOptions`](#playcontrolsmoduleoptions)

The editor origin, the reporting options, and whether to emit the development module.

#### Returns

`string`

The ES module source.

#### Remarks

In development, the module listens for the editor's connect message as soon as it is evaluated,
which is before the game's `main.ts` runs, and keeps the port
(`listenForEditorPlayControls`); `attachEditorPlayControls(app)` then starts the play controls on
it, so the editor's first connect message is never lost to `await createApp(...)`. Vite replacing
the module stops both. The `import.meta.hot` calls are written out literally because Vite
finds them by reading the source, not by running it. In a production build the export is an empty
function, the same shape as `acceptHotReload` from `virtual:ignifx/scripts`, so the game's
`main.ts` builds either way and ships no editor code.
