# 07 · Wishlist: examples and features the engine cannot show yet

This document is the backlog behind the catalogue. It lists the examples game developers would expect
to find on ignifx.com and cannot yet, and the engine features they need first, ranked by how useful
each is and how much work it costs. It exists so the website plan and the engine backlog agree on
what is missing, and so nothing here leaks onto the site before it is real.

Sources: the pinned `@babylonjs/lite@1.27.0` type definitions (the only authority for what Babylon
Lite has), the engine's skills and architecture documents (the only authority for what ignifx
exposes), and the external references in §7, each of which was checked against its primary page on
2026-09-07. Research was drafted by agents and verified claim by claim before it was written here.

## 1. The rule

**A wishlist item is not an example and is not on the website until it is delivered and functional.**

- It does not appear in `website/examples/catalogue.ts`, not even with a "coming soon" status. The
  site build accepts only catalogue entries whose status is `ready` and fails on anything else
  (`04-examples-platform.md` §2), so the rule is enforced by the build, not by memory.
- It is not mentioned on the features page, the home page, or the press kit. The honesty rules in
  `01-strategy-and-ia.md` §6 apply: the site claims what the repository proves.
- It graduates in this order, and only in this order:
  1. The engine feature ships on `main` with tests, TSDoc, a regenerated API report, a skill entry
     and a changeset, as `AGENTS.md` requires of every public API change.
  2. An example is built to the definition of done in `04-examples-platform.md` §9: under 200 lines,
     kit-based, assets attributed, poster and golden committed, budgets asserted.
  3. The catalogue entry is added with status `ready`, the example page appears on the next deploy,
     and the item is deleted from this document.
- Items that can never run in a browser tab (Steam, native mobile, third-party portal SDKs, which the
  site's no-third-party rule also forbids) graduate to a **guide** with a captured video or poster,
  never to an example.

## 2. How to read the tables

| Column         | Meaning                                                                                                                                                                                                                                                                |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Today**      | What exists now. "Lite:" names the exact exported symbols in `index.d.ts`; "ignifx:" says what the engine exposes.                                                                                                                                                     |
| **Path**       | `engine` = expose something Lite already has; `custom` = buildable on top of the engine's public API as game code or a small package; `upstream` = Babylon Lite lacks the primitive, so it needs Lite work first; `third-party` = an integration with an external SDK. |
| **Effort**     | S under a week, M one to three weeks, L one to two months, XL more, for one engineer, ±40%.                                                                                                                                                                            |
| **Usefulness** | How many games would use it and how hard it is to live without: High, Medium, Low.                                                                                                                                                                                     |
| **Unlocks**    | The example pages that become possible.                                                                                                                                                                                                                                |

Nine catalogue rows already carry the status `engine` (`04` §7: primitives, morph targets, Gaussian
splats, device loss, depth of field, chromatic aberration, TAA, contact shadows, SSGI, instancing).
They are wishlist items too; they stay in the catalogue with that status because Babylon Lite has the
capability and the engine change is small and known. This document does not repeat them except where
a larger item depends on them.

### 3.2 Post-processing that Babylon Lite does not have

Babylon.js, the parent project, ships every effect below (its `PostProcesses` source directory lists
`thinSSAO2PostProcess`, `thinSSRPostProcess`, `thinMotionBlurPostProcess`, `thinFXAAPostProcess`,
`thinGrainPostProcess`, `thinSharpenPostProcess`, `volumetricLightScatteringPostProcess`,
`colorCorrectionPostProcess`). Babylon Lite 1.27.0 ships none of them: `index.d.ts` has zero hits for
SSAO, motion blur, FXAA, grain and sharpen, and mentions vignette and screen-space reflection only in
prose. Two paths exist: ask upstream to port the thin implementations into Lite's frame-graph task
model, or build them in ignifx as fullscreen render tasks once W-R7 lands.

## 5. Prioritisation

Usefulness against effort, from the tables above. "Foundations" unlock several other items and
should go first regardless of their own example.

| Tier                      | Items                                                                                                                                                                                                                                                                             |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Foundations**           | W-R1 custom shader materials · W-R7 render tasks and render-to-texture · W-R23 physics constraints · W-R22 particles                                                                                                                                                              |
| **Quick wins (S, High)**  | W-F11 game feel kit · W-F18 photo mode · W-R20 day-night cycle · W-R18 texture arrays · W-R30 Draco and meshopt · W-2D3 nine-slice and masks · W-F14 error reports                                                                                                                |
| **Strategic (M–L, High)** | W-R2 material plugins · W-R13 thin instancing · W-R10 lightmaps · W-R14 terrain · W-R25 IK and root motion · W-2D1 2D lighting · W-F3 replays · W-F4 accessibility · W-F7 dialogue · W-F8 AI · W-F9 timeline and virtual cameras · W-F12 saves · W-F13 audio effects · W-F1 Steam |
| **Later (XL or Medium)**  | W-F2 networking · W-R28 WebXR · W-F16 streaming · W-F17 mods · W-F19 editor · W-R19 CSG                                                                                                                                                                                           |
| **Upstream-gated**        | W-R4 SSAO · W-R5 SSR · W-R6 motion blur and FXAA · W-R8 volumetrics · W-R9 subsurface · W-R12 point-light shadows · W-R3 compute · W-R24 cloth and soft bodies                                                                                                                    |

Recommended first batch, if the owner funds any of it: W-R1, W-R7 and W-R23 as foundations, then
W-F11, W-R20 and W-F18 because they are cheap and produce three catalogue examples within a week.

Items already buildable today as custom code on the public API (W-R20 cycle, W-F11, W-F18, parts of
W-2D1 and W-2D3) may skip the engine step in §1 and go straight to an example, provided the example
stays under the catalogue's 200-line limit; otherwise the helper becomes a package first.
