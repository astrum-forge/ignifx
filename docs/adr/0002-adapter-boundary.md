# ADR-0002 · Adapter boundary around Babylon Lite

**Status:** Accepted · **Date:** 2026-09-05

## Context

Lite publishes a minor version every few days and declares that backward compatibility is not a goal; its docs and `index.d.ts` already disagree in places (`setSubtreeVisible` export name, `createGpuPicker` arity). ignifx must present a stable API to games and agents (`CONSTITUTION.md` §3.4, Article IV).

## Options considered

1. **Use Lite types everywhere** — least code. Cons: every Lite change becomes an ignifx breaking change; agents learn two APIs.
2. **Adapter directory per package (`src/lite/**`) with escape hatches** — Lite imports confined; ignifx types are the public surface; `.lite` accessors exist for power users, marked unstable.
3. **Full abstraction with a renderer interface** — could swap renderers. Cons: heavy, hypothetical; contradicts the WebGPU-only decision.

## Decision

Option 2. Only `src/lite/**` may import `@babylonjs/lite` (lint-enforced). Public ignifx APIs use ignifx types; Lite objects are reachable only through named `.lite` escape hatches with no stability guarantee. Lite is pinned exactly; upgrades are dedicated pull requests that run the adapter compatibility suite and visual tests.

## Consequences

- Some duplication (ignifx math types structurally compatible with Lite's).
- Upgrades are deliberate and testable; breaking Lite changes surface in one directory.
- The adapter is also where Lite gaps are worked around (collision body identities, animation ticking).

## Validation (2026-09-05)

Spikes S2.1, S2.2, S2.3, and the instancing half of S2.4 were run against `@babylonjs/lite@1.27.0` on macOS 26 (Darwin 25.5, arm64), Node 24.20.0, Vitest 5.0.0, Playwright 1.63.0, in Chromium with `--enable-unsafe-webgpu --use-webgpu-adapter=swiftshader`. Every Lite claim below is cited against `packages/core/node_modules/@babylonjs/lite/index.d.ts` (by line) or against a file under its `lib/` (which ships readable ESM, not minified output), and every one that could be observed at runtime has a test named beside it.

The adapter code these findings shaped lives in `packages/core/src/lite/**`, split into a CPU half that the Node project covers and `packages/core/src/lite/gpu/**`, which needs a device and is covered by the browser project.

### S2.2 — adding a mesh after `registerScene`

The crux is what Lite calls a _material family_. `createPbrMaterial` stamps every PBR material with the **same** `_buildGroup` function — a process-wide singleton — and so do the Standard and Shader factories; only node materials get one per material.

| Fact                                                                                                                                                                                                                                                          | Evidence                                                                                                                                                                                                                          |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| There are four build groups in the whole process — pbr, standard, shader, node — not one per material.                                                                                                                                                        | `lib/material/pbr/pbr-material.js` (`getPbrGroupBuilder` memoises), `lib/material/standard/create-standard-material.js`, `lib/material/shader/shader-material.js` line 123, `lib/material/node/node-material.js` (the exception). |
| A scene keys its renderable groups by that function, and `addToScene` after `registerScene` queues a material swap.                                                                                                                                           | `lib/scene/scene-core.js`, `addToScene`.                                                                                                                                                                                          |
| If the group was built at registration (`group.r` exists) the swap rebuilds the mesh **synchronously** inside the frame. If it was not, the mesh goes to a dynamically imported runtime builder, and for PBR that recompiles every PBR pipeline in the scene. | `lib/scene/scene-material-swap.js`, `lib/scene/scene-runtime-mesh-build.js` (`rebuildScenePbrPipelines(scene, true)`).                                                                                                            |
| Lite has **no** compile, precompile, or warm-up API, and no public way to await a runtime build (`scene._runtimeBuilds` is private).                                                                                                                          | Grep of `index.d.ts` for `warm`, `precompile`, `prepare`, `compile`: only `prepareShaderMaterialPipeline*`, which is for `ShaderMaterial` alone.                                                                                  |

Measured frames-to-visible, Chromium + SwiftShader, 48×48 canvas, MSAA 1, three runs (`warm-up.browser.test.ts`). "Round trip" is the cost of one `captureScreenshot` on a scene that is already correct — the capture is served at the end of a later frame (`lib/engine/screenshot.js`), so it has to be subtracted:

| Case                                                        | Capture round trip (frames) | Total wait (frames) | Attributable to the material swap |
| ----------------------------------------------------------- | --------------------------- | ------------------- | --------------------------------- |
| PBR box, no PBR mesh existed at `registerScene`             | 1–3                         | 4–6                 | **3, 3, 3**                       |
| PBR box, PBR family warmed before `registerScene`           | 1–2                         | 3                   | **2, 1, 2**                       |
| PBR box, a PBR mesh was already being drawn                 | 1                           | 1                   | **0, 0, 0**                       |
| Standard box, no Standard mesh existed at `registerScene`   | 1                           | 4                   | **3, 3, 3**                       |
| Standard box, Standard family warmed before `registerScene` | 1–2                         | 3                   | **1, 1, 1**                       |

So a cold family costs three extra frames on a software adapter and a warm one costs zero to two. Three frames is a visible pop at 60 Hz; it is also, on a real GPU with a bigger shader, a number that only grows. The policy this produces is proposed as **ADR-0014**, and `warmUpMaterials` in `packages/core/src/lite/gpu/warm-up.ts` implements it: one hidden degenerate triangle per material, added before `registerScene`. Hiding is enough, because `visible` is read when a renderable is drawn and not when it is built (`lib/scene/visibility.js`).

### Gaps in Lite's public surface that the adapter works around

| Gap                                                                                                                                                                                            | What the adapter does                                                                                                                                                                                                                                                                                             |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The scene's own render task is not reachable: `getFrameGraph` exposes only `build`/`execute`/`dispose` (`index.d.ts` 5367), so `addTaskAfter(scene, task, sceneRenderTask)` cannot be written. | `appendPostProcessTask` uses `addTask`, which appends and therefore already runs after the render pass, then records just that task with `buildFrameGraphTask`. | There is no way to **remove** a frame-graph task.                                                                                                                                              | `setPostProcessTaskEnabled(task, false)` flips `Task.executionEnabled`, which skips every pass while keeping the task recorded (`lib/frame-graph/frame-graph.js`). ### Corrections to `docs/architecture/07-rendering.md`

1. §1 lists `powerPreference` among "engine options exposed by `createApp`". **There is no such option.** Neither `EngineOptions` (`index.d.ts` 4709) nor `SurfaceOptions` (`index.d.ts` 12622) declares it, and `lib/engine/engine.js` line 47 hard-codes `requestAdapter({ powerPreference: "high-performance" })`. The only way in is a private `_adapterOptionsHook`. `toLiteEngineOptions` therefore does not accept one, and `render-diagnostics.test.ts` asserts the absence.
2. §1 does not mention `SurfaceOptions.format`, which overrides the swapchain format and must not be an `*-srgb` one — `srgb: true` is how sRGB encoding is requested.
3. §1 says `app.renderer.setSize(w, h)` maps to `setSurfaceSize` "for `OffscreenCanvas`". That qualifier is load-bearing and should be stated as a rule: on a laid-out DOM canvas the size set that way survives exactly one frame, because Lite's loop calls `resizeEngine` at the start of every frame (`lib/engine/engine.js`, `startEngine`). Resolution scaling on a DOM canvas goes through `maxDevicePixelRatio`. Measured in `render-features.browser.test.ts`.
4. §2.2's field table gives `diffuse`/`specular` for every light type; a hemispheric light uses `diffuseColor`/`specularColor`.
5. §2.2 says changing light topology "triggers `rebuildSceneRenderables`". It should also say that a **parented** shadow-casting light needs its own `direction` written from the node's world forward axis, or its shadow will not match its shading.
6. §5 says `app.renderer.captureScreenshot()` → `captureScreenshot(engine)`. Worth adding: the promise is only served from inside a rendered frame, so it never settles under the null engine or after `stopEngine`.
7. §2.1's `Camera` table maps `clearColor` to `scene.clearColor`; that field is a `GPUColorDict` in **linear** values, and with the default (non-sRGB) swapchain those values reach the canvas unencoded.

## Corrections after the visual suite (2026-09-06)

The Phase 2 visual golden suite (`tests/visual/`) rendered the exit-criterion scenes at 512×512 on
SwiftShader and compared them with committed images. It found two defects that every existing test
had missed, both of them cases where a test asserted that something _changed_ rather than what it
changed **to**. Both are fixed; the rows above that they supersede say so.

| Defect                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Why nothing caught it                                                                                                                                                                                                                      | The fix                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A `PostProcessStack` presented a black frame on a real swapchain.** The chain's first effect took `surfaceRenderTarget(engine)` (`engine.scRT`) as its `sourceTexture`. `createSurface` calls `context.configure` with no `usage` (`lib/engine/surface.js` line 30), so the swapchain texture is `RENDER_ATTACHMENT` only; binding it as a sampled texture fails validation and Chromium rejects the whole frame's command buffer. Measured for bloom, SMAA and image processing, singly and combined, at MSAA 1 and 4.                                                                                                       | `post-process.browser.test.ts` asserted that the presented image _differed_ from the plain scene. Going black is a difference.                                                                                                             | Post-processing became a rendering feature, `rendering.features.postProcessing`, decided at `createSceneContext` because `RenderTaskConfig.rt` is read when the task is built and Lite exposes no handle to retarget it. With it on, the scene is created with `defaultRenderTask: false` and `installOffscreenRenderPath` (`src/lite/gpu/render-path.ts`) builds a render task into an offscreen colour target plus a `createCopyToTextureTask` that composites it onto the swapchain. A chain reads that offscreen target and its last effect writes the swapchain, at which point the copy is disabled. `IGX-0710` reports a stack attached without the feature. |
| **A shadow-casting light parented under an entity shaded from the wrong direction and cast nothing.** `Light` created its Lite light with local direction `[0, 0, 1]` **and** parented it under the entity node, then wrote the entity's _world_ forward into `light.direction`. Lite composes `parentWorld × localMatrixFromDirection(direction, position)` and feeds `worldMatrix[8..10]` to the shader (`lib/light/directional-light.js` lines 8-10, 20-22), so the entity's rotation was applied twice — while the shadow frustum, fitted from `light.direction`/`light.position` directly, used the single-rotation value. | `shadows.browser.test.ts` asserted that the whole frame's **mean** luminance dropped when the feature was on. A frame that is wrong everywhere is still darker than one with no shadow pass at all. Nothing asserted _which_ pixels moved. | ignifx no longer parents a Lite light. `src/lite/light.ts` creates every kind with `parent = null`, and `syncLightWorldPose` writes the entity's world pose onto the light's own observables in each frame its `worldMatrixVersion` moved: the world **forward** axis for a directional or spot light, the world **up** axis for a hemispheric light's sky direction, and the world position for anything that has one. With no parent, `worldMatrix` _is_ the local matrix, so the shader, the lights UBO, and the shadow frustum cannot disagree. The pose write is also the "this light moved" nudge the UBO needs.                                              |

Two further facts fell out of the fix, both verified in `lib/`:

- **A `RenderTarget` sized by a `SurfaceContext` follows the canvas for free.** `resolveSize` re-reads
  `canvas.width`/`canvas.height` on every `buildRenderTarget` (`lib/engine/render-target.js`), and a
  surface resize calls each rendering context's `_resize`, which for a scene is `frameGraph.build()`
  (`lib/scene/scene-core.js` lines 67-68) — every target is reallocated and every task re-recorded,
  which is also what refreshes the bind groups holding the old views. So the chain needs no resize
  handling of its own, and the lazily allocated kind of target is the right one after all: the only
  rule is that a target must be written by an earlier task than the one that reads it.
- **`createImageProcessingTask` can only ever be the last effect.** It begins its render pass on
  `engine.scRT._colorView` unconditionally and accepts no target
  (`lib/frame-graph/image-processing-task.js`), so nothing downstream can read what it produced. The
  chain moves it to the end whatever `order` the component declares.

The regression tests are the assertions the old ones were missing: `post-process.browser.test.ts` now
asserts brightness and direction (exposure 2 is brighter than exposure 1; bloom lifts a background
corner that was below 8/255) at MSAA 1 and 4 and across a canvas resize, and
`shadows.browser.test.ts` samples named bands to prove which hemisphere of a ball is lit, that a
180-degree turn of the light entity swaps it, that a point light's lit region follows its entity, and
that the ground under a caster is darker than ground further away.

### Two more the goldens found, both now fixed (2026-09-06)

**A `Model` cast no shadow and received none.** `Model` declared `castShadows` and `receiveShadows`
in its schema and applied neither: `RenderSyncSystem.#rebuildCasters` walked only the world's
`MeshRenderer`s — `collectCasters` existed on that component and on no other — so an instantiated
glTF subtree never reached a generator's caster list, and Lite's per-mesh `receiveShadows`
(`index.d.ts` 7160) was never written across the clone. Found while regenerating the goldens
(`tests/visual/README.md`), which is why `gltf-viewer.png` showed a shadow catcher with nothing to
catch.

**The fix.** `ModelInstance` collects every mesh of the clone once, at instantiation — the tree's
shape is fixed from the moment `instantiateContainer` built it, so a per-frame walk would buy
nothing (`collectSubtreeMeshes`, `src/lite/gpu/mesh.ts`, the same structural `"material" in node`
test `overrideSubtreeMaterials` uses). `Model` answers `collectCasters` and `consumeCasterChange`
from that list exactly as `MeshRenderer` does from its single clone, and the sync system walks both
component kinds. Two cases needed more than symmetry. A **destroyed** model cannot report a caster
change, because it has left `world.components(Model)` before the system next runs — so `onDetach`
raises `RendererImpl.needsCasterRebuild`, which the next reconciliation consumes. And the caster
lists are now rebuilt only in a frame that owes no `rebuildSceneRenderables`: Lite's shadow task
builds a render task from the caster meshes and flushes its pending list by looking each caster
material's `_buildGroup` up in `scene._groups`, and a group that is not there yet is a bare
`throw Error()` inside the frame (`lib/frame-graph/render-task.js`). A `Model` is the ordinary way
to hit that — the component only exists once its glTF handle settled, so its material family
reaches the scene through the runtime material-swap path — and it cost 3 uncaught errors in 12
loads of the glTF viewer on SwiftShader before the gate was added. Regression tests:
a Node test that the system asks models for casters at all and that a destroyed one still rebuilds
the lists, and a browser test placing a `Box.glb` over a ground `MeshRenderer` and measuring the
band its shadow falls in (0 against 218 on SwiftShader, 2026-09-06).

**`rendering.clearColor` was never applied.** The section declared it and nothing read it: only
`Camera.clearColor` and `Environment.clearColor` reached `scene.clearColor`, so a project that named
a clear colour and no camera override got Lite's mid grey. **The fix.** `RendererImpl.applyClearColor`
is now the single writer — it decodes sRGB to linear and is what all three callers go through — and
`attachHandles` calls it with the setting as the render scene is created. That fixes the precedence
in place: the setting is written once, before any frame; an `Environment` writes over it when its
own field changes; the main camera's non-null override is written every frame and therefore wins.
Documented in `07-rendering.md` §2.1 and §2.5.
