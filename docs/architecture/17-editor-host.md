# 17 · Editor Host

**Status:** Design standard (pre-1.0) · **Packages:** `@ignifx/editor-host` · **Related:** `00-overview.md` §2, `15-devtools-and-diagnostics.md` §5, `14-platform-electron.md` §3; in `astrum-forge/ignifx-editor`: the editor plan §3.1–§3.6 and §5 (ask E0), ADR-E001, ADR-E008, spike S0.1

---

## 1. What it is

The ignifx editor (a separate application, `astrum-forge/ignifx-editor`) never bundles the engine. It runs the **project's own** engine instead: it starts the project's Vite dev server and embeds two pages from it in `<iframe>`s.

- The **scene view** is `/__ignifx_editor__/`, a page this package's Vite plugin adds. Its module creates an app from the project's `@ignifx/core`, with the project's extensions and scripts.
- The **play view** is the project's own `index.html`, unchanged, plus one call in `main.ts` that hands the app to the editor in development.

Both pages import the project's single copy of `@ignifx/core`, so a project script's `Component` is the same class the host sees, and the engine version is whatever the project installed. The editor talks to each page over a versioned JSON-RPC protocol on a `MessagePort`.

`@ignifx/editor-host` is an extension-layer package beside `@ignifx/devtools` (`00-overview.md` §2.1). It imports `@ignifx/core`, and its Vite entry imports `@ignifx/vite-plugin`'s module ids; both are peer dependencies, so the project's copies are the ones used. A project adds it as a development dependency at the same version as its `@ignifx/core`. It is on the engine's version line, not the editor's.

This release speaks protocol 0.3: the page, the handshake, liveness, the play controls, and the scene document transport (§6.1), with which the scene view mirrors the editor's open scene. Its one Babylon Lite module is `src/lite/gizmos.ts` (`CONSTITUTION.md` §3.4): the gizmos, the selection outline and a pick that resolves glTF models. `@babylonjs/lite` is a peer dependency, so the project's copy is the one used.

## 2. Two entries

| Entry                        | Runs in                                 | Exports                                                                                         |
| ---------------------------- | --------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `@ignifx/editor-host`        | The scene view and the play view (page) | `startEditorHost`, `startEditorPlayControls`, the protocol types and constants, the error codes |
| `@ignifx/editor-host/vite`   | The dev server's Node process           | `editorHostPlugin`, the module ids, and the source generators the plugin uses                   |
| `@ignifx/editor-host/client` | Type checking only                      | The ambient declaration of `virtual:ignifx/editor`                                              |

Importing either entry does nothing (`CONSTITUTION.md` §3.5). The only code with an import-time effect is the module the plugin generates for the scene view's page, which calls `startEditorHost`.

## 3. The Vite plugin

`editorHostPlugin({ editorOrigin, extensions?, bootScene?, heartbeatIntervalMs? })` returns two plugins. List them after `ignifx()` from `@ignifx/vite-plugin`, which serves `virtual:ignifx/scripts` and `virtual:ignifx/manifest`.

**`ignifx-editor-host`** (`apply: "serve"`, so a build never contains the scene view):

- A connect middleware, registered directly in `configureServer` so it answers before Vite's HTML fallback, serves `<base>__ignifx_editor__/` through `server.transformIndexHtml` (which adds Vite's HMR client) and redirects the path without its trailing slash. Every other request goes to Vite untouched.
- The page loads `virtual:ignifx/editor-host-entry`, a generated module that imports `startEditorHost` from `@ignifx/editor-host`, `scripts` and `acceptHotReload` from `virtual:ignifx/scripts`, `manifest` from `virtual:ignifx/manifest`, and `extensions` from the project's extensions module. It passes `import.meta.env.IGNIFX_CONFIG` as the settings, exactly as a template's `main.ts` does, then calls `acceptHotReload(host.app)` and hands every `ignifx:asset-changed` event to `host.assetChanged` (§6.1, engine ask E23); the `import.meta.hot` calls are written out literally. Every bare import resolves from the project root, so the host joins the project's module graph.
- **The extensions seam.** A template builds its extension list inline in `main.ts`, where nothing else can import it. The plugin imports `extensions()` from `src/extensions.ts` (the `extensions` option changes the path) when that file exists, and passes no extensions when it does not. All four templates are editor-ready (ask E2) and keep the list there, so `main.ts` and the scene view share it.
- **Pre-bundling.** Setting `optimizeDeps.entries` replaces Vite's default crawl of every HTML file, and Vite concatenates arrays when it merges a plugin's config. So when the extensions module exists, the plugin adds it to `entries`, restating `**/*.html` only if the project set no entries of its own. It also adds `@ignifx/editor-host` to `optimizeDeps.exclude`: served as it is, its `@ignifx/core` import resolves to the same pre-bundled core the game uses, rather than a second copy inside a pre-bundled host.
- **The engine version.** Core's build stamps `VERSION` from its `package.json`, but core run from source reports `"0.0.0"`. The plugin therefore reads `version` from the project's resolved `@ignifx/core/package.json` and passes it to the host as `engineVersion`; the host reports core's `VERSION` whenever it is stamped, and the plugin's version only when it is not.

**`ignifx-editor-host:play-controls`** (every command) serves `virtual:ignifx/editor`. Under `vite dev` the module calls `listenForEditorPlayControls(…)` as soon as it is evaluated, which is before the game's `main.ts` body runs, and exports `attachEditorPlayControls(app)`, which calls the connector's `attach(app)`; Vite replacing the module disposes the connector and the controls it attached (§5); the `import.meta.hot` calls are written out literally, because Vite finds them by reading the source. Under `vite build` it exports an empty function and imports nothing — the same shape as `acceptHotReload` (`15-devtools-and-diagnostics.md` §5). A project whose `main.ts` imports `virtual:ignifx/editor` therefore needs the plugin in `vite.config.ts` for both commands.

## 4. The scene view's host

`startEditorHost(options)` opens the channel **before its first `await`** (the editor posts the port on the iframe's `load` event, which can fire while `createApp` is still running), then creates the app with the project's extensions, settings and manifest, in edit mode (`createApp({ editMode: true })`, ADR-0028; `editMode: false` runs it as a game), calls `app.registerComponents(scripts)`, creates the persistent `editor` scene instance (`world.createScene("editor", { persistent: true })`) with the editor camera in it, loads `bootScene` through `app.world.loadScene` if one is given, and starts the app. With a canvas it then opens the render overlay for the gizmos. It resolves to an `EditorHost` handle that owns the app: `dispose()` stops the heartbeat, closes the port, removes the window listener and disposes the app. If creation, the scene load or `start()` fails, the channel is closed and the error is rethrown.

With a canvas the gizmos and the outline live in core's render overlay (`app.renderer.openOverlay()`, `07-rendering.md` §2.10, ADR-0031), so the scene view keeps the project's `rendering.msaaSamples`. Lite's own utility layer cannot be used in an ignifx app: registered after `app.start()` it blacks out the render scene, and at MSAA 4 it draws nothing (editor spike S0.2 §3.2).

The app is reached only through that handle, which lives in the generated module's scope. Nothing is global, so two apps (the scene view and the play view) stay independent even when Chromium puts both documents in one process (`CONSTITUTION.md` §3.6).

## 5. The play view

The game's `main.ts` calls `attachEditorPlayControls(app)` from `virtual:ignifx/editor`; the app stays reachable only through the entry's own reference. The templates call it after `await createApp(...)`, while the editor posts its port on the view's `load` event, which can come first. So the generated module listens before `main.ts` runs: `listenForEditorPlayControls(options)` keeps the newest port from exactly `editorOrigin` (closing the one it replaces) without reading from it, and `attach(app)` hands the window over to the controls in the same turn and serves that port, where the editor's `hello` has waited (engine ask E24). Only the first `attach` takes the waiting port; the controls serve every later port as usual. `startEditorPlayControls(app, options)` is the same controls without the early listener. Neither ever disposes the game's app. The controls answer four methods after the handshake, each with `{ isRunning, isPaused, frameCount }`:

| Method  | Effect                                                                                                                   |
| ------- | ------------------------------------------------------------------------------------------------------------------------ |
| `play`  | Clears `app.time.paused` and calls `app.start()` (a no-op when running)                                                  |
| `pause` | Sets `app.time.paused`; `updateWhenPaused` scripts and systems keep running                                              |
| `step`  | `app.stop()`, then one `app.step(deltaSeconds)` unpaused, then paused again; `deltaSeconds` defaults to `fixedDeltaTime` |
| `stop`  | `app.stop()`. The editor resets the game by reloading the view                                                           |

`app.step()` refuses to run beside the render loop, which is why `step` stops the loop first; `play` restarts it.

`playState` (no parameters, additive in 0.3) answers `{ state, frameCount, time }` without changing anything: `state` is `"playing"` (the loop runs, time not paused), `"paused"` (`app.time.paused`, including after `step`, which leaves the loop stopped on its frame) or `"stopped"` (no loop: before the game starts it, or after `stop`); `frameCount` is `app.time.frameCount` and `time` is `app.time.time`. After the handshake the controls send `playStateChanged` with the same report whenever `state` changes: a change a play method makes right after that method's answer, and one the game makes itself (setting `app.time.paused`, calling `app.stop()`) within one heartbeat interval, since core announces neither. The phase at the handshake is taken as known, so the first notification is the first change after it.

`playStats` (no parameters, additive in 0.3, engine ask E25) answers `{ fps, frameTimeMs, entityCount, frameCount }` without changing anything. `frameTimeMs` is the mean `rawDeltaMs` of the newest frames in `app.diagnostics`' frame history that add up to one second (all of them when there are fewer), and `fps` is `1000 / frameTimeMs`, both rounded to hundredths; a paused game still renders, so both are measured while paused, and both are `0` while the frame loop does not run (stopped, or stepped and left on its frame) or before its first frame. `entityCount` counts the live entities of every scene instance, persistent ones and the members of instanced prefabs included; `frameCount` is `app.time.frameCount`. There is no notification: the editor's stats strip polls `playStats` while it is shown, twice a second, so the host keeps no timer and sends nothing nobody reads.

The play controls also relay the game's reports with the scene view's shapes, as play notifications (`HostCapability.logRelay`, additive in 0.3): `log` for every record of `app.log`, `hostError` with `AppErrorData` for every `app.onError` report, and `hotReloaded` for every hot reload. What the game reports before the editor's `hello` is kept, the newest 256, and sent right after `ready`; a stack is the page's own (Chromium's `at … (url:line:column)` frames, the URLs the dev server serves), which the editor maps back to project files.

## 6. The protocol

The host speaks protocol **0.3** of `@ignifx/editor-protocol`, which the editor repository publishes on its own version line (ADR-E008). Until that package is on npm, `src/protocol/` is a copy of its modules, one file for each, with identical code; afterwards the host depends on it. `src/protocol/index.ts` lists the one difference, in comments only, and the two editor modules a host does not need. `test/wire.test.ts` replays the editor's recorded 0.2 host messages (`test/fixtures/host-0.2-wire.json`) at the current protocol line, and `test/wire-0.3.test.ts` replays the 0.3 fixture (`test/fixtures/host-0.3-wire.json`), both copied from the editor repository, through a live host.

1. **Connect.** The editor posts `{ type: "ignifx-editor/connect" }` to the view's window with a `MessagePort` as the one transferred object. The host accepts it only when `event.origin` equals `editorOrigin` (§7). A view reload is a new document that needs a new port, and the editor sends a fresh one on every `load`; the host also accepts a new port at any time, closing the previous one and stopping its heartbeat. Both views listen before their first `await` (the play view through `virtual:ignifx/editor`, §5), so the one message the editor sends on `load` is enough; a host from before engine ask E24 could miss it in the play view.
2. **Handshake.** The editor sends `hello { editorVersion, protocol }`. A host whose protocol version is compatible answers `ready { engineVersion, protocol, capabilities, hostKind }`; otherwise it answers `incompatibleProtocol` with its own version in `data`. Before 1.0 the minor plays the role of the major, so compatible means the same major and minor (0.3 refuses 0.2); from 1.0 only the majors must match. Malformed parameters get `invalidParams`.
3. **Liveness.** `ping` is answered with `"pong"` at any time, ahead of any request still running. After `ready`, the host sends a `heartbeat` notification every `heartbeatIntervalMs` (default 1000). Chromium reports nothing to the parent when an out-of-process iframe's renderer dies, so a stopped heartbeat is how the editor finds a dead view.
4. **Everything else.** Requests are answered one at a time, in arrival order: an `applyOps` sent right after an `openScene` sees the scene that request opened. A method the host does not have gets `methodNotFound`; a known method before `hello` gets `notReady`; a message that is not a JSON-RPC envelope gets `invalidRequest` with `id: null`. A failing method gets `internalError`, with the `IgnifxError` code in `data.code` when there is one.

The scene host lists `heartbeat`, plus `gizmos`, `screenshot`, `viewMode2d` and `pick2d` when it has a canvas; a headless host has none of their methods and `setViewMode` accepts `"3d"` only there. Both list `logRelay` (additive in 0.3): they relay the app's log lines, `app.onError` reports and hot reloads (below and §5), and `hotReloadDefaults` (additive in 0.3, engine ask E25): after a script's hot reload the scene follows changed defaults itself (§6.1). The play controls list `heartbeat`, `playControls` and `logRelay`.

### 6.1 Scene documents (protocol 0.3)

The editor holds each open scene as a document and the scene view mirrors it: the editor opens the scene with the whole file, then sends every command's ops as it applies them to the document. The host reports what the user does in the view as notifications, which the editor turns into commands; it never edits the document. Every uid on the wire is a document uid. The document's entities live in their own scene instance; the editor camera lives in the persistent `editor` instance, which no selection, pick or `readBack` reaches. A member of an instanced prefab resolves to its nearest document ancestor, the instance root. The scene methods answer `notReady` until the app has started; the host's first `schemasChanged`, sent after `ready` once the app has started, is the editor's cue.

| Method                | What the host does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

Answers `{ entityCount, warnings, viewMode }`, then sends `sceneOpened` with the same `viewMode` (§6.2). A build failure is `internalError` with the code.                                                                                                                                                                                                                                                                                                     |
| `closeScene`          | Unloads the open document, if any, and clears the selection.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `applyOps`            | Applies the ops in order, never stopping at a failure, and answers `{ applied, failures }` (codes: editor-core's ten, plus `engineError` with the `IGX-` code). See below.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `readBack`            | `serializeScene` of the document with `engineVersion` omitted and the host's settings: the requested records in file order, the uids not found, the settings, and the serializer's issues.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `select`              | Keeps the document uids, in order, without duplicates; outlines them; attaches the gizmo to the last one. In 2D mode the bounds are sprite quads, tilemap extents and positions (§6.2).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

| `getColliderOutlines` | `{ outlines }` for the requested document entities that are open: each enabled collider's world-space line segments, six numbers a segment, from `app.physics.colliderOutlines` and `app.physics2d.colliderOutlines` (read by shape; a 2D outline lies at its entity's world `z`), rounded to 0.01 mm. Empty without a physics extension; `noScene` while nothing is open.                                                                                                                                                                                                                                                                                                                                                                             |
| `getSchemas`          | `describeRegisteredSchemas(app.world.registry, describeSchemas())` of the live registry (engine, extensions and the project's scripts, the host's own left out), each with its `toJsonSchema` as `propsSchema`, plus core's file-format entries. Fields carry their inspector options (`step`, `hidden`, `readonly`, `group`, `assetType`, `componentType`); components carry `allowMultiple` and `package` (optional 0.3 members since editor PR #35). `ignifx/Transform` carries `builtIn: true`.                                                                                                                                                                                                                                                    |

**Additions within 0.3 (engine ask E21).** `pick`'s `ray` and `plane` and the `describeSettings` method are optional additions, so the protocol stays 0.3: an editor treats a `pick` answer without `ray` as one from an older host, and `methodNotFound` from `describeSettings` the same way. They were written here first, with their fixture messages (`pickMissRay`, `pickMissRay2d`, `describeSettings`, `describeSettingsResponse`); the editor copies the module and the fixture back into `@ignifx/editor-protocol`, after which the two are byte-identical again. Engine ask E22 adds, the same way, the optional `viewMode` of `openScene`'s result and of `sceneOpened` (fixture: `openSceneResponse`, `sceneOpened`, `sceneOpened2d`, and the 2D hit `pickHit2d`); an editor treats an answer without it as one from an older host. Engine ask E23 adds the `assetReloaded` notification (fixture: `assetReloaded`, `assetReloadedModel`); an older host never sends it. ADR-0028's amendment of 2026-10-20 adds `setAnimateMaterials` and `getColliderOutlines` (fixture: `setAnimateMaterials`, `getColliderOutlines`, `getColliderOutlinesResponse`), which an older host answers with `methodNotFound`; the scene view's physics bodies exist without stepping, so the outlines follow every move the editor makes. Engine ask E25 adds the play view's `playStats` method (fixture: `playStats`, `playStatsResponse`, `playStatsStoppedResponse`), which an older host answers with `methodNotFound`, and the `hotReloadDefaults` capability, which an older host does not list.

**Ops on the live world.** `createEntity` and `instantiate` build the records as a subtree with `instantiateScene`, loading their assets first with `loadSceneDependencies`, then re-decode the props that reference the rest of the document; a uid already in use is `duplicateUid`. `destroyEntity` is `destroyImmediate`. `reparent` keeps the local transform (`setParent(parent, { worldPositionStays: false })`) and both it and `reorder` place the entity among its document siblings with `entity.setSiblingIndex`. `setEntityField` writes `name`, `active`, `static`, `layer` (by name) and `tags`; `setTransform` the local position, rotation and scale. `addComponent` is `addComponentFromRecord` (uid, `enabled`, decoded props, index); an unregistered type is `engineError` `IGX-0307`. `setProp` decodes the value with the field's schema, rebuilding the field's JSON for a deeper path, and assigns it the way the inspector writes a field; an absent value restores the default. `setSceneSetting` edits the settings the host keeps, which `readBack` writes; the systems that read scene settings read them when a scene opens. `setOverride` and `removeOverride` edit the instance root's override list and rebuild its subtree from the prefab, then re-point references from the rest of the document into it. After any failure the editor resends `openScene`, so the host does not roll back.

**Notifications.** `sceneOpened` after each `openScene` answer. `schemasChanged` after `ready` once the app has started, and after every `app.hotReload.onApplied`, which covers a script that changes its fields and one registered for the first time. `hotReloaded` on `app.hotReload.onApplied`, each error as `{ message, code, stack }`. `selectionChanged` when a click in the view changes the selection (a plain click replaces it, Shift, Ctrl or Cmd toggles, a click on nothing clears it). `transformDragging`, at most every 50 ms, and `transformDragged` at pointer-up with `before` read at drag start, both rounded with `canonicalizeNumber`; nothing is sent when the drag changed nothing. `hostError` on `app.onError`: the thrown error's `code` and `message`, and `AppErrorData` as `data` (`source`, `phase` and `phaseName`, `entity` and `entityName`, `component` as its `typeId`, `stack`). `log` for every record of `app.log`, without `data` but for the first `Error` in it as `error: { message, code, stack }`; the app's default `onError` handler logs one such line per report, just before the `hostError`. `assetReloaded` after an asset reload in place (below).

**Asset reload in place (engine ask E23).** The page's module hands every `ignifx:asset-changed` event of the Vite plugin to `EditorHost.assetChanged(change)`. An asset the app has not loaded, a removed file, the open document's own file, and any type outside `scene`, `model`, `mesh`, `material`, `spriteatlas` and `shader` are left alone. Otherwise the host calls `app.assets.reload(address)` and waits for the handle's `onReplaced` (an asset error on `app.onError` meanwhile ends the wait; the assets service reports a failed reload only there, without the address). The renderers read a model, mesh, material and sprite atlas from their handle every frame, and a shader's materials rebuild on its `onReplaced`; a texture is left out because the materials and atlases built from it keep the texture they were given, which the default reload unloads. For a scene or prefab the host then rebuilds each document instance root that instances it, directly or through the scenes it instances (an instance inside another rebuilt one is rebuilt with it), the way `setOverride` does: the root's record, transform, overrides and document children are kept, the members are built from the new file, and references from the rest of the document into the subtree are resolved again. `readBack` then writes the new file's hash. The rebuild runs in the same queue as the requests, so no request sees half of it; a root that fails to rebuild is a `hostError`. Last the host sends `assetReloaded { address, type, entities }`, `entities` being the rebuilt roots in document order, so the editor compares its document with the view instead of reloading it.

**Hot-reloaded defaults (engine ask E25).** A script's hot reload keeps every live field value (`15-devtools-and-diagnostics.md` §5), so a field the document leaves out would keep the default from before the edit. The host therefore keeps, for each document component, which fields its record sets (from `openScene`, `createEntity`, `addComponent` and `setProp`, where a value sets the field and an absent one leaves it out), and for each instance root its override list (from `openScene`, `createEntity`, `instantiate` and the override ops). It reads every registered type's file-form defaults once the app has started and again for the types each `app.hotReload.onApplied` report names. When a field's default changed, or a field is new, the host, in the same queue as the requests: gives that field `createDefault()` on each document component of the type whose record leaves it out, and keeps it where the record sets it, even to the old default; then rebuilds each outermost instance root whose members (not the document's own components) hold a component of the type, the way an asset reload does, but with the override lists the document holds, because the serializer recomputes overrides by diffing the live members with their scene and would read every stale member as an override. Members take the prefab's values with the new defaults and the instance's overrides on top; instance roots under a rebuilt one are rebuilt with it, with their own lists. A root that fails to rebuild is a `hostError`. No notification follows: `hotReloaded` and `schemasChanged` go out as before, and a request sent after them sees the defaults applied. A component whose type the host did not know when the scene opened has no instance, which this does not repair. The host lists `hotReloadDefaults` in `ready`, and an editor that sees it does not reopen the scene for changed defaults.

**The view.** The gizmos are Lite's position, rotation and scale gizmos in core's render overlay, attached to the primary selection's `transform.lite`; Lite writes the entity's own transform, so drag end needs no write-back (S0.2 §2). A detached Lite gizmo keeps drawing, so a hidden one is collapsed to zero scale. Snapping is a post-correction in the host's drag listener, which keeps the unsnapped value apart (S0.2 §3.4). The outline is a line box over each selected entity's mesh bounds, because Lite's bounding-box gizmo drags whatever is pressed inside it (S0.2 §7). The editor camera is a `runInEditMode` script beside a `Camera` of priority 1 000 000: left drag orbits (yielding to the gizmo by Lite's three rules, S0.2 §4.2), middle drag pans, right drag with W, A, S, D, Q and E flies, the wheel dollies, and a left click picks.

### 6.2 The 2D view (engine ask E22)

The host does not depend on `@ignifx/2d`. It reaches the project's copy by data: `app.twoD` when the project registers the extension, and the 2D component classes by type id from the registry (`ignifx/Camera2D`, `ignifx/SpriteRenderer`, `ignifx/Tilemap`), as `@ignifx/physics-2d` finds a `Tilemap` (`11-2d-toolkit.md` §2.5).

- **The view mode a scene is made for.** After `openScene` builds the file, the host reports `viewMode: "2d"` when the project draws sprites only (`twoD.mode: "sprite"`, read after the file's own `settings.twoD`), or when the scene has a `Camera2D` and no 3D `Camera`; otherwise, and always without `@ignifx/2d`, `"3d"`. It does not switch by itself; the editor sends `setViewMode`.
- **The 2D editor camera** (S0.2 §5). With `@ignifx/2d` the editor camera's entity also carries a `Camera2D` of priority 1 000 000, disabled in 3D mode, and the `EditorCamera2D` script. In 2D mode the `Camera2D` is enabled, so the sprites draw through it and the level's own `Camera2D` keeps exactly what the file says, and the 3D `Camera` turns orthographic, 500 m in front of the plane looking along +Z with the same half-height, so the gizmo overlay and the 3D picker see the same rectangle. The zoom is `Camera2D`'s (screen pixels per layer pixel). Middle drag, right drag and Space with left drag pan; the wheel zooms about the cursor through 0.125, 0.25, 0.5, 1, 2, 3, 4, 6, 8, 12, 16, 24 and 32; a left click picks. The first switch to 2D on a document starts where the level's highest-priority `Camera2D` looks, at its `orthographicSize`, or frames the document when it has none; reopening the same address keeps the view. Back in 3D, the 3D camera takes up where it was.
- **Frame.** `frame` in 2D mode fits the union of the entities' positions, every `SpriteRenderer` quad under them (`SpriteRenderer.bounds`, as the last frame synced it) and every loaded `Tilemap`'s extent, with a 20 % margin.
- **Pick** (`pick2d`). In 2D mode `pick` and view clicks call `app.twoD.pickAt` at the backing pixel with `includeUnpickable: true` and a filter to the document's scene, so the editor selects what the game marks unpickable. A hit answers `point: [x, y, 0]`, the world point under the cursor, and `distance: null`. Hit or miss, `ray` is the orthographic eye's (straight down +Z, built from the 2D camera's own arithmetic, so it never lags a pan by a frame) and `plane` is the same world point. Without a sprite hit, a `"mixed"` project, or one without `@ignifx/2d`, goes on to `pickAsync` through the orthographic eye; a `"sprite"` project misses.

## 7. Security

The host page drives a live engine, so two independent checks keep other pages away from it:

- **`frame-ancestors`.** Under `vite dev` both views are served with `Content-Security-Policy: frame-ancestors <editorOrigin>`. A website the developer has open cannot frame `127.0.0.1:<port>/__ignifx_editor__/` or the game's `index.html`. The scene view's page sets the header itself; for the play view the plugin adds it to every request a browser makes for a page (a `GET` or `HEAD` whose `Accept` names `text/html`), leaving the page's content unchanged. A tab opened on the dev server is not a frame, so the game still runs standalone. A `Content-Security-Policy` the project sets in `server.headers` replaces the plugin's on the play view.
- **The origin check.** Both hosts ignore a connect message whose `event.origin` is not exactly `editorOrigin`, so only the editor can hand either view a port, framed or not.

`editorOrigin` must be `scheme://host[:port]` with no path, wildcard, quote, comma or semicolon (`IGX-1801`), which also keeps it from ending the CSP directive early. The editor passes it when it spawns the dev server; it differs between the packaged editor (`ignifx://app`) and the editor's own development server, so it is never hard-coded. Keep the dev server on loopback. Production builds contain no host code at all.

## 8. Errors

The package owns `IGX-1800`–`IGX-1899`. `IGX-1801`: `editorOrigin` is not an origin. `IGX-1802`: no `window` and no `messageTarget` (Node). `IGX-1803`: an option outside its domain. The page half throws `IgnifxError`; the Vite plugin throws `EditorHostPluginError` with the same codes, because it runs without `@ignifx/core`, as `@ignifx/vite-plugin` does.

- **The grid and the light and camera gizmos** are not drawn yet.
