# 17 · Editor Host

**Status:** Implemented; describes the code on `main` · **Packages:** `@ignifx/editor-host` · **Related:** `00-overview.md` §2, `15-devtools-and-diagnostics.md` §5, `14-platform-electron.md` §3, ADR-0028, ADR-0031; in `astrum-forge/ignifx-editor`: ADR-E001, ADR-E008 and `docs/protocol.md` (the editor's side of the protocol)

This document is the description of the engine–editor protocol: what each method, notification and capability makes the host do. The wire shapes (parameters, results, constants) are the types in `packages/editor-host/src/protocol/`.

**Source map** (`packages/editor-host/src/`)

- `host.ts` — `startEditorHost` (the scene view, §4). `play-controls.ts`, `play-stats.ts`, `play-query.ts`, `play-input.ts` — the play view (§5). `channel.ts` — the port, the handshake, the request queue and what runs beside it (§6). `app-reports.ts` — log, error and hot-reload relay with its clipping.
- `protocol/` — the wire types, a copy of the editor's `@ignifx/editor-protocol` (§6): `handshake.ts` (capabilities), `scene.ts`, `scene-ops.ts`, `play.ts`, `render-views.ts`, `light-probe-bake.ts`, `rpc.ts` (error codes), `version.ts`.
- `scene/scene-host.ts` — the scene methods (§6.1); `scene/document.ts`, `ops.ts`, `held-references.ts` — the mirrored document, ops and instance rebuilds; `asset-reload.ts`, `defaults.ts` — reload in place and hot-reloaded defaults; `schemas.ts`, `settings.ts`.
- `scene/editor-camera.ts`, `editor-camera-2d.ts`, `view-2d.ts`, `gizmo-drag.ts`, `editor-grid.ts`, `grid.ts`, `rect-pick.ts`, `screenshot.ts`, `collider-outlines.ts`, `tilemap-cells.ts`, `sample-animation.ts`, `sample-sprite-animation.ts` — the view and its methods (§6.1, §6.2).
- `scene/game-view.ts`, `thumbnails.ts` (§6.3); `scene/light-probe-baker.ts` (§6.4).
- `lite/` — the only files that touch Babylon Lite: `gizmos.ts`, `grid.ts`, `editor-lines.ts`, `sprite-game-view.ts`, `drawn-meshes.ts`.
- `vite.ts`, `vite/plugin.ts`, `vite/modules.ts` — `editorHostPlugin` and the generated modules (§3). `error-codes.ts` — `IGX-1801`–`IGX-1803` (§8).
- Tests that pin the wire: `packages/editor-host/test/wire.test.ts`, `wire-0.3.test.ts` and `test/fixtures/`.

Invariants to keep:

- The host runs the project's own copies of `@ignifx/core`, Babylon Lite and the extensions; every optional package (`@ignifx/2d`, `@ignifx/3d`, `@ignifx/input`, physics) is reached by type id or by shape, never imported (§1, §5, §6.2).
- Nothing is global and importing an entry does nothing; the app is reachable only through the handle (§2, §4).
- Both views listen for the port before their first `await` (§4, §5).
- A connect message is accepted only from exactly `editorOrigin`, and both views are served with `frame-ancestors <editorOrigin>` (§7).
- Requests are answered one at a time in arrival order; only `ping`, `renderThumbnail`, `bakeLightProbes` and `cancelBake` run beside the queue (§6).
- The host never edits the document and never rolls back; every uid on the wire is a document uid (§6.1).
- A new method, field or capability is an addition within protocol 0.3; `src/protocol/` changes only together with the editor's copy (§6).
- Every rebuild of an instance starts from the override list the document holds, never from a diff of the live members (§6.1).
- Reports and answers are clipped to the protocol's caps before they are sent (§5).
- A production build contains no host code (§3, §7).

---

## 1. What it is

The ignifx editor (a separate application, `astrum-forge/ignifx-editor`) never bundles the engine. It runs the **project's own** engine instead: it starts the project's Vite dev server and embeds two pages from it in `<iframe>`s.

- The **scene view** is `/__ignifx_editor__/`, a page this package's Vite plugin adds. Its module creates an app from the project's `@ignifx/core`, with the project's extensions and scripts.
- The **play view** is the project's own `index.html`, unchanged, plus one call in `main.ts` that hands the app to the editor in development.

Both pages import the project's single copy of `@ignifx/core`, so a project script's `Component` is the same class the host sees, and the engine version is whatever the project installed. The editor talks to each page over a versioned JSON-RPC protocol on a `MessagePort`.

`@ignifx/editor-host` is an extension-layer package beside `@ignifx/devtools` (`00-overview.md` §2.1). It imports `@ignifx/core`, and its Vite entry imports `@ignifx/vite-plugin`'s module ids; both are peer dependencies, so the project's copies are the ones used. A project adds it as a development dependency at the same version as its `@ignifx/core`. It is on the engine's version line, not the editor's.

The host speaks protocol 0.3 (§6). Its Babylon Lite code is in `src/lite/` (`CONSTITUTION.md` §3.4): the gizmos, the selection outline and a pick that resolves glTF models (`gizmos.ts`), the grid (`grid.ts`), the editor's line sets (`editor-lines.ts`), the 2D game view (`sprite-game-view.ts`) and the walk over drawn meshes for box selection (`drawn-meshes.ts`). `@babylonjs/lite` is a peer dependency, so the project's copy is the one used.

## 2. Entries

| Entry                        | Runs in                                 | Exports                                                                                         |
| ---------------------------- | --------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `@ignifx/editor-host`        | The scene view and the play view (page) | `startEditorHost`, `startEditorPlayControls`, the protocol types and constants, the error codes |
| `@ignifx/editor-host/vite`   | The dev server's Node process           | `editorHostPlugin`, the module ids, and the source generators the plugin uses                   |

Importing any of the three does nothing (`CONSTITUTION.md` §3.5). The only code with an import-time effect is the module the plugin generates for the scene view's page, which calls `startEditorHost`.

## 3. The Vite plugin

`editorHostPlugin({ editorOrigin, extensions?, bootScene?, heartbeatIntervalMs? })` returns two plugins. List them after `ignifx()` from `@ignifx/vite-plugin`, which serves `virtual:ignifx/scripts` and `virtual:ignifx/manifest`.

**`ignifx-editor-host`** (`apply: "serve"`, so a build never contains the scene view):

- A connect middleware, registered directly in `configureServer` so it answers before Vite's HTML fallback, serves `<base>__ignifx_editor__/` through `server.transformIndexHtml` (which adds Vite's HMR client) and redirects the path without its trailing slash. Every other request goes to Vite untouched.
- The page loads `virtual:ignifx/editor-host-entry`, a generated module that imports `startEditorHost` from `@ignifx/editor-host`, `scripts` and `acceptHotReload` from `virtual:ignifx/scripts`, `manifest` from `virtual:ignifx/manifest`, and `extensions` from the project's extensions module, which it calls for the scene view's app and passes again as `createExtensions` for the thumbnail stage. It passes `import.meta.env.IGNIFX_CONFIG` as the settings, exactly as a template's `main.ts` does, then calls `acceptHotReload(host.app)` and hands every `ignifx:asset-changed` event to `host.assetChanged` (§6.1); the `import.meta.hot` calls are written out literally. Every bare import resolves from the project root, so the host joins the project's module graph.
- **The extensions seam.** A template builds its extension list inline in `main.ts`, where nothing else can import it. The plugin imports `extensions()` from `src/extensions.ts` (the `extensions` option changes the path) when that file exists, and passes no extensions when it does not. All four templates keep the list there, so `main.ts` and the scene view share it.
- **Pre-bundling.** Setting `optimizeDeps.entries` replaces Vite's default crawl of every HTML file, and Vite concatenates arrays when it merges a plugin's config. So when the extensions module exists, the plugin adds it to `entries`, restating `**/*.html` only if the project set no entries of its own. It also adds `@ignifx/editor-host` to `optimizeDeps.exclude`: served as it is, its `@ignifx/core` import resolves to the same pre-bundled core the game uses, rather than a second copy inside a pre-bundled host.
- **The engine version.** Core's build stamps `VERSION` from its `package.json`, but core run from source reports `"0.0.0"`. The plugin therefore reads `version` from the project's resolved `@ignifx/core/package.json` and passes it to the host as `engineVersion`; the host reports core's `VERSION` whenever it is stamped, and the plugin's version only when it is not.

**`ignifx-editor-host:play-controls`** (every command) serves `virtual:ignifx/editor`. Under `vite dev` the module calls `listenForEditorPlayControls(…)` as soon as it is evaluated, which is before the game's `main.ts` body runs, and exports `attachEditorPlayControls(app)`, which calls the connector's `attach(app)`; Vite replacing the module disposes the connector and the controls it attached (§5); the `import.meta.hot` calls are written out literally, because Vite finds them by reading the source. Under `vite build` it exports an empty function and imports nothing — the same shape as `acceptHotReload` (`15-devtools-and-diagnostics.md` §5). A project whose `main.ts` imports `virtual:ignifx/editor` therefore needs the plugin in `vite.config.ts` for both commands.

## 4. The scene view's host

`startEditorHost(options)` opens the channel **before its first `await`** (the editor posts the port on the iframe's `load` event, which can fire while `createApp` is still running), then creates the app with the project's extensions, settings and manifest, in edit mode (`createApp({ editMode: true })`, ADR-0028; `editMode: false` runs it as a game), calls `app.registerComponents(scripts)`, creates the persistent `editor` scene instance (`world.createScene("editor", { persistent: true })`) with the editor camera in it, loads `bootScene` through `app.world.loadScene` if one is given, and starts the app. With a canvas it then opens the render overlay for the gizmos. It resolves to an `EditorHost` handle that owns the app: `dispose()` stops the heartbeat, closes the port, removes the window listener and disposes the app. If creation, the scene load or `start()` fails, the channel is closed and the error is rethrown.

With a canvas the gizmos and the outline live in core's render overlay (`app.renderer.openOverlay()`, `07-rendering.md` §2.10, ADR-0031), so the scene view keeps the project's `rendering.msaaSamples`. Lite's own utility layer cannot be used in an ignifx app: registered after `app.start()` it blacks out the render scene, and at MSAA 4 it draws nothing.

The app is reached only through that handle, which lives in the generated module's scope. Nothing is global, so two apps (the scene view and the play view) stay independent even when Chromium puts both documents in one process (`CONSTITUTION.md` §3.6).

## 5. The play view

The game's `main.ts` calls `attachEditorPlayControls(app)` from `virtual:ignifx/editor`; the app stays reachable only through the entry's own reference. The templates call it after `await createApp(...)`, while the editor posts its port on the view's `load` event, which can come first. So the generated module listens before `main.ts` runs: `listenForEditorPlayControls(options)` keeps the newest port from exactly `editorOrigin` (closing the one it replaces) without reading from it, and `attach(app)` hands the window over to the controls in the same turn and serves that port, where the editor's `hello` has waited. Only the first `attach` takes the waiting port; the controls serve every later port as usual. `startEditorPlayControls(app, options)` is the same controls without the early listener. Neither ever disposes the game's app. The controls answer four methods after the handshake, each with `{ isRunning, isPaused, frameCount }`:

| Method  | Effect                                                                                                                   |
| ------- | ------------------------------------------------------------------------------------------------------------------------ |
| `play`  | Clears `app.time.paused` and calls `app.start()` (a no-op when running; after `step` it restarts the loop)               |
| `pause` | Sets `app.time.paused`; `updateWhenPaused` scripts and systems keep running                                              |
| `step`  | `app.stop()`, then one `app.step(deltaSeconds)` unpaused, then paused again; `deltaSeconds` defaults to `fixedDeltaTime` |
| `stop`  | `app.stop()`. The editor resets the game by reloading the view                                                           |

`app.step()` refuses to run beside the render loop, which is why `step` stops the loop first; `play` restarts it, and `app.start()` runs the extensions' `onStart` only once, so the game resumes where it was.

Four more methods read the game without changing it:

| Method         | Effect                                                                             |
| -------------- | ---------------------------------------------------------------------------------- |
| `playState`    | `{ state, frameCount, time }` (below)                                              |
| `playStats`    | `{ fps, frameTimeMs, entityCount, frameCount }` (below)                            |
| `screenshot`   | `{ dataUrl, width, height }`: the game's canvas as an image (below)                |
| `queryRuntime` | `{ entity, omittedComponents, frameCount, time }`: one entity's live state (below) |

`playState` (no parameters) answers `{ state, frameCount, time }` without changing anything: `state` is `"playing"` (the loop runs, time not paused), `"paused"` (`app.time.paused`, including after `step`, which leaves the loop stopped on its frame) or `"stopped"` (no loop: before the game starts it, or after `stop`); `frameCount` is `app.time.frameCount` and `time` is `app.time.time`. After the handshake the controls send `playStateChanged` with the same report whenever `state` changes: a change a play method makes right after that method's answer, and one the game makes itself (setting `app.time.paused`, calling `app.stop()`) within one heartbeat interval, since core announces neither. The phase at the handshake is taken as known, so the first notification is the first change after it.

`playStats` (no parameters) answers `{ fps, frameTimeMs, entityCount, frameCount }` without changing anything. `frameTimeMs` is the mean `rawDeltaMs` of the newest frames in `app.diagnostics`' frame history that add up to one second (all of them when there are fewer), and `fps` is `1000 / frameTimeMs`, both rounded to hundredths; a paused game still renders, so both are measured while paused, and both are `0` while the frame loop does not run (stopped, or stepped and left on its frame) or before its first frame. `entityCount` counts the live entities of every scene instance, persistent ones and the members of instanced prefabs included; `frameCount` is `app.time.frameCount`. There is no notification: the editor's stats strip polls `playStats` while it is shown, twice a second, so the host keeps no timer and sends nothing nobody reads.

`screenshot` captures the game's canvas with the scene view's request and answer: `{ width?, height?, format: "png" | "jpeg", quality? }` → `{ dataUrl, width, height }`, each side 1 to `SCREENSHOT_MAX_SIZE` (2048), the same size rule and encoding (`src/scene/screenshot.ts` serves both views). It changes nothing: a paused game is captured paused, since it still renders. While the frame loop does not run (before the game starts it, after `stop`, after `step`) it fails with `notPlaying` (`-32003`), and before the game's first frame with `notReady`, the code the scene view uses while it starts. Only a canvas-backed game has the method and lists `HostCapability.screenshot` in `ready`; a headless one answers `methodNotFound`. A capture waits for the game's next frame, and the channel answers one request at a time, so the controls check `app.isRunning` every 50 ms while it waits: when the game stops its own loop first (`app.stop()`, `dispose()`), the answer is `notPlaying` and the requests behind it go on. A play view that is hidden or throttled (no `requestAnimationFrame`) still runs its loop, so that check does not fire: the answer only comes late, and the editor's play request timeout (10 s, `PLAY_REQUEST_TIMEOUT_MS`) bounds the wait.

`queryRuntime` takes `{ entity, components? }`, an entity uid and an optional list of type ids, and answers the entity as core's `serializeEntity` writes it from the live world: `{ uid, name, parent, transform, … , components }`, the scene format's entity record. It is the serialized form only: what a component does not serialize is not visible, and nothing is evaluated (no expressions, no script calls). With `components`, only components of those type ids are kept (an id the entity does not carry matches nothing). `components` may name at most 64 type ids (`invalidParams` otherwise). The answer is bounded twice. Each value is capped while it is copied: a prop string is clipped to `QUERY_RUNTIME_MAX_STRING_LENGTH` (65,536, a quarter of the budget, ending `… [clipped]`, so one long string does not cost its component its place), a list is cut to `HOST_LIST_MAX_LENGTH` (4096) items, an object keeps its first `QUERY_RUNTIME_MAX_KEYS` (256) keys, and every key, the entity's `name` and `layer`, each component `type` and each of at most 256 tags is clipped to 256 characters; when two keys clip to the same one, the first keeps it. Keys are written as own properties, so a map key `__proto__` stays an entry. No marker is written into a value: a map's keys can be any string (core checks schema field names, `^[A-Za-z][A-Za-z0-9]*$`, but not map keys), so no key would be safe. What the caps left out (keys, list items, tags) is counted in `omittedEntries` instead, and a value that is not JSON (a non-finite number, a function or `undefined` from a custom codec) or nests deeper than 256 levels becomes `null`. And the whole `result` is at most `QUERY_RUNTIME_MAX_JSON_LENGTH` (262,144) UTF-16 code units as JSON text: components are added in the entity's order, at most `QUERY_RUNTIME_MAX_COMPONENTS` (64) of them, until the next one would not fit; it and every component after it are counted in `omittedComponents` (a copy that cannot fit stops as soon as that is certain, so a huge component costs no more than the budget). The editor's `isQueryRuntimeResult` checks the same length. `frameCount` and `time` say when it was read. It changes nothing. A uid no live entity has is `unknownEntity` (`-32004`): a scene's own entities keep their file uids at run time, but entities a script or a prefab spawns get new ones each run. While the game is stopped (before it starts, after `stop`) it answers `notPlaying`; a paused game answers, and so does a stepped one, which is paused on its frame, so pause, `step`, `queryRuntime` reads the game frame by frame. Every play view lists `HostCapability.queryRuntime`.

One more method feeds the game input:

| Method      | Effect                                                                              |
| ----------- | ----------------------------------------------------------------------------------- |
| `sendInput` | `{ queued }`: key and pointer events queued into the game's own `app.input` (below) |

`sendInput` takes `{ events }`, 1 to `SEND_INPUT_MAX_EVENTS` (64) of them, in order: `{ type: "keydown" | "keyup", control }`, where `control` is the `<Keyboard>` control name (`w`, `space`, `arrowUp`, `shiftLeft`: the physical key, letters and digits only), and `{ type: "pointermove" | "pointerdown" | "pointerup", x, y, button? }`, where `x` and `y` are fractions of the game's canvas from 0 to 1 and `button` an integer from 0 to 4 (default 0). The controls check every event first (a malformed one, or a key the game's keyboard does not have, is `invalidParams` and nothing is queued), then hand each to `app.input.simulateEvent`, the way headless tests drive the engine: positions become backing-store pixels (`x × canvas.width`), and a move or release reports the motion since the previous pointer event it sent in CSS pixels (`× clientWidth / width`), a press none, as the page's own pointer adapter does. The game resolves them on its next frame, through the same pipeline as real input. A held key stays down until a `keyup`; the editor releases what it pressed. It answers `{ queued }`, the number of events. Nothing is dispatched to the DOM, to the editor's window or to the operating system: the events exist only in the game's input queue. While the game is stopped it answers `notPlaying`; a paused game takes them, and so does a stepped one. A stepped game runs no frames, so it never drains its input queue by itself: events wait until the next `step` (or `play`), and an agent that sends input to a stepped game steps after sending. The checks run before anything is queued; if `simulateEvent` itself throws partway (a broken `@ignifx/input`), the events before it stay queued and the request answers `internalError`. The host does not depend on `@ignifx/input`: it finds `app.input` by name and calls `simulateEvent` (and `resolveControl`, to check a key) by shape, as it reaches `app.twoD`, so only a game with `app.input` has the method and lists `HostCapability.sendInput` in `ready`; a game without it answers `methodNotFound`.

The play controls also relay the game's reports with the scene view's shapes, as play notifications (`HostCapability.logRelay`): `log` for every record of `app.log`, `hostError` with `AppErrorData` for every `app.onError` report, and `hotReloaded` for every hot reload. What the game reports before the editor's `hello` is kept, the newest 256, and sent right after `ready`; a stack is the page's own (Chromium's `at … (url:line:column)` frames, the URLs the dev server serves), which the editor maps back to project files. Both views clip each string in a report to `HOST_TEXT_MAX_LENGTH` (1 MiB, ending `… [clipped]`) and each list to `HOST_LIST_MAX_LENGTH` (4096), the caps past which the editor drops a report whole.

## 6. The protocol

The host speaks protocol **0.3** of `@ignifx/editor-protocol`, which the editor repository owns on its own version line (ADR-E008) and has not published to npm. Until it is published, `src/protocol/` is a hand-synchronised copy of its modules, one file for each, with identical code; afterwards the host depends on the package. `src/protocol/index.ts` describes how the comments are meant to differ and names the two editor modules a host does not need.

**Additions within 0.3.** `minor` changes when messages or fields are added in a way an older peer can ignore (`src/protocol/version.ts`), but before 1.0 a minor bump makes every 0.3 editor refuse the host. So a new method, an optional field and a new capability are added within 0.3, and the peers find out from each other: a host lists what it has in `ready.capabilities`, a method the host does not have answers `methodNotFound`, an asset kind `renderThumbnail` does not take answers `invalidParams`, and an optional field may be absent.

`test/wire.test.ts` replays the editor's recorded 0.2 host messages (`test/fixtures/host-0.2-wire.json`) at the current protocol line, and `test/wire-0.3.test.ts` replays the 0.3 fixture (`test/fixtures/host-0.3-wire.json`), both copied from the editor repository, through a live host.

1. **Connect.** The editor posts `{ type: "ignifx-editor/connect" }` to the view's window with a `MessagePort` as the one transferred object. The host accepts it only when `event.origin` equals `editorOrigin` (§7). A view reload is a new document that needs a new port, and the editor sends a fresh one on every `load`; the host also accepts a new port at any time, closing the previous one and stopping its heartbeat. Both views listen before their first `await` (the play view through `virtual:ignifx/editor`, §5), so the one message the editor sends on `load` is enough.
2. **Handshake.** The editor sends `hello { editorVersion, protocol }`. A host whose protocol version is compatible answers `ready { engineVersion, protocol, capabilities, hostKind }`; otherwise it answers `incompatibleProtocol` with its own version in `data`. Before 1.0 the minor plays the role of the major, so compatible means the same major and minor (0.3 refuses 0.2); from 1.0 only the majors must match. Malformed parameters get `invalidParams`.
3. **Liveness.** `ping` is answered with `"pong"` at any time, ahead of any request still running. After `ready`, the host sends a `heartbeat` notification every `heartbeatIntervalMs` (default 1000). Chromium reports nothing to the parent when an out-of-process iframe's renderer dies, so a stopped heartbeat is how the editor finds a dead view.
4. **Everything else.** Requests are answered one at a time, in arrival order: an `applyOps` sent right after an `openScene` sees the scene that request opened. `renderThumbnail` (§6.3), `bakeLightProbes` and `cancelBake` (§6.4) are the exceptions: they run beside the queue, as `ping` does (a bake reads the world in a queue slot of its own first). A method the host does not have gets `methodNotFound`; a known method before `hello` gets `notReady`; a message that is not a JSON-RPC envelope gets `invalidRequest` with `id: null`. A failing method gets `internalError`, with the `IgnifxError` code in `data.code` when there is one.

The scene host lists `heartbeat`, plus `gizmos`, `screenshot`, `viewMode2d`, `pick2d`, `pickRect`, `grid`, `gridOverlay`, `tilemapCells` and `editorLines` when it has a canvas, and `spriteAnimation` with or without one; a headless host has none of their methods and `setViewMode` accepts `"3d"` only there. Both list `logRelay`: they relay the app's log lines, `app.onError` reports and hot reloads (below and §5), and `hotReloadDefaults`: after a script's hot reload the scene follows changed defaults itself (§6.1). The play controls list `heartbeat`, `playControls`, `logRelay` and `queryRuntime`, plus `screenshot` when the game has a canvas and `sendInput` when it has `app.input`.

### 6.1 Scene documents (protocol 0.3)

The editor holds each open scene as a document and the scene view mirrors it: the editor opens the scene with the whole file, then sends every command's ops as it applies them to the document. The host reports what the user does in the view as notifications, which the editor turns into commands; it never edits the document. Every uid on the wire is a document uid. The document's entities live in their own scene instance; the editor camera lives in the persistent `editor` instance, which no selection, pick or `readBack` reaches. A member of an instanced prefab resolves to its nearest document ancestor, the instance root. The scene methods answer `notReady` until the app has started; the host's first `schemasChanged`, sent after `ready` once the app has started, is the editor's cue.

What the host does for each method:

- **`openScene`**: Clears the selection, checks the file with `validateSceneFile` (refused: `invalidParams` with `data.issues`, and no scene open), unloads the open document and builds the file object with `world.loadSceneFile`, published at `address` (or `memory:scene/unsaved`) and never fetched. A component that an instance root's record and an `add` override to its one-root prefab's root both carry with one uid, which `readBack` wrote before it wrote each `add` once, is built once, as the list adds it, with one `IGX-0608` warning, so `readBack` reads the same from the first frame; an `add` to any other member that reuses the uid of a root's own component is not that form, so both are built, with an `IGX-0608` warning of its own. Answers `{ entityCount, warnings, viewMode }`, then sends `sceneOpened` with the same `viewMode` (§6.2). A build failure is `internalError` with the code.
- **`closeScene`**: Unloads the open document, if any, and clears the selection.
- **`applyOps`**: Applies the ops in order, never stopping at a failure, and answers `{ applied, failures, warnings }` (codes: editor-core's ten, plus `engineError` with the `IGX-` code; `warnings` as `openScene`'s). See "Ops on the live world" below.
- **`readBack`**: `serializeScene` of the document with `engineVersion` omitted and the host's settings, serialized again on every call, so a change a `"run"` system or a `runInEditMode` script made outside an op shows: the requested records in file order, the uids not found, the settings, and the serializer's issues. An instance root's `overrides` are the list the document holds, in its order and in the file's form (no `op` for a `replace`, no value for a `remove`, transform numbers canonical, as editor-core keeps them), while the serializer still reads the root's members as they were built from that list; once they read differently (something other than an op changed a member), the serializer's own list, a diff in the instanced file's order, is written instead, so the change shows.
- **`select`**: Keeps the document uids, in order, without duplicates; outlines them; attaches the gizmo to the last one. Never sends `selectionChanged`.
- **`setGizmo`**: Mode (`none` hides every gizmo), local or world axes, and snapping (`gizmos`).
- **`frame`**: Fits the entities' world bounds (meshes, or positions where nothing is drawn) in the editor camera's view; `"all"` frames the document's roots. In 2D mode the bounds are sprite quads, tilemap extents and positions (§6.2).
- **`pick`**: Converts the point to backing-store pixels by the canvas's own ratio (CSS pixels × `width / clientWidth`), the one conversion the host makes, picks with `app.renderer.pickAsync` restricted to the document's scene, which resolves a glTF `Model` through its nearest entity node, and resolves the hit to its document entity. Hit or miss, the answer carries the editor camera's `screenToRay` at that backing pixel as `ray: { origin, direction }` (world space, a unit direction) and, when the ray meets `z = 0` at or ahead of its origin, that point as `plane: [x, y, 0]`. In 2D mode it picks sprites first (§6.2). A point outside the canvas, or a headless view, misses with no ray. Changes nothing.
- **`pickRect`**: Box selection (`pickRect`): `{ x0, y0, x1, y1, unit, mode? }`, two opposite corners in either order in `pick`'s unit, clipped to the canvas; `mode` is `"intersect"` (default) or `"contain"`. Each visible mesh of the document's scene (not one marked `EDITOR_ONLY_METADATA_KEY`) counts for the nearest document entity above it, so a prefab member counts for its instance root and a glTF model for its entity; its 8 local bounds corners go through its world matrix and the editor camera's view and projection matrices, cut where an edge crosses the camera plane. In 2D view mode each sprite's quad and each tilemap's extent count too, through the 2D camera, and a `"sprite"` project's meshes do not. An entity's boxes are joined, then matched: any overlap, or (`contain`) wholly inside and wholly in front of the camera. Answers `{ entities, truncated }` in document order, at most 2 000 (`PICK_RECT_MAX_ENTITIES`); an entity that draws nothing is never listed. A headless view, no open scene or a rectangle off the canvas answers none. Changes nothing.
- **`screenshot`**: Checks the 2048-pixel cap, hides the gizmo and the outline, captures the next frame with `app.renderer.captureScreenshot()`, scales it and encodes a PNG or JPEG data URL (`screenshot`).
- **`setViewMode`**: Switches the view between the 3D editor camera and the 2D one (§6.2). `"2d"` needs `viewMode2d`; a headless host refuses it with `invalidParams`.
- **`describeSettings`**: `{ sections, values }`: core's `describeSettings(app)`, each section with its entry of `settingsJsonSchema(app)` as `propsSchema`, and the value the app resolved for each section, in the settings form (`{ x, y, z }`, `{ r, g, b, a }`), copied as plain JSON (a non-finite number is left out). Answered only when asked: no notification announces settings.
- **`setAnimateMaterials`**: Sets `app.renderer.animateMaterialsInEditMode` to `enabled`: the editor's "animate materials" toggle, which runs or holds the shader clock of materials and post effects. The app starts with it on, so an editor sends its own state again after every `ready`.
- **`setGrid`**: Shows or hides the view's grid and sets its spacing (`grid`): `{ visible?, size?, overlay?, height? }`, each call setting the whole grid, a field left out taking its default (`visible: true`, `size: 1` metre, from 0.001 to 1000; with `gridOverlay`, `overlay: false` and `height: 0`, from -100000 to 100000 metres). The host starts with the defaults, so an editor sends its own state again after every `ready`. See "The grid" below.
- **`setTilemapCells`**: Writes a tilemap editor's cells into the open scene's live tilemaps (`tilemapCells`): `{ asset, layer, cells }`, `asset` the tilemap document's address as a `Tilemap`'s `map` names it, `layer` a layer name or index, `cells` flat `[index, tile, …]` pairs in the file's order (row-major, top row first, as the document's `tiles`), at most 2 000 000 numbers (`TILEMAP_CELLS_MAX_NUMBERS`). Every `Tilemap` of the open scene whose loaded `map` is the asset gets one `Tilemap.setCells` (rows flipped to the engine's bottom-up order), so its renderer and collision follow; all are checked before any is written, and an unknown layer or a cell outside it is `invalidParams`. Answers `{ tilemaps, changed }`; a tilemap not loaded yet is skipped. The file on disk is untouched; a reopen or a reload shows the file again, so the editor saves (or sends the cells again).
- **`setEditorLines`**: Draws a set of the editor's world-space line segments over the view (`editorLines`): `{ id, lines, color? }`, six numbers a segment as `getColliderOutlines` answers them (at most 600 000, `EDITOR_LINES_MAX_NUMBERS`), `color` `[r, g, b, a?]` from 0 to 1 (a light green when left out). A set replaces the set of its id; at most 64 ids (`EDITOR_LINES_MAX_SETS`). One Lite line system per set in the render overlay, so it draws over the frame in 3D and 2D view modes, unpickable, marked `EDITOR_ONLY_METADATA_KEY` (never in the game view), never in the play view. Sets outlive `openScene`; a page load starts with none, so an editor sends them again after `ready`. `clearEditorLines { id? }` removes one set, or all.
- **`getColliderOutlines`**: `{ outlines }` for the requested document entities that are open: each enabled collider's world-space line segments, six numbers a segment, from `app.physics.colliderOutlines` and `app.physics2d.colliderOutlines` (read by shape; a 2D outline lies at its entity's world `z`), rounded to 0.01 mm. At most 256 entities (`COLLIDER_OUTLINES_MAX_ENTITIES`) and 600 000 numbers (`COLLIDER_OUTLINES_MAX_NUMBERS`) per answer; whole outlines past a cap are left out and `truncated` is `true`. Empty without a physics extension; `noScene` while nothing is open. The scene view's physics bodies exist without stepping (`09-physics.md` §11), so the outlines follow every move the editor makes.
- **`getSchemas`**: `describeRegisteredSchemas(app.world.registry, describeSchemas())` of the live registry (engine, extensions and the project's scripts, the host's own left out), each with its `toJsonSchema` as `propsSchema`, plus core's file-format entries. Each component's `title` and `description` are its class's own `static title` and `static description`, which every engine package declares on its components, so an extension's curated names arrive without the host importing it. Fields carry their inspector options (`step`, `hidden`, `readonly`, `group`, `assetType`, `componentType`); components carry `allowMultiple` and `package` and, when their class has any, `requires`: the type ids in the class's `static requires`, `null` for a required class without a `typeId`; the editor adds those components itself. Every component also carries `extends`, the type ids of the classes it derives from that are registered under their own `static typeId`, nearest first, empty when none. The engine's `requires` check matches by inheritance (`getComponent`), so an editor counts a required type id as present when a component on the entity has that id or lists it in `extends`. `ignifx/Transform` carries `builtIn: true`.
- **`sampleAnimation`**: `{ posed }` from the engine's `Animator.sample(state, normalizedTime, { parameters })` on the document entity's `Animator` (ADR-0028, amendment of 2026-10-20), found by type id `ignifx/Animator` and called by shape, so the host does not depend on `@ignifx/3d`. An entity the document lacks or one without an `Animator` is `invalidParams`; so is an engine refusal (`IGX-1202`–`IGX-1204`, `IGX-1215`, `IGX-1216`), with its code as `data.code`. `posed` is `false` while the clips load, when the model lacks a clip the state names, and always headless. Names are capped at 256 characters and `parameters` at 64 values (`SAMPLE_ANIMATION_MAX_NAME_LENGTH`, `SAMPLE_ANIMATION_MAX_PARAMETERS`).
- **`sampleSpriteAnimation`**: `{ posed }` from `@ignifx/2d`'s `SpriteAnimator.sample(clip, frame)` or `SpriteAnimator.sampleTime(clip, time)` on the document entity's `SpriteAnimator` (`spriteAnimation`), found by type id `ignifx/SpriteAnimator` and called by shape. Params `{ entity, clip, frame }` or `{ entity, clip, time }`, exactly one of the two (`time` in seconds; a looping clip wraps, a one-shot clip holds its ends). The frame is written onto the entity's `SpriteRenderer` and playback stops there. An entity the document lacks or one without a `SpriteAnimator` is `invalidParams`; so is an unknown clip (`IGX-1108`, as `data.code`). `posed` is `false` while the animation document or the atlas loads.

**Ops on the live world.** `createEntity` and `instantiate` build the records as a subtree with `instantiateScene`, loading their assets first with `loadSceneDependencies`, and pass the rest of the document as its `outsideReferences`, so a reference to a uid outside the subtree resolves as it would in the whole file; a uid already in use is `duplicateUid`, and records `validateSceneFile` refuses (an instance entry with two overrides of one identity among them) are `invalidValue` `IGX-0608`, before anything is built. `destroyEntity` is `destroyImmediate`. `reparent` keeps the local transform (`setParent(parent, { worldPositionStays: false })`) and both it and `reorder` place the entity among its document siblings with `entity.setSiblingIndex`. `setEntityField` writes `name`, `active`, `static`, `layer` (by name) and `tags`; `setTransform` the local position, rotation and scale. `addComponent` is `addComponentFromRecord` (uid, `enabled`, decoded props, index); an unregistered type is `engineError` `IGX-0307`. `setProp` decodes the value with the field's schema, rebuilding the field's JSON for a deeper path, and assigns it the way the inspector writes a field; an absent value restores the default. `setSceneSetting` edits the settings the host keeps, which `readBack` writes; the systems that read scene settings read them when a scene opens. `setOverride` and `removeOverride` edit the instance root's override list (an override is found by its identity: path, `op`, and an added component's uid, so `setOverride` replaces the one the list holds and never adds a second) and rebuild its subtree from the prefab, then re-point references from the rest of the document into it. A rebuild resolves the subtree's references the same way, so one an override holds (an added component's, or a member's overridden field) that names a document entity outside the instance resolves after every rebuild as it does at `openScene`. The re-pointing covers the document's components, the components other instances' `add` overrides give their members, and the members' own fields that other instances' overrides aim into the subtree (a member is not in the document, so the host reads those fields from the live members of the instances whose override lists point into the subtree, before it destroys the subtree), and decodes only the fields that point into the subtree; a member's other references in such a field, to its own instance's members, keep what they held. A reference there that now names nothing (an added component the edit removed) is a warning, as on a reopen; another reference in the same field that resolved nowhere when it was built is not reported again. A component an `add` override gives the root of a one-root prefab is built from the override list only, although the serializer writes it as the root's own component; `readBack` writes it once, in the list. Every subtree an op or a rebuild builds is named by the document's address, and its build problems (an override that names nothing in the prefab, a reference that resolves nowhere in the document, outside the subtree included) are written to `app.log` as warnings, one each, in the form `world.loadSceneFile` writes a scene's (`IGX-0604: scenes/level.scene.json: …`), so they reach the editor as `log` lines that read as a reopen's; the op still applies. Those an `applyOps` request meets, in its ops' builds and in the rebuilds they trigger, are also its answer's `warnings`, in order, in `openScene`'s `{ code, message }` form (the `log` line puts the document's address between the two), and `warnings` is an empty list when there were none. Both are sent: the answer's list is the authoritative record of a command's problems, the one an MCP tool or the undo stack ties to the command, and the `log` lines are the Console's copy. An asset reload or new defaults has no answer, so a rebuild there reports through `log` alone. After any failure the editor resends `openScene`, so the host does not roll back.

**Notifications.** `sceneOpened` after each `openScene` answer. `schemasChanged` after `ready` once the app has started, and after every `app.hotReload.onApplied`, which covers a script that changes its fields and one registered for the first time. `hotReloaded` on `app.hotReload.onApplied`, each error as `{ message, code, stack }`. `selectionChanged` when a click in the view changes the selection (a plain click replaces it, Shift, Ctrl or Cmd toggles, a click on nothing clears it). `transformDragging` at pointer-down with the transform at drag start, then at most every 50 ms, and `transformDragged` at pointer-up with `before` read at drag start, both rounded with `canonicalizeNumber`; every drag gets both, even one that ends where it started, so the editor can hold its undo until the drag ends. `hostError` on `app.onError`: the thrown error's `code` and `message`, and `AppErrorData` as `data` (`source`, `phase` and `phaseName`, `entity` and `entityName`, `component` as its `typeId`, `stack`). `log` for every record of `app.log`, without `data` but for the first `Error` in it as `error: { message, code, stack }`; the app's default `onError` handler logs one such line per report, just before the `hostError`. `assetReloaded` after an asset reload in place (below).

**Asset reload in place.** The page's module hands every `ignifx:asset-changed` event of the Vite plugin to `EditorHost.assetChanged(change)`. An asset the app has not loaded, a removed file, the open document's own file, and any type outside `scene`, `model`, `mesh`, `material`, `spriteatlas` and `shader` are left alone. Otherwise the host calls `app.assets.reload(address)` and waits for the handle's `onReplaced` (an asset error on `app.onError` meanwhile ends the wait; the assets service reports a failed reload only there, without the address). The renderers read a model, mesh, material and sprite atlas from their handle every frame, and a shader's materials rebuild on its `onReplaced`; a texture is left out because the materials and atlases built from it keep the texture they were given, which the default reload unloads. For a scene or prefab the host then rebuilds each document instance root that instances it, directly or through the scenes it instances (an instance inside another rebuilt one is rebuilt with it), the way `setOverride` does: the root's record, transform, overrides and document children are kept, the members are built from the new file (without the recorded hash, so the rebuild reports no `IGX-0604` mismatch; a stale override is still a `log` warning), and references from the rest of the document into the subtree are resolved again. `readBack` then writes the new file's hash. The rebuild runs in the same queue as the requests, so no request sees half of it; a root that fails to rebuild is a `hostError`. Last the host sends `assetReloaded { address, type, entities }`, `entities` being the rebuilt roots in document order, so the editor compares its document with the view instead of reloading it.

**Hot-reloaded defaults.** A script's hot reload keeps every live field value (`15-devtools-and-diagnostics.md` §5), so a field the document leaves out would keep the default from before the edit. The host therefore keeps, for each document component, which fields its record sets (from `openScene`, `createEntity`, `addComponent` and `setProp`, where a value sets the field and an absent one leaves it out), and for each instance root its override list (from `openScene`, `createEntity`, `instantiate` and the override ops). It reads every registered type's file-form defaults once the app has started and again for the types each `app.hotReload.onApplied` report names. When a field's default changed, or a field is new, the host, in the same queue as the requests: gives that field `createDefault()` on each document component of the type whose record leaves it out, and keeps it where the record sets it, even to the old default; then rebuilds each outermost instance root whose members (not the document's own components) hold a component of the type, the way an asset reload does. A component an `add` override gives the root of a one-root prefab counts as a member, though the serializer writes it as the root's own. Every rebuild (`setOverride`, `removeOverride`, an asset reload, new defaults) starts from the override lists the document holds and records the edited list, never one the serializer recomputes by diffing the live members with their scene: that diff writes an added component as its whole record, leaves out an override equal to the scene's value, and would read every stale member as an override. Members take the prefab's values with the new defaults and the instance's overrides on top; instance roots under a rebuilt one are rebuilt with it, with their own lists. A root that fails to rebuild is a `hostError`. No notification follows: `hotReloaded` and `schemasChanged` go out as for any hot reload, and a request sent after them sees the defaults applied. A component whose type the host did not know when the scene opened has no instance, which this does not repair. The host lists `hotReloadDefaults` in `ready`, and an editor that sees it does not reopen the scene for changed defaults.

**The view.** The gizmos are Lite's position, rotation and scale gizmos in core's render overlay, attached to the primary selection's `transform.lite`; Lite writes the entity's own transform, so drag end needs no write-back. A detached Lite gizmo keeps drawing, so a hidden one is collapsed to zero scale. Snapping is a post-correction in the host's drag listener, which keeps the unsnapped value apart. The outline is a line box over each selected entity's mesh bounds, because Lite's bounding-box gizmo drags whatever is pressed inside it. The editor camera is a `runInEditMode` script beside a `Camera` of priority 1 000 000: left drag orbits (yielding to the gizmo by the three rules Lite documents for its own controls; `src/scene/editor-camera.ts` states them), middle drag pans, right drag with W, A, S, D, Q and E flies, the wheel dollies, and a left click picks.

**The grid.** A `Scene Grid` entity in the persistent `editor` instance carries the host's `EditorGrid` script, which places the grid after every frame's cameras have moved; the document, `readBack`, picks and the play view never see it. In 3D view mode it is a square at `y = 0` in the render scene, drawn with Lite's `createGridMaterial` (object-space lines, so the square is scaled to its extent and the material's ratio and offset keep the lines on world multiples of the spacing): centred under the eye, reaching 40 eye heights (at least 100 lines, inside the far plane), faded out radially by an opacity texture before its edge, with the spacing ten times coarser for each tenfold of eye height above 25 lines. It is depth-tested against the document's meshes, alpha-blended without depth writes, unpickable and casts no shadow. With the `gridOverlay` capability, `setGrid`'s `height` moves the square to that `y` (the spacing then follows the eye's height above it), and `overlay: true` draws it in the render overlay instead, fainter, so a floor mesh at the grid's height does not hide it; within the overlay it still depth-tests against the gizmos. In 2D view mode it is a square at `z = 0` in the render overlay, over the sprites (a `"sprite"` project's sprite pass clears the render scene): lines `size` apart, ten times coarser while closer than 8 screen pixels, and from zoom 8 one line per layer pixel with a major line every `size`. Every tenth line is a major line otherwise. `screenshot` captures the grid while it is visible. The grid's Lite module is loaded with `import()` once the view has a canvas.

### 6.2 The 2D view

The host does not depend on `@ignifx/2d`. It reaches the project's copy by data: `app.twoD` when the project registers the extension, and the 2D component classes by type id from the registry (`ignifx/Camera2D`, `ignifx/SpriteRenderer`, `ignifx/Tilemap`), as `@ignifx/physics-2d` finds a `Tilemap` (`11-2d-toolkit.md` §2.5).

- **The view mode a scene is made for.** After `openScene` builds the file, the host reports `viewMode: "2d"` when the project draws sprites only (`twoD.mode: "sprite"`, read after the file's own `settings.twoD`), or when the scene has a `Camera2D` and no 3D `Camera`; otherwise, and always without `@ignifx/2d`, `"3d"`. It does not switch by itself; the editor sends `setViewMode`.
- **The 2D editor camera**. With `@ignifx/2d` the editor camera's entity also carries a `Camera2D` of priority 1 000 000, disabled in 3D mode, and the `EditorCamera2D` script. In 2D mode the `Camera2D` is enabled, so the sprites draw through it and the level's own `Camera2D` keeps exactly what the file says, and the 3D `Camera` turns orthographic, 500 m in front of the plane looking along +Z with the same half-height, so the gizmo overlay and the 3D picker see the same rectangle. The zoom is `Camera2D`'s (screen pixels per layer pixel). Middle drag, right drag and Space with left drag pan; the wheel zooms about the cursor through 0.125, 0.25, 0.5, 1, 2, 3, 4, 6, 8, 12, 16, 24 and 32; a left click picks. The first switch to 2D on a document starts where the level's highest-priority `Camera2D` looks, at its `orthographicSize`, or frames the document when it has none; reopening the same address keeps the view. Back in 3D, the 3D camera takes up where it was.
- **Frame.** `frame` in 2D mode fits the union of the entities' positions, every `SpriteRenderer` quad under them (`SpriteRenderer.bounds`, as the last frame synced it) and every loaded `Tilemap`'s extent, with a 20 % margin.
- **Pick** (`pick2d`). In 2D mode `pick` and view clicks call `app.twoD.pickAt` at the backing pixel with `includeUnpickable: true` and a filter to the document's scene, so the editor selects what the game marks unpickable. A hit answers `point: [x, y, 0]`, the world point under the cursor, and `distance: null`. Hit or miss, `ray` is the orthographic eye's (straight down +Z, built from the 2D camera's own arithmetic, so it never lags a pan by a frame) and `plane` is the same world point. Without a sprite hit, a `"mixed"` project, or one without `@ignifx/2d`, goes on to `pickAsync` through the orthographic eye; a `"sprite"` project misses.

### 6.3 The game view and thumbnails

Defined in `src/protocol/render-views.ts` (`RenderViewMethod`). A host with a canvas lists `gameView`, and `thumbnails`, `thumbnailMaterials`, `thumbnailAtlases` and `thumbnailTextures` where `OffscreenCanvas` exists and the host can build the stage's extensions (a `createExtensions` option, or no extensions at all); a headless host lists neither and answers their methods with `methodNotFound`. Both answer images as `screenshot` does: a PNG or JPEG data URL, scaled and encoded in the page.

- **Game view.** `setGameView { enabled, width?, height? }` (sides 1 to 2048, 640 by 360 until given) allocates or frees a render texture (`07-rendering.md` §2.11) and answers `{ enabled, width, height }`. `gameViewFrame { format, quality? }` renders the open document's own main camera into it on the next frame, beside the editor camera's view, and answers `{ dataUrl, width, height, camera }` with the camera entity's document uid. The camera is the one the game would use: the enabled `Camera` in the document with the highest `priority`, the first on a tie. A document with none answers `dataUrl: null, camera: null`. It fails with `noScene` while no scene is open and `invalidRequest` while the view is off. The editor polls it; nothing is rendered between requests. It draws the render scene only. Three capabilities extend it: with `gameViewOnDemand` the request does not wait on the animation-frame loop, which a `visibility: hidden` iframe never runs, so `renderToTexture` gets `maxWaitMs` (20 ms) and the renderer draws the frame itself when none comes (`07-rendering.md` §2.11); with `gameViewSize` the request may carry `width` and `height`, and the view resizes to them first, so the frame has the Game panel's aspect; with `gameView2d` a document whose only main camera is a `Camera2D` renders too: after one frame (`app.renderer.nextFrame`, same wait) a second Lite sprite renderer on an `OffscreenCanvas` surface of the view's size draws `app.twoD.layers`, the world layers through the level camera's own `resolve` at that size, cleared to `rendering.clearColor` as it reads at that moment, and `convertToBlob` reads it back (`src/lite/sprite-game-view.ts`). The surface and renderer exist only for the request, so no main frame acquires the surface's texture and no closed scene's layers are held; Lite's shared sprite pipeline cache keeps that cheap. A document with a `Camera` uses it. Not drawn: a `PostProcessStack` on the document camera (a render texture gets the raw scene colour: the stack's chain lands on the swapchain, its targets are sized to the surface, and Lite's image-processing task writes `engine.scRT` only, with no target, so a per-texture chain needs that task to take a target or a custom-effect replacement for it), parallax layers' offsets, tilemap chunks outside the editor camera's view, and the 3D scene under a `"mixed"`-mode 2D view.
- **Thumbnails.** `renderThumbnail { asset, size?, format, quality? }` renders a model (`.glb`, `.gltf`, or `type: "model"`), a prefab (`.prefab.json`, `.scene.json`, or `type: "scene"`), a material (`.material.json` or `type: "material"`, `thumbnailMaterials`), a sprite atlas (`.atlas.json` or `type: "spriteatlas"`, `thumbnailAtlases`) or an image (`.png`, `.jpg`, `.jpeg`, `.webp`, or `type: "texture"` with one of those extensions, `thumbnailTextures`) on its own and answers a square image of `size` (1 to 1024, default 128). Anything else, a GPU-compressed texture included, is `invalidParams`. A material is shown on a sphere (a `MeshAsset.sphere` the stage keeps) in a scene of its own on the stage, lit and framed as a model, once its loads are done. An atlas or an image never reaches the stage: the host fetches it through the project's asset `fetch` and `app.assets.resolveUrl` (an atlas's `image` resolved against the atlas's address as `@ignifx/2d` does), decodes it with `createImageBitmap` and draws it fitted and centred in the square on a transparent background (black in a JPEG), without smoothing when enlarged, so pixel art stays sharp. The host renders it in a second app of its own, created on the first request from fresh instances of the project's extensions (`createExtensions`, which the generated scene view sets to the project's `extensions` function; an extension object belongs to one app, `IGX-0411`), its settings, assets and scripts on a 1x1 `OffscreenCanvas`, so a thumbnail never shows or lights the open document: a persistent stage scene holds a camera, a hemispheric and a directional light; the asset is loaded alone (`loadSceneFile` in `"single"` mode), the camera frames its mesh bounds once they hold still (or after four frames with nothing drawn and no asset loading, rather than waiting the full 120), `renderToTexture` renders it at twice the size and the encoder scales it down. The stage app is disposed with the host. The channel runs `renderThumbnail` beside its one-at-a-time queue, since it never reads the document: the frames it waits for hold up no other request, and thumbnails queue among themselves, one subject on the stage at a time.

### 6.4 Light-probe bakes (`bakeLightProbes`)

Defined in `src/protocol/light-probe-bake.ts` (`LightProbeBakeMethod`, `LightProbeBakeNotification`); fixture `test/fixtures/host-0.3-bake-wire.json`. Every scene host lists `bakeLightProbes`. The host bakes with core's `bakeLightProbes` over its own edit-mode world, so the bake traces what the view shows — prefab instance members, `Model`s (under a GPU read from their drawn meshes through Lite's `getMeshTriangles`, headless from the file), primitives and data meshes, every transform with its rotation, lights with their `bakeMode` — instead of a trimmed copy of the scene file. The host writes no file.

- **Request.** `bakeLightProbes { volume, counts? | spacing?, directLight?, sky?, rays?, maxDistance? }`. `volume` is the uid of an entity of the open document with a `LightProbeVolume`; its world position is the box's centre and its world scale the box's size (axis-aligned, a rotation ignored). `counts: [x, y, z]` spreads that many probes face to face (one probe on an axis sits at the centre); `spacing` (0.05–1000 m, default 2) puts probes at most that far apart, at least two on each axis of non-zero size. The grid must fit a `.probes.json` (X ≤ 1024, Y × Z ≤ 4096) and 16 384 probes (`BAKE_MAX_PROBES`), checked by the host as `invalidGrid` whether it comes from `counts` or `spacing`; `volume` is at most 128 characters, and every sky channel or harmonic at most 1e6 in magnitude. `sky` is core's `LightProbeBakeSky` (a colour, a gradient, or 27 harmonics); absent, it is the open document's `Environment`'s diffuse harmonics when a GPU host has them installed — Lite's pre-scaled irradiance polynomial (`EnvironmentTextures.sphericalHarmonics`) turned back into radiance and rotated by `Environment.rotation`, so a probe in the open shows what the environment lights a surface with — and black otherwise; `null` is black.
- **Answer.** `{ probes, stats: { probes, triangles, skipped, ms }, skips, sky }`: `probes` the `.probes.json` document (`writeLightProbeFile`), its coefficients rounded to six significant digits and those below 1e-6 answered as 0, so the largest document stays under 3 MiB of JSON, inside the editor's 4 MiB message limits; `skips` core's `LightProbeBakeSkip`s (at most 256), `sky` `"request"`, `"environment"` or `"none"`.
- **Progress and cancel.** `bakeProgress { volume, done, total }` at most every 100 ms, the first after the first probe. `cancelBake` (`{}` or no parameters) answers `{ cancelled }` and cancels the running bake or one still waiting for its queue slot, which then fails without running; the bake fails with `invalidRequest` and `data: { reason: "cancelled", cause: "cancelBake" }`. Any change to the document (`openScene`, `closeScene`, `applyOps`, `setTilemapCells`, an asset reload that rebuilds instances, a hot reload's new defaults) cancels it the same way with `cause: "sceneChanged"`, so a bake never mixes the old world with the new.
- **Failures.** `noScene`; `unknownEntity` (`data.reason: "unknownEntity"`); `invalidParams` with `notAVolume` or `invalidGrid`; `invalidRequest` with `busy` while a bake is pending or runs; `invalidRequest` with `outOfRange` when a baked coefficient is not finite or above 1e12 (a light of absurd intensity), so no `.probes.json` ever holds `null`. Error codes stay the existing ones so an editor's `isRpcMessage` keeps accepting them; `data.reason` (`isBakeFailureData`) tells them apart.
- **Scheduling.** Core reads the world once, synchronously, before its first yield, so the host reads the world in a slot of its request queue and then traces beside the queue in slices of about 8 ms, like `renderThumbnail`: `applyOps`, `pick` and the rest keep answering, and the view keeps drawing. The bake request itself arrives beside the channel's queue, so its slot can come before a change sent just ahead of it that the channel has not handed on yet; that change then cancels the bake as `sceneChanged` rather than leaving it with the old world.

## 7. Security

The host page drives a live engine, so two independent checks keep other pages away from it:

- **`frame-ancestors`.** Under `vite dev` both views are served with `Content-Security-Policy: frame-ancestors <editorOrigin>`. A website the developer has open cannot frame `127.0.0.1:<port>/__ignifx_editor__/` or the game's `index.html`. The scene view's page sets the header itself; for the play view the plugin adds it to every request a browser makes for a page (a `GET` or `HEAD` whose `Accept` names `text/html`), leaving the page's content unchanged. A tab opened on the dev server is not a frame, so the game still runs standalone. A `Content-Security-Policy` the project sets in `server.headers` replaces the plugin's on the play view.
- **The origin check.** Both hosts ignore a connect message whose `event.origin` is not exactly `editorOrigin`, so only the editor can hand either view a port, framed or not.

`editorOrigin` must be `scheme://host[:port]` with no path, wildcard, quote, comma or semicolon (`IGX-1801`), which also keeps it from ending the CSP directive early. The editor passes it when it spawns the dev server; it differs between the packaged editor (`ignifx-editor://app`) and the editor's own development server, so it is never hard-coded. Keep the dev server on loopback. Production builds contain no host code at all.

## 8. Errors

The package owns `IGX-1800`–`IGX-1899`. `IGX-1801`: `editorOrigin` is not an origin. `IGX-1802`: no `window` and no `messageTarget` (Node). `IGX-1803`: an option outside its domain. The page half throws `IgnifxError`; the Vite plugin throws `EditorHostPluginError` with the same codes, because it runs without `@ignifx/core`, as `@ignifx/vite-plugin` does.

## 9. Not in this release

- **The rest of the 2D view**: planar gizmos (Lite's 3D gizmos draw through the orthographic eye), a sprite selection outline (the outline boxes meshes only), the pixel-perfect toggle and collider handles of the host's own (the editor draws its handles through `setEditorLines`).
- **The light and camera gizmos** are not drawn.
- **Thumbnails of other assets** (`renderThumbnail` renders models, prefabs, materials, sprite atlases and browser-decoded images; not GPU-compressed textures, sprite animations or tilemaps), and UI text in the game view (it draws the render scene, and a `Camera2D` document's sprite layers with `gameView2d`; §6.3).
- **Box selection of what draws nothing** (`pickRect` lists entities by their drawn bounds: lights, cameras and empty entities are never listed), and a thin-instanced mesh counts by one instance's bounds.
- **Gizmo handles of the host's own**: snapping post-corrects Lite's stock gizmos, and multi-selection pivots are not in protocol 0.3.
- **Live scene settings**: `setSceneSetting` changes what `readBack` writes; systems that read settings (the 2D toolkit's block) see the change at the next `openScene`.
