# 13 · UI

**Status:** Implemented in Phase 8 (2026-09-06) · **Package:** `@ignifx/ui` · **Related:** `08-input.md` §5, `07-rendering.md` §1 and §6, `11-2d-toolkit.md` §2.7

Babylon Lite has no GUI system. ignifx's answer is deliberate: **game UI is HTML** layered over the canvas, and **in-world or pixel-HUD text** uses Lite's text renderer. HTML gives every game accessibility, fonts, layout, localization, and any framework the team already knows, in browsers and Electron alike.

`@ignifx/input` is an **optional** peer: the overlay, the text components and the localization service work without it, and only the two touch widgets need it.

---

## 1. Overlay host (`app.ui`)

- `app.ui.root`: an absolutely positioned `<div>` covering the canvas, `pointer-events: none` by default; children opt in with `pointer-events: auto` (or the `ignifx-ui-interactive` class). Games mount React/Preact/Svelte/Vue/vanilla trees into it, or into named layers (`app.ui.layer("hud")`, `app.ui.layer("menu", { zIndex })`).
- **When it is built.** Not while the extension registers: `AppImpl.initialize` registers every extension _before_ it creates the Lite engine, so `app.renderer.surface` throws `IGX-0107` there. The host is constructed inert and mounted from `UiSystem.onWorldCreated`, which fires later inside the same `createApp` call — the hook `@ignifx/2d` uses for the same reason. By the time `await createApp(...)` resolves, `app.ui.root` is an element.
- **Where it is attached.** As the canvas's next sibling, inside the canvas's own parent, so an overlay moves with a canvas in a positioned wrapper and two apps in one document get one overlay each (`CONSTITUTION.md` §3.6). A canvas with no parent falls back to `document.body`.
- **Layers.** The `ui.layers` settings section declares the layers created up front, back to front, at z-index `10`, `20`, `30`… (`UI_LAYER_Z_STEP`). Declaring them there is what makes their stacking order independent of the order the game happens to call `layer()` in; an undeclared name is created on first use.
- **Scaling modes.** A canvas has two sizes — its CSS size, and its backing store (`canvas.width`/`.height`). `Camera.worldToScreen`, Lite's text renderer, and `app.renderer.captureScreenshot()` all answer in **backing-store** pixels; a DOM element is placed in CSS pixels. The mode decides what one "UI unit" is:

  | Mode    | One UI unit is      | Root size               | Scale                       |
  | ------- | ------------------- | ----------------------- | --------------------------- |
  | `"css"` | one CSS pixel       | the canvas's CSS size   | `1`                         |
  | `"fit"` | one reference pixel | `referenceResolution`   | `min(cssW/refW, cssH/refH)` |
  | `"dpi"` | one backing pixel   | the canvas's pixel size | `cssW / backingW`           |

  `"fit"` keeps aspect and centres the letterbox, for pixel-art HUDs authored once. `"dpi"` is the mode §1 previously called "constant physical size": the concrete meaning is that the overlay's coordinate system _is_ the render target's pixel grid, so an element at `left: 100px` lands on render-target column 100 — which is what a capture-perfect HUD needs, and what makes a UI unit a fixed physical size for a given panel. `app.ui.pixelMapping` is the conversion, and `WorldAnchor` applies it for you.

- **Safe areas.** The root carries `--ignifx-safe-top`, `--ignifx-safe-right`, `--ignifx-safe-bottom` and `--ignifx-safe-left`, each set to `env(safe-area-inset-*, 0px)`, plus `--ignifx-ui-scale`.
- **Focus routing.** `InputService.uiHasFocus` is a plain settable property — its own documentation says _"`@ignifx/ui` assigns it"_ — and nothing in `@ignifx/input` watches the DOM for it. `@ignifx/ui` therefore owns the policy, and defines it as **text entry**, matching `08-input.md` §5's "while a DOM text field has focus": `<textarea>`, `<select>`, a `contenteditable` element, or an `<input>` whose type is not one of the button-like or slider-like types. A focused `<button>` deliberately does _not_ stop gameplay. `data-ignifx-focus="capture"` / `"ignore"` overrides the guess. The watcher is scoped to the whole document, not to the root, because a framework may portal a menu anywhere.
- **Pointer routing.** §1 previously said pointer events reaching a `pointer-events: auto` element are "marked handled". There is no such mechanism, and none is needed for the common case: `@ignifx/input` reads `pointerdown`, `wheel` and `contextmenu` from the **canvas**, and the overlay root is the canvas's _sibling_, so a press that lands on an interactive UI element is never queued at all. What is not covered is the drag: `pointermove`, `pointerup` and `pointercancel` are read from the **window**, so a drag that started on a slider still moves `<Pointer>/delta`. `app.ui.pointerOverUi` is `true` while a pointer is down on the overlay, and the host writes the same value into `app.input.uiHasPointer` (added to `@ignifx/input` on 2026-09-06), which masks pointing-device actions the way `uiHasFocus` masks the keyboard — so a drag that began on a slider no longer turns the camera, without any script checking a flag.
- **Visibility** follows `app.ui.visible` and per-layer `visible`.

## 2. Components bridging world and DOM

All four are driven by one system in `PreRender` at order **1100** — after `@ignifx/core`'s `RENDER_SYNC_ORDER` (900), which is what refreshes each camera's render-target size, and inside the `[1001, 9999]` band reserved for extensions.

- `WorldAnchor`: keeps a DOM element positioned at the entity's screen position (name tags, health bars, markers), with `offset`, `hideWhenBehindCamera`, `clampToScreen`, and `scaleWithDistance` (plus `referenceDistance`, `minScale`, `maxScale`). Updated in batch, using `Camera.worldToScreen` — whose output is in backing-store pixels, converted to UI units by the host's `pixelMapping`. The element is the game's: it is assigned in code, is never serialised, and the component writes only `position`, `left`, `top`, `transform` and `display` on it. A point behind the camera is hidden, or — with `clampToScreen` — reflected about the viewport centre before clamping, so an off-screen marker goes to the correct edge.
- `WorldText` (3D): a Lite `createTextRenderable` inside the render scene, for signs and banners; `billboard`, `alwaysOnTop`, and `pixelsPerUnit` (default 100), because Lite lays text out in pixels. **It has to exist before `app.start()`.** `addTextRenderable` pushes a _deferred_ scene builder, `buildScene` drains those exactly once when `registerScene` runs, and `rebuildSceneRenderables` — the only public rebuild — does not drain them. A sign that first gets its text mid-game logs `IGX-1308` and does not draw. Lite also has no `removeTextRenderable`, so a destroyed `WorldText` empties its block and zeroes its opacity (it draws nothing and holds no GPU buffers) while the record itself stays in the scene's renderable list. Both are recorded as Babylon Lite gaps.
- `WorldText2D`: the same shaped block drawn as a pixel-space Lite **text layer**, positioned at the entity's projected position with `offset`, `screenOffset`, `pivot` and `hideWhenBehindCamera`. It can be created at any time, which makes it the right choice for damage numbers and for anything spawned mid-game.
- `HudText`: pixel-space text through a Lite `TextRenderer` when DOM text is not desirable (capture-perfect pixel HUDs, screenshots via `captureScreenshot`), anchored to one of nine points of the render target. The renderer is a second rendering context on the app's surface, created lazily on the first `PreRender` tick and registered _after_ the render scene with `clear: false`, exactly as `@ignifx/2d`'s sprite renderer is.
- Shared fields: `font` (a core `FontAsset`), `text`, `i18nKey`, `fontSize`, `color`, `align`, `maxWidth`, `lineHeight`, `opacity`. Changing `text` or `color` re-shapes in place; changing `font`, `fontSize`, `maxWidth`, `align` or `lineHeight` rebuilds the block, because Lite's `updateDefaultTextData` reuses the size and layout options the block was created with. `align` aligns a block's lines against **each other**, not against `maxWidth`, so centring a block on screen is `anchor`/`pivot` or arithmetic against `metrics`.

## 3. Helpers

- `VirtualJoystick`, `VirtualButton`: touch controls feeding `@ignifx/input`'s virtual device. They reach it structurally rather than by importing `@ignifx/input`, so the peer stays genuinely optional; without it they throw `IGX-1305`. They replace the in-template widget the 2D templates shipped in Phase 6, writing the same `<Virtual>/joystick` and `<Virtual>/…` controls with the same axis convention.
- `Dialog`, `Toast` and `LoadingScreen` are plain DOM helper classes with no styling opinions beyond a minimal stylesheet injected once per document; templates ship their own CSS and target the `ignifx-ui-*` class names. A pause menu is `new Dialog(app.ui, { title, buttons })` plus `app.pause()`. `LoadingScreen.bindTo(app.assets)` follows `app.assets.onProgress`, bytes-weighted where the build recorded sizes. A `Toast` runs on the **game** clock (`toast.advance(dt)`), so it pauses with the game and is deterministic in a headless test.
- `Localization` (`app.i18n`) is a tiny key/value service with ICU-style plurals, loaded from `.i18n.json` assets in the `ignifx.i18n` format (`06-serialization-and-scene-format.md` §6): one document carries every locale. `{name}` interpolation, `{n, plural, …}` with `=0`-style exact matches and the active locale's CLDR categories, and `#` for the number. `select`, number and date skeletons, and ICU's apostrophe quoting are out of scope. A missing key renders as the key itself and logs once; a message that cannot be parsed reports `IGX-1304`. UI helpers and all three text components accept keys through `i18nKey`.

## 4. Non-goals

A retained-mode canvas GUI, data binding, or a UI editor. Teams that need canvas-drawn UI (e.g. inside a render texture) can use sprite layers and text layers directly.

## 5. Diagnostics

`@ignifx/ui` owns the whole `13xx` range (`15-devtools-and-diagnostics.md` §1).

| Code       | Meaning                                                                      |
| ---------- | ---------------------------------------------------------------------------- |
| `IGX-1301` | A second `ui()` extension was registered on one app.                         |
| `IGX-1302` | A `.i18n.json` file is not an `ignifx.i18n` document this build can read.    |
| `IGX-1303` | `app.i18n.locale` was set to a locale no loaded document declares.           |
| `IGX-1304` | A message pattern could not be parsed.                                       |
| `IGX-1305` | `VirtualJoystick`/`VirtualButton` was built without `@ignifx/input`.         |
| `IGX-1306` | A text component has no `font` assigned, so it has nothing to draw.          |
| `IGX-1307` | A DOM-only member was reached on a host with no document, and did nothing.   |
| `IGX-1308` | A `WorldText` was given its text after `app.start()`; Lite will not draw it. |

## 6. Headless

`07-rendering.md` §6's rule applies: a headless member is a documented no-op, not a throw. §1 previously said "the host hides itself in headless mode" — it is _absent_ rather than hidden. With no DOM canvas (a headless app, an `OffscreenCanvas`, a canvas outside a document) `app.ui.root` is `null`, `app.ui.isActive` is `false`, every layer's `element` is `null`, every mutation does nothing, one debug line is logged, and no text renderer is created. The text components still shape and measure text, because Lite's `createFontFromBuffer` and `createDefaultTextData` touch no device — which is what makes layout, localization and the anchor arithmetic testable under Node.
