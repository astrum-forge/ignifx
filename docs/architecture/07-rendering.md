# 07 · Rendering (the Babylon Lite adapter)

**Status:** Design standard; describes the engine as built (pre-1.0) · **Package:** `@ignifx/core` (`src/lite/**`) · **Related:** `00-overview.md` §3, `02-scene-graph.md`, `11-2d-toolkit.md`

ignifx does not render; Babylon Lite does. This document defines the components that expose Lite's renderer to entities, and the rules the adapter follows. Lite names and behaviour are those of the pinned Babylon Lite version (`pnpm-workspace.yaml` catalog); `src/` paths are under `packages/core/`.

Invariants:

- Feature opt-ins are applied before `registerScene`; a late toggle is `IGX-0704` (§1.1).
- A mesh is hidden with visibility, never removed from the scene: Lite disposes a mesh that leaves its last scene (§2.3).
- A light is never parented in Lite; the adapter writes its world pose each frame it moves (§2.2).
- Topology changes coalesce into one `rebuildSceneRenderables` per frame, and shadow caster lists are rebuilt only in a frame that owes none (§2.2, §2.3).
- A post-process chain never samples the swapchain, and `imageProcessing` is always last (§2.7).
- Every optional GPU path is a chunk loaded on first use; a game that never asks for it ships and runs none of it (`CONSTITUTION.md` §2.5).
- Public coordinates are backing-store pixels; only the picker adapter converts to CSS pixels (§2.1, §3).
- A clear colour presents as a fully fogged fragment of that colour would (§2.1).
- Each Lite private field the adapter touches (`scene._envTextures`, the frame graph's `_tasks`, `scene._disposables`, a task's `_sceneUBO`) is named in its section; re-check them at every Lite bump.
- `app.dispose()` follows §7: physics before scenes, scenes before the engine.

## 1. Engine and surface

- `createApp({ canvas })` first checks that `navigator.gpu` exists (`isWebGpuAvailable`; `assertWebGpuAvailable` in `src/lite/engine.ts`) and rejects with `IgnifxError` code `IGX-0701` when it does not, then calls `createEngine(canvas, options)`. The check does not request an adapter. Templates catch it and show a static "WebGPU required" page.
- Engine options exposed by `createApp`: `msaaSamples` (1 or 4, default 4), `alphaMode`, `srgb`, `format`, `maxDevicePixelRatio` (default `0`, which means "do not clamp": native DPR), `useHighPrecisionMatrix`/`useFloatingOrigin` (large worlds; off by default), `requiredLimits`.
- Sizing: Lite re-reads `clientWidth × clientHeight × devicePixelRatio` at the start of every frame (`resizeEngine`). ignifx exposes `app.renderer.pixelRatio` (maps to `maxDevicePixelRatio`) and `app.renderer.resolutionScale` (0.25–1, implemented by lowering `maxDevicePixelRatio`); for `OffscreenCanvas` it exposes `app.renderer.setSize(w, h)` (`setSurfaceSize`; on a laid-out DOM canvas Lite re-reads the layout size next frame, so `setSize` is an `OffscreenCanvas`-only API). Lite always requests a `high-performance` adapter; there is no `powerPreference` option.
- One render scene per world (`createSceneContext(engine)`), registered in `app.start()` via `registerScene`, or `registerSceneWithShadowSupport` when `rendering.features.shadows` is on (§1.1).
- One surface, on the main thread: multiple surfaces (`createSurface`) and worker rendering are not supported.

### 1.1 Feature opt-ins are declared up front

Lite enables many features only through explicit calls that must happen **before `registerScene`** (its deferred-builder drain). Process- or scene-global opt-ins: `enableStandardSkeleton()`, `enableMaterialStencil()`, `enablePbrLightmap()` (async), `enableMaterialPlugins(scene)`, `enableAsyncShaderPipelineCompilation`, `enableBoneControl()` (before loading skinned assets), `enableGltfCameras()`, and the `enableDeviceLost*Recovery` family (before creating resources). ignifx therefore takes a `rendering.features` block in `ignifx.config.ts`/`createApp` (`{ shadows, postProcessing, skeletons, boneControl, stencil, lightmaps, materialPlugins, asyncPipelines, deviceLostRecovery }`), applies the corresponding calls during `app.start()` before `registerScene`, and rejects late toggles with `IGX-0704`. Two of those names are not `enable*` calls at all: `shadows` picks `registerSceneWithShadowSupport` over `registerScene`, and `postProcessing` picks the scene's whole render path at `createSceneContext` (§2.7) — earlier than the rest, because a frame graph is built there and Lite exposes no way to retarget its render task afterwards. Extensions declare the features they need through `ctx.requireRenderingFeature(name)` at registration. Per-object opt-ins (`enableThinInstanceGpuCulling(mesh, enabled)`, `setAlphaToCoverage(target, enabled)`) are `MeshRenderer`/material fields that the adapter applies when it creates the Lite object, before that object is registered.

Entities added after `registerScene` go through Lite's runtime material-swap path, which compiles new material families asynchronously (a mesh may appear a few frames after `addToScene`). The adapter therefore warms material families at `app.start()`, before `registerScene`: the default PBR material, a Standard probe, and every material asset already loaded (ADR-0014). The warm-up is skipped when the scene has no light at start, because a probe registered into a lightless scene leaves later meshes of that family undrawn. `app.renderer.warmUp(materials)` exists for spawn-heavy games.

## 2. Components

### 2.1 `Camera`

| Field              | Type / default                                           | Lite mapping                                                                                      |
| ------------------ | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `projection`       | `"perspective"` \| `"orthographic"`; default perspective | `enableOrthographicCamera` / `disableOrthographicCamera`                                          |
| `fov`              | vertical degrees, default 60                             | `camera.fov` (radians)                                                                            |
| `orthographicSize` | half-height in world units, default 5                    | `camera.ortho.halfHeight`                                                                         |
| `near`, `far`      | 0.1, 1000                                                | `nearPlane`, `farPlane`                                                                           |
| `viewport`         | `{x, y, width, height}` normalized, default full         | `camera.viewport` (`NormalizedViewport`; y measured from the bottom, per `resolveCameraViewport`) |
| `clearColor`       | `[r,g,b,a]` or `null`; default `null`                    | `scene.clearColor` (main camera only)                                                             |
| `priority`         | number, default 0                                        | main camera = highest priority enabled camera                                                     |
| `renderTarget`     | `RenderTexture \| null`, default `null`; not serialized  | a render task into the texture (§2.11); never the main camera                                     |

- Implementation: a Lite `FreeCamera` (`createFreeCamera({0,0,0}, {0,0,1})`) parented to the entity's node so the entity's transform defines the view; `world.mainCamera` sets `scene.camera`. A world with no enabled camera renders nothing and logs `IGX-0706` once — unless another rendering context has claimed the frame through `Renderer.addCameraSource`, an `@internal` hook whose one caller is `@ignifx/2d`: a `"sprite"`-mode world draws through a `Camera2D` and needs no `Camera` at all, so the warning would be wrong there. The claim is re-asked every frame and clears the once-only latch, so a world that later loses its `Camera2D` warns exactly as one that loses its `Camera` does.
- **Clear-colour precedence.** There is one `scene.clearColor` and three things that may write it, so they are ranked, strongest first:
  1. `Camera.clearColor` on the **main** camera, when it is not `null`; the sync system writes it every frame that camera renders.
  2. `Environment.clearColor` of the winning environment, when it is not `null`, written whenever the field changes or that environment becomes the winner (§2.5).
  3. The `rendering.clearColor` setting, written once as the render scene is created, before any frame has run. ignifx's default for it is opaque black.
  4. Babylon Lite's own default, a mid grey, which only code that bypasses `createApp` ever sees.

  A camera or environment whose `clearColor` goes back to `null` does **not** restore the setting: `null` means "leave the scene's clear colour alone".

- **What a clear colour looks like on screen.** Every one of those is stored as sRGB `[r,g,b,a]` and **presents as a fully fogged PBR fragment of that colour would**: with no image processing (exposure 1, contrast 1, tone mapping `"none"`) a channel lands on screen at `value * 255`, so an sRGB `0.5` reads back as byte `128`.
  - **Why the renderer has to do this.** Lite stores the clear value into the colour target untouched. The PBR shaders apply exposure, the tone-mapping curve, the `1/2.2` encode and contrast to what they draw, fog included, but nothing applies them to the clear, and Lite's own transmission and solid-skybox paths read `scene.clearColor` as the colour that should come out (`lib/frame-graph/transmission.js` `executeRenderTaskLinear`, `lib/material/pbr/background-solid-skybox.js`).
  - **The renderer applies that image processing to the clear colour on the CPU** (`src/render/image-processing-color.ts`): it decodes with `pow(c, 2.2)` as the fog block does, multiplies by the exposure, applies the curve Lite's shaders are compiled with (standard, ACES or neutral, the same constants), encodes, clamps and applies contrast. The state is read from `scene.imageProcessing` rather than from `Environment`, because `loadEnvironment` writes it too, and the `PreRender` system re-applies the clear colour whenever that state changes. So under ACES an sRGB `0.5` presents as byte `104`, and a fully fogged floor whose fog colour is the clear colour meets the sky with no band.
  - **Surface format.** `setSceneClearColor` writes the processed sRGB value unchanged on the default surface, whose format (`navigator.gpu.getPreferredCanvasFormat()`, `bgra8unorm` or `rgba8unorm`) does not encode, and decodes it only when the surface renders through an `*-srgb` view (`rendering.srgb: true`), which encodes it again on write. The offscreen path (§2.7) renders into targets of the surface's own format, so the same rule holds there, and bloom leaves a clear below its threshold alone.
  - **The exception** is a `PostProcessStack` whose `imageProcessing` effect is on: that pass grades the whole finished frame, clear included, as if it were linear (exposure, contrast, then a `1/2.2` curve), so an sRGB `0.5` presents as `186` there. Like everything else in the frame, fogged fragments included, it is graded again on top.
  - **2D.** `@ignifx/2d`'s `"sprite"` mode has its own clear, because the sprite pass owns the swapchain pass and nothing the render scene did survives underneath: it clears to rung 3, the `rendering.clearColor` setting, by the same rule, and rungs 1 and 2 do not apply (there is no `Camera` or `Environment` in a 2D scene, and `Camera2D` has no `clearColor` field).
  - `test/render/clear-color.browser.test.ts` pins all three writers, with ACES tone mapping, with a bloom chain and against a fogged floor.
- Methods, all in backing-store pixels (the canvas's `width`/`height`, the space `pickAsync` and `<Pointer>/position` share; not CSS pixels): `screenToRay(x, y, out?)` returns a world `Ray` or `null`; `worldToScreen(point, out)` writes `out` and returns whether the point is in front of the camera; `screenToWorldPoint(x, y, distance, out)` and `viewportToWorldPoint(u, v, distance, out)` return `out` or `null`; `getProjectionMatrix(out)` (via Lite `getProjectionMatrix(camera, aspect)`) and `getViewMatrix(out)`.
- Cinemachine-style rigs live in `@ignifx/3d` and `@ignifx/2d` as scripts that drive the camera entity's transform; the `Camera` component itself has no follow logic.

### 2.2 `Light`

- `type`: `"directional"` | `"point"` | `"spot"` | `"hemispheric"` maps to `createDirectionalLight` / `createPointLight` / `createSpotLight` / `createHemisphericLight`, **unparented**; the entity's world pose is written onto the light each frame it moves.
- `color` (sRGB), `intensity` map to `diffuse`/`specular` (linear) and `intensity`; hemispheric lights use `diffuseColor`/`specularColor`.
- `range` (point and spot) maps to `range`.
- `spotAngle` (degrees, full cone), `spotExponent` map to `angle` (radians), `exponent`.
- `groundColor` (hemispheric) maps to `groundColor`.
- `shadows`: `{ enabled, technique: "esm" | "pcf" | "csm", mapSize, bias, normalBias, darkness, cascades, maxDistance, stabilizeCascades, cascadeLambda, cascadeBlend }` maps to `createEsmDirectionalShadowGenerator` / `createPcfDirectionalShadowGenerator` / `createCsmDirectionalShadowGenerator` / `createPcfSpotlightShadowGenerator`, assigned to `light.shadowGenerator`.
- `includeOnly` / `exclude` (entity refs) map to `includedOnlyMeshIds` / `excludedMeshIds`.
- `bakeMode`: see §2.15.

- Point-light shadows and area lights are not available in Lite; the schema rejects `shadows.enabled` on point lights (`IGX-0703`).
- **A light is not parented in Lite.** Every other render component mirrors its entity by parenting a Lite object under the entity's node; a light cannot, because Lite reads its pose from two places that only agree when there is no parent. The shader takes the light's direction from `worldMatrix[8..10]`, which Lite composes as `parentWorld × localMatrixFromDirection(direction, position)`; the shadow frustum is fitted from `direction`/`position` **directly**. A parented light given a world direction is rotated twice; a parented light left with its local direction shades one way and casts another (ADR-0002).
- **The adapter writes the entity's world pose onto the light instead**, in each frame the entity's `worldMatrixVersion` moved: the world forward axis for a directional or spot light, the world **up** axis for a hemispheric light's sky direction, and the world position for anything that has one. That write is also the only "this light moved" signal Lite has — the lights UBO re-uploads only when a light's own observables are written.
- Changing light topology (adding a shadow caster light after start) triggers `rebuildSceneRenderables`; the adapter batches this to once per frame.
- Lite reads a generator's settings only when it builds it, so changing any field of `shadows` (technique, `mapSize`, bias, darkness, the cascade knobs) on a light that already casts releases its generator and attaches a new one on the next frame, at the cost of one renderable rebuild, as toggling `shadows.enabled` costs.
- **A shadow map is redrawn only when something it tracks moved.** Lite skips the pass unless a caster's `worldMatrixVersion` or thin-instance version, the light, or the camera (CSM; the floating origin for the others) changed. A skinned mesh posed by its skeleton, and a shader material moving its vertices by a uniform, change none of those, so on their own their shadows would freeze in the first pose drawn. Every generator therefore gets two layers when it is built (`src/lite/gpu/shadow-generator.ts`): Lite's `enableSkeletonShadows`, which fits the light to each skinned caster's posed bounds and redraws when those bounds change, and the engine's own check (`src/lite/shadow-caster-shapes.ts`), which redraws in any frame a caster's bone matrices or a shader material's uniform or resource versions changed — a pose that stays inside the same box included. The cost is one redraw per frame in which something really changed shape. Not covered: a storage buffer rewritten in place. Vertex-stage displacement beyond the mesh's own bounds is invisible to a PCF or ESM directional fit and to GPU instance culling unless the shader declares it with `// @ignifx displace` (§2.8). Morph targets would need Lite's `enableMorphTargetShadows`, which ignifx does not call.
- **A disabled light is dimmed, not removed.** While `enabled && entity.activeInHierarchy` is false the adapter writes intensity `0` and releases the shadow generator; enabling it writes the field's intensity back and attaches a new generator. Removing the light instead would change the light count every compiled PBR permutation bakes in, so every toggle would cost a renderable rebuild; releasing the generator still costs one, exactly as `shadows.enabled = false` does.

### 2.3 `MeshRenderer`

```ts
class MeshRenderer extends Component.define({
  mesh: asset(MeshAsset), // "models/hero.glb#mesh:Body" or a primitive created in code
  materials: array(asset(MaterialAsset)), // one per submesh; empty → default material
  castShadows: bool(true),
  receiveShadows: bool(true),
  renderOrder: i32(0),
  pickable: bool(true),
  lightmap: optional(…), // a baked lightmap placement, §2.15
}) {}
```

- `materials` keeps its array shape for the day Lite exposes submesh materials; a Lite `Mesh` has one `material`, so index 0 is used and the rest are ignored.
- A `MeshAsset` holds a template Lite `Mesh` (geometry uploaded once). Each `MeshRenderer` clones the template (`cloneTransformNode`, which shallow-clones meshes and shares GPU buffers) and parents the clone to the entity node, then `addToScene`. Removing the component calls `removeFromScene` on the clone; the template's buffers stay alive while the asset is retained (Lite ref-counts shared geometry).
- Primitives: `MeshAsset.box(app, options?)`, `.sphere`, `.plane`, `.ground`, `.cylinder`, `.capsule`, `.torus`, and `MeshAsset.fromData(app, name, data)` (Lite `createBox`, `createSphere`, … `createMeshFromData`). Each returns an `AssetHandle<MeshAsset>` the caller owns and releases (`release()` or `using`).
- Shadow casting is expressed through Lite's per-generator caster lists (`setShadowTaskCasterMeshes`); the adapter maintains those lists from `castShadows`. It rebuilds them only in a frame that owes no `rebuildSceneRenderables`: Lite's shadow task records a render pass over the caster meshes and looks each caster material's build group up in the scene, and a caster whose material family the scene has not registered yet throws inside the frame. So a caster added at runtime joins the lists on the frame after its renderable rebuild has resolved.
- `visible` is derived from `entity.activeInHierarchy && component.enabled && !displayHidden` (`mesh.visible`); never remove a mesh from the scene to hide it (Lite disposes a mesh leaving its last scene). `displayHidden` is a runtime flag, not a schema field, so scene files never save it; it also writes Lite's `pickable = false` while set, because Lite's pickers ignore `visible`, so a mesh hidden for display neither returns from nor occludes a pick: it is how a system chooses what is drawn without changing the document, as `@ignifx/3d`'s `LodGroup` does in an edit-mode app (ADR-0028). It is one flag with one owner, the group that lists the renderer as a level; a second group that lists it leaves it alone and warns with `IGX-1217` (ADR-0028 L4).

### 2.4 `Model`

```ts
class Model extends Component.define({
  model: asset(ModelAsset),
  materialOverrides: map(asset(MaterialAsset)), // by material name
  castShadows: bool(true),
  receiveShadows: bool(true),
  pickable: bool(true),
}) {
  readonly nodes: ReadonlyMap<string, LiteSceneNode>; // glTF node name → the instance's Lite node
  readonly animations: readonly LiteAnimationGroup[]; // Lite groups, re-bound per instance; consumed by @ignifx/3d Animator
  readonly skeletons: readonly LiteSkeleton[];
  attachToNode(nodeName: string, entity: Entity): boolean; // parents the entity's node under a glTF node (bone attachments); false when no such node
}
```

- Instantiation clones the asset's container root (`cloneTransformNode`) under the entity node and `addToScene`s it; animation groups are duplicated per instance. The instanced Lite subtree is opaque: it is not expanded into entities. `attachToNode` covers the common "weapon in hand" case.
- glTF cameras and lights inside models are always ignored. Lite gates cameras behind a process-global `enableGltfCameras()` that must run before the first load, so a per-asset flag could not decide it; a container's lights are never added to the scene.
- The adapter strips `animationGroups` from the container before `addToScene` so that Lite does not tick them; ignifx's animation system owns advancement (`01-lifecycle-and-time.md` §3).
- **`castShadows` and `receiveShadows` cover the whole instantiated subtree**, and mean exactly what they mean on a `MeshRenderer` (§2.3). Every mesh in the clone is collected **once**, when the subtree is instantiated — its shape is fixed from then on — and that list is what the model contributes to `setShadowTaskCasterMeshes` while it casts, and what `receiveShadows` is written across (Lite's `receiveShadows` is per mesh). A hidden model casts nothing, for the same reason a hidden `MeshRenderer` does. Instantiating a model, showing or hiding it, and flipping `castShadows` each report a caster change and rebuild the lists that frame; destroying one cannot report anything — the component has left the world's list — so its teardown raises the renderer's "caster set may have moved" flag and the next frame rebuilds.
- **A skinned or morph-target model added after `app.start()` draws.** Lite registers its PBR skinning and morph-target shader fragments only during a full PBR group build that contains such a mesh, but a mesh added to a PBR group that already exists (the warm-up builds one whenever the scene has a light at start) is built at once without them, and Lite caches that bind-group layout under a key that does not name the fragments. Left alone, the first such model a page adds turns every later frame into a WebGPU validation error and a black canvas. So the render sync system reads which kinds the scene's PBR meshes use (`src/lite/pbr-deformers.ts`) and clears Lite's layout caches before the first rebuild that sees a kind no earlier build composed, the same reset a change in shadow-map count gets (§2.2). A skinned model is drawn in its bind pose until that rebuild, one frame later; the first morph-target mesh instead costs a frame or two that WebGPU rejects, because the shader Lite builds without the fragment does not compile.
- **How the caches are cleared.** Lite's layout caches can only be cleared through the reset each material-group builder registers on `scene._disposables`. A rebuild registers the same module-level function again, so `src/lite/shadow.ts` records every function pushed while it is already in the list. A function seen for the first time (a family's first build, at registration, inside a rebuild, or in Lite's own runtime build of a family's first mesh after start) earns one confirming rebuild: `app.start()` runs it right after registration, a rebuild runs it straight after itself, and the render sync system schedules it for a runtime build. Each function asks once, so one-off disposers cannot loop.

### 2.5 `Environment`

One per world (the most recently enabled wins; the adapter logs `IGX-0705` once while two are enabled).

- **Fields:** `environment: asset(EnvironmentAsset)` (IBL `.env`/`.hdr`), `skybox: { enabled, size }`, `rotation` (degrees, Y), `blur` (0 to 1), `fog: { mode: "none" | "linear" | "exp" | "exp2", color, density, start, end }`, `imageProcessing: { exposure, contrast, toneMapping: "standard" | "aces" | "neutral" | "agx" | "none" }`, `clearColor`. They map to `loadEnvironment`, `setEnvironmentRotation`, `setEnvironmentBlur`, `scene.fog`, `setSceneImageProcessing`, `scene.clearColor`. There is no ambient-colour field: Lite has no scene-level ambient term, and a hemispheric `Light` supplies a flat one.
- **`clearColor`** is `optional(color())` and defaults to `null`, as `Camera.clearColor` does, which is what leaves the `rendering.clearColor` setting standing in a world whose environment never sets its own. A colour is written only when it changes, which keeps the main camera's per-frame override above it (§2.1). `imageProcessing` applies to the clear colour too (§2.1), so fog whose colour matches `clearColor` fades into the background with no band at any exposure, contrast or curve.
- **Winner changes.** Each environment writes only what changed since its own last write, so the one that becomes the winner (the newer one was disabled or removed) first forgets those writes and writes every field again; otherwise the scene would keep the previous winner's fog and clear colour.
- **`"agx"`** is ignifx's own Lite `ToneMapping` in `src/lite/gpu/agx-tone-mapping.ts`, loaded by a dynamic `import()` only when a scene names it: Benjamin Wendt's minimal AgX (a fit of Blender 4.0's "AgX Base"), base look only, raised to the power 2.2 after the sigmoid so Lite's `pow(1/2.2)` encode follows as for the other curves. The HDR output pass runs the same WGSL, and `image-processing-color.ts` carries the same numbers for the clear colour.

**Assigning a different loaded `EnvironmentAsset` swaps the lighting.** Lite declares no public way to replace a registered scene's environment — no `scene.environmentTexture`, no `unloadEnvironment` — so the adapter writes the one field every consumer of it reads: `scene._envTextures`, the field `loadEnvironment` itself assigns and the field Lite's own device-lost recovery replaces. `installSceneEnvironment` in `src/lite/gpu/environment.ts` is the only place ignifx touches a Lite field `index.d.ts` does not declare; its header records the `lib/` line behind every claim and a browser test pins the name. The diffuse harmonics and the LOD scale follow at once, because the render task's scene-UBO cache is keyed on the slot's object identity; the **specular** reflection follows only after the material groups are rebuilt, because a PBR bind group holds the cube map's texture view — so the component reports an install as a topology change and the §2.2 coalescing fires the frame's one `rebuildSceneRenderables`, one frame later as for any other topology change. Installing also re-applies rotation, blur, and image processing, because `loadEnvironment` overwrites `scene.imageProcessing` (tone mapping on, exposure 0.8, contrast 1.2) on every load. The GPU resources belong to the assets and are released by the asset system, so two retained handles can be swapped back and forth for nothing. Assigning `null` is defined as "stop steering", not "go dark": Lite has no inverse of `loadEnvironment`, so the last installed environment keeps lighting the scene, exactly as detaching the component does, and `Environment.installed` keeps naming it.

**`skybox` is decided when the environment loads, and only reported here.** Lite builds the background inside `loadEnvironment`, as a feature-owned `Renderable` queued in the scene's deferred builders and drained by `registerScene`; `Renderable` carries no visibility flag, no size, and no handle, and Lite offers nothing that removes or re-aims one. So the `.environment.json` is the authority (`skyboxEnabled`, `skybox`, `skyboxSize`); a `skybox` record that was _set_ to something the installed environment did not deliver logs `IGX-0711` once per component instead of being silently ignored (a field still at its schema default reports nothing, so a project whose declaration turns the background off is never told off for leaving the component alone); and an environment loaded **after** `app.start()` gets no background at all, because nothing drains the deferred builders again. A declaration that enables a skybox and names no image passes the `.env` as its own `skyboxUrl`, which is what selects Lite's HDR cube background over the flat box painted in a snapshot of the clear colour. A swap does not move that background, so a world that switches environments at runtime wants `skyboxEnabled: false` and `Environment.clearColor`.

### 2.6 Materials

- `MaterialAsset` from `.material.json` (`06-serialization-and-scene-format.md` §6):
  - `"type": "pbr"` → `createPbrMaterial(props)`: `baseColor`, `baseColorTexture`, `metallic`, `roughness`, `metallicRoughnessTexture`, `normalTexture`, `emissive`, `emissiveTexture`, `occlusionTexture`, `alphaMode` (`opaque|mask|blend`), `alphaCutoff`, `doubleSided`, `unlit`, plus opt-in extensions (`clearcoat`, `sheen`, `transmission`, `anisotropy`, `iridescence`) that the adapter enables only when present so unused shader code is tree-shaken.
  - `"type": "standard"` → `createStandardMaterial()` + `setStandard*Texture` setters.
  - `"type": "shader"` → `createShaderMaterial` from a `ShaderAsset` (§2.8); `shader`, `values`, `textures`, `defines` in the file. `MaterialAsset.setUniform/getUniform/setTexture/setDefine/setStorageBuffer` edit a live shader material (`IGX-0712` unknown name, `IGX-0713` wrong shape, `IGX-0718` on a PBR or Standard material).
  - `surfaces: [handle | "$asset"]` on a PBR definition attaches surface shaders (§2.8).
- Materials are shared: many renderers reference one asset. Per-renderer variation uses material _instances_ (`MaterialAsset.clone(app)`, an ignifx-level copy of the material props that creates a new Lite material); many copies of one mesh take per-instance colours through `InstancedMeshRenderer.setColors` (§2.9).
- Property changes after the scene is registered go through Lite's dirty mechanism (`markMaterialUboDirty` / opt-in `enableMaterialTracking`); the adapter marks dirty on setter calls.

### 2.7 `PostProcessStack`

Attached to the main camera entity. The schema is one record per built-in effect plus a list of custom ones:

- `bloom`, `smaa` and `imageProcessing` each carry `enabled` and an `order`; with the entries of `custom` (post-effect shaders, §2.8, each with its own `order`) they form the **chain**. Each chain entry maps to a Lite post-process task appended to the scene frame graph with `addTask`, which puts it after the render pass.
- `contactShadows` and `ssgi` are records too, but not chain entries: they run on the scene colour ahead of the chain (below).
- Temporal anti-aliasing and ambient occlusion are project settings, not stack entries (§2.13, §2.14).

**Post-processing is a feature opt-in and renders through an offscreen target.** A chain can never sample the swapchain: `createSurface` configures the canvas context with no `usage`, so its texture is `RENDER_ATTACHMENT` only and binding it as a source fails WebGPU validation, rejecting the whole frame — a black page. So a project that wants a `PostProcessStack` declares `rendering.features.postProcessing` (§1.1). With it on, the render scene is created with `defaultRenderTask: false` and ignifx builds its own frame graph:

```text
[shadow] → scene ──→ sceneColor ──→ present ──→ swapchain
                         └─ a PostProcessStack appends its effects here, and disables present
```

- `sceneColor` is an offscreen, single-sample colour target — resolved from the MSAA target through the render task's `rst` when MSAA is on — and it carries the `TEXTURE_BINDING` the swapchain lacks.
- `present` is a copy task that composites `sceneColor` onto the swapchain. It always runs unless a chain is writing the swapchain itself, so the frame is never lost: an empty chain, a chain with every effect off, and a disabled stack all present the plain scene.
- Every target is sized by the surface, so a canvas resize reallocates them through the frame-graph rebuild Lite already does; the chain handles no resize itself.
- `imageProcessing` is always recorded **last**, whatever `order` says: Lite's task writes the swapchain unconditionally and takes no target, so nothing can read what it produced.
- A `PostProcessStack` may be configured before `app.start()`: its chain is appended to Lite's frame graph without recording while the scene is unregistered, and `registerScene`'s own `frameGraph.build()` then records it after the scene task (recording while the scene is unregistered fails with Lite error 107, "sourceTexture has no color texture").
- A `PostProcessStack` attached without the feature logs `IGX-0710` once and is inert. The feature costs one full-screen blit per frame while no chain is recorded, which is why it is off by default.
- **Tuning is live; shape is rebuilt.** A write to `bloom.weight`/`kernel`/`threshold`/`exposure` or to any SMAA field on a running stack is re-uploaded to the recorded Lite task on the next `PreRender` (`updateUniforms()`), and only when a value changed. A change to the chain's _shape_ — which effects are enabled, their `order`, or bloom's `scale`, which sizes the blur targets at creation — disposes the chain and records a new one; the old tasks stay in the frame graph disabled, because Lite has no removal.

**HDR output (`rendering.hdr`).** Off by default; on, the render path is built by `src/lite/gpu/hdr-output.ts`, a chunk `createRenderEngine` imports only then. The scene draws into an `rgba16float` target (with MSAA, a multisampled `rgba16float` target that resolves into it). Lite's PBR shader tone maps, encodes and clamps every fragment, so a material plugin (`ignifx-hdr-linear-output`) saves the colour before that block and restores it before the fragment is written; the renderer gives it to every PBR material in the scene each frame, rebuilding a material it patches after registration. One output pass then applies `scene.imageProcessing` (exposure, contrast and the standard, ACES, neutral or AgX curve, whatever the `Environment` or `loadEnvironment` set) with the same `pow(1/2.2)` encode, clamp and contrast, so a PBR-only scene presents the same image as without HDR. The clear colour is stored decoded (`pow(c, 2.2)`) and goes through the same pass. The pass writes the swapchain, or `sceneColor` when built-in effects follow it.

**HDR coverage.** Every other colour writer writes linear colour too, so nothing is encoded twice:

- **Fog.** The restore re-applies Lite's PBR fog block (its own copy of `calcFogFactor`, which Lite declares only in fogged shaders). The fog colour is stored decoded (`pow(c, 2.2)`) while HDR is on: the HDR path swaps the `Environment`'s fog config for a decoded copy before each frame that changed it, so the restore and the Standard fog block both mix linear colour.
- **Unlit PBR.** Without an environment Lite assigns the unlit colour at `NI`, after the save, so unlit materials get their own plugin that recomputes `baseColor * unlitColor` before the fragment is written.
- **Standard materials** do no image processing and no encode; a plugin at `BC` (priority 1000, after any other plugin) decodes their colour with `pow(c, 2.2)`, the exact inverse of the output pass's encode, and bakes through `reconcileMaterialPlugins`. Surface shaders only run on PBR hosts (a Standard host is refused), and their composite runs before the save, so the PBR plugin covers them.
- **Custom `.wgsl` materials** (particles, foliage) write display colour. Under HDR, `src/lite/gpu/shader-material.ts` renames the file's `@fragment fn mainFragment` and adds a `mainFragment` with the same parameters that decodes its result (premultiplied colour is un-premultiplied around the decode). A fragment that returns a struct is left alone.
- **Skybox.** A PBR skybox (`setPbrSkybox`) is a PBR material and gets the PBR plugin. Lite's `.env` and `.dds` background skyboxes have fixed shaders; ignifx adds a patch to Lite's skybox patch list (`scene._environmentSkyboxShaderPatchLoaders`, created by `setEnvironmentRotation(scene, 0)` at install) that returns the cube map's colour before its own exposure, encode and contrast. Lite's six-face `loadSkybox` cube and its solid and ground backgrounds have no patch point and are still encoded twice.
- **Sprites** (`@ignifx/2d`, `particles-2d`) need nothing: a `SpriteRenderer` is a separate rendering context that draws on the swapchain after the scene's frame graph, so it never passes through the output pass (`packages/2d/test/hdr.browser.test.ts`).
- **Custom post effects first.** The leading run of custom effects in a `PostProcessStack` (those ordered before any built-in one) is inserted between the scene pass and the output pass with `addTaskBefore`, ping-ponging through `rgba16float` links; the first reads the HDR texture directly, and the output pass is rebound (`setEffectTexture`) to the last one's result. SMAA and Lite's `imageProcessing` task stay after the output pass, because they expect display colour in the surface's 8-bit format; bloom under HDR is the HDR bloom described below, which runs ahead of the output pass. A chain of custom effects only leaves the output pass writing the swapchain.

```text
[shadow] → scene ──→ hdr (rgba16float) ─ [custom effects] ─→ output ──→ swapchain
                                                              └──→ sceneColor ─ built-in chain → swapchain
```

What changes under a tone-mapping curve: Standard and custom-shader colour, which Lite never image-processes, goes through the scene's exposure, curve and contrast like PBR colour; the `.env` skybox, which Lite exposes and encodes without a curve, gets the curve too. With Lite's defaults (exposure 1, contrast 1, no curve) the output pass only re-encodes, and every writer presents the bytes the plain path presents (`packages/core/test/render/hdr-coverage.browser.test.ts`).

**Auto exposure (`rendering.autoExposure`).** Off by default and ignored without `rendering.hdr`; on, `createRenderEngine` also imports `src/lite/gpu/auto-exposure.ts` and a compute task runs between the scene and the output pass. One dispatch reads a 64×64 grid of the HDR target (whatever its size) into a 256-bin `log2` luminance histogram (range −12 to 12; bin 0 takes black, such as the clear, and is not metered); a second, one workgroup, drops the darkest and brightest 10% of the counted texels, averages the rest in `log2` space, clamps it to `[minEv, maxEv]`, eases the current EV towards it (`speedUp` when brighter, `speedDown` when darker, `1 − exp(−dt·speed)`; the first metered frame snaps) and writes `log2(0.18) + compensation − EV` into a 1×1 `r32float` texture. The output pass multiplies the linear colour by `exp2` of that texel before the `Environment`'s exposure and curve. All on the GPU, no readback; `dt` is wall-clock time measured in the per-frame update, clamped to 0.25 s. The settings are read once at `app.start()`.

**Contact shadows and SSGI.** Two records, `contactShadows` (`enabled`, `intensity`, `length`, `thickness`, `samples`) and `ssgi` (`@beta`, desktop tier: `enabled`, `intensity`, `radius`, `samples`, `halfResolution`, `environmentDiffuse`), wire Lite's `createScreenSpaceContactShadowsPostProcessTask` and `createScreenSpaceGlobalIlluminationPostProcessTask`. Both off by default; enabling one loads `src/lite/gpu/contact-shadows.ts` or `ssgi.ts`, plus `scene-color-passes.ts` and the shared scene inputs (§2.12), whose `depth32float` target is the tasks' `depthTexture` (Lite reconstructs normals from depth, so the normals input is unused). They are not chain entries: they run on the scene colour right after the scene task, ahead of the present blit, the HDR output pass and the chain, ping-ponging between the scene's resolved target (`ScenePresenter.scenePass`) and one scratch target, with a copy back when the count is odd. Under `rendering.hdr` that target is the linear `rgba16float` one, so both work on linear colour; on the plain path they work on display colour, and there no pass writes the scene target (`ScenePass.isTargetWritable`): it is allocated lazily, and a Lite post-process task that writes a lazy target reallocates it in `record()`, destroying the texture the scene task recorded (a black frame and WebGPU's "Destroyed texture" error). The plain path ping-pongs between two scratch targets instead and always ends with the copy.

```text
scene ─→ S ─ contact ─→ scratch ─ ssgi ─→ S ─→ present / output pass / chain
```

- **Light.** Contact shadows march towards the first shadow-casting directional light, else the first directional light; with none the task runs disabled.
- **Camera.** Lite's tasks keep the camera they were created with, so a change of `scene.camera` rebuilds them, as do toggling either record, the stack's `enabled`, and `ssgi.halfResolution`. Every other field is written onto the tasks each frame.
- **Not counting the bounce twice.** Lite's SSGI composite is additive. A material plugin (`ignifx-ssgi-environment`, priority -1, so before the HDR save) subtracts `(1 - environmentDiffuse)` of the environment's irradiance (`finalIrradiance`, `lib/material/pbr/fragments/ibl-fragment.js`) at `CUSTOM_FRAGMENT_BEFORE_FINALCOLORCOMPOSITION`; specular is untouched. That point is injected at both `AI` and `NI`, and `finalIrradiance` exists only with an environment, so the plugin declares a module-scope `finalIrradiance` of zero that the IBL `let` shadows, and subtracts only the change since its previous run: one subtraction whichever side of the IBL code it lands, none without an environment. It is attached to lit PBR materials only while SSGI runs, and only with `rendering.hdr` or the `materialPlugins` feature (the bridges must exist before registration); the factor is baked into the WGSL, so changing it recompiles.
- **Removal.** The tasks are spliced out of the frame graph's private task list on teardown, as the scene inputs do.
- **Tests.** `packages/core/test/render/screen-space-effects.browser.test.ts`: contact shadows darken a box-on-floor frame and leave it unchanged once off; SSGI brightens it under HDR; both together keep the plain path lit with no device error; the plugin darkens an `.env`-lit frame.

**HDR bloom.** Under `rendering.hdr`, `PostProcessStack.bloom` is not Lite's LDR bloom: it is a downsample/upsample chain on the linear `rgba16float` scene colour (`src/lite/gpu/bloom-hdr.ts`, a chunk the stack imports the first frame it asks for bloom under HDR). Six `rgba16float` mips from 1/2 to 1/64 resolution are surface-scaled targets; the first downsample is the 13-tap filter of Jimenez (SIGGRAPH 2014) with a Karis average against fireflies and an optional soft-knee threshold, the others the plain 13-tap; each upsample is a 9-tap tent blended into the next larger mip as `mix(mip, tent, radius)`; the composite writes back into the HDR target through the blend unit, `mix(hdr, bloom, intensity)` without a threshold (the default: energy is redistributed, not added) or `hdr + bloom · intensity` with one. Its 12 tasks go in through `HdrOutputHandle.insertLinearTask`, after every linear task already in place (TAA's resolve among them) and right before the output pass, so the glow is exposed and tone mapped with the rest of the frame and the output pass needs no rebinding:

```text
scene → hdr ─ down → mip₀ … mip₅ ─ up … → mip₀ ─ composite → hdr → output → swapchain
```

Which bloom runs: with `rendering.hdr` on, the HDR bloom **replaces** the LDR bloom (the LDR one is left out of the chain), reads `intensity`, `radius` and `hdrThreshold` and ignores `order`; with `hdr` off the LDR bloom runs and ignores those three fields. The chain is built once per stack and only switched on and off after that (Lite cannot remove tasks); at detach its tasks are disabled and their `record` made a no-op, so a later frame-graph rebuild walks them harmlessly. Until the chunk has loaded (a frame or two) the frame presents without bloom.

**Combinations no test covers:** the clear colour under HDR with `rendering.srgb`; auto exposure metering the writers that are still encoded twice (above); contact shadows and SSGI with MSAA or across a resize; HDR bloom with MSAA. Device loss is in §4.

### 2.8 Custom shaders

Rationale: ADR-0024. Three authoring forms, all `.wgsl` files whose `// @ignifx` pragma comments are the declaration; nothing is kept in sync with a JSON manifest, and the declaration doubles as the inspector schema.

- **Shader material** (`// @ignifx shader`). Lite path: `createShaderMaterial`; the whole file is both stages (`mainVertex`, `mainFragment`). It gets Lite's `shaderSystem.*` uniforms, the `scene` UBO, ignifx's `time`, `unscaledTime`, `deltaTime`, `mainLightDirection`, `mainLightColor` and `ambientColor` in `shaderUniforms`, textures, read-only storage buffers, defines, blend/cull/depth state, and `instancing matrices|matrices-colors`. It does not get direct lights, received shadows, or a `cull front` mode.
- **Surface shader** (`// @ignifx surface`). Lite path: one Lite `MaterialPlugin` on a **PBR** host, with the hooks `displace`, `surface`, `composite`. It gets lights, shadows, IBL, fog and tone mapping; `baseColor`, `alpha`, `emissive`, `normal`, the composited colour; and a world-space vertex offset. `roughness` and `metallic` are readable and ignored on write. It does not get a uniform, texture or `time` in `displace` (§8), and a Standard host is refused (`IGX-0723`); without `rendering.features.materialPlugins` a material that carries one is `IGX-0716`.
- **Post effect** (`// @ignifx post`). Lite path: `createEffectWrapper` + `createEffectRenderTask`, recorded into the §2.7 chain. It gets `inputTexture`, `screenSize`, `time`, and declared uniforms and textures, and is ordered with the built-ins, `imageProcessing` still last. It does not get depth or normals.

- **Pragma grammar.** `attributes`, `system`, `uniform name: type = default [range] [step] [color] [tooltip]`, `texture name [srgb] [normal] [default white|black|transparent] [array]`, `storage name: array<T>`, `define NAME = …`, `blend … cull … depthWrite … depthTest … transmissive instancing …`, `displace metres`. `src/render/shader-pragma.ts` parses it at runtime; `@ignifx/vite-plugin` parses the same file with `wgsl_reflect` at build time and reports syntax errors (`IGX-0654`) and contract violations (`IGX-0655`) with a line. Declared uniforms reuse the schema kinds, so `ignifx.schemas.json` and the devtools inspector see them for free; `color(...)` is written in sRGB and uploaded linear.
- **Per-frame uniforms.** `ShaderUniformSystem` (`PreRender`, before the render sync) uploads the ignifx uniforms once per frame per material that declares them, allocation-free. `time` is `app.time.time`, so it freezes under `app.pause()`. Light uniforms come from the highest-intensity enabled directional `Light`; with none present they are zeros and `IGX-0714` is logged once.
- **Hot reload.** A `ShaderAsset` connects to its handle's `onReplaced` and rebuilds every material built from it in place, so renderers keep the same material object. A compile failure keeps the last good material and reports `IGX-0715` through `app.onError`.
- **Displacement margin.** Lite's mesh bounds (`boundMin`/`boundMax`) are object-local and know nothing of a vertex stage, yet the directional PCF/ESM fit reads them directly (`computeDirectionalLightMatrix`, `lib/shadow/shadow-base.js`) and the GPU instance culler pads its per-instance sphere only by `setThinInstanceCullBoundsPad`. So `// @ignifx displace <metres>` declares the furthest the vertex stage moves a vertex, in world metres, and `MaterialAsset.displacement` sums it over the shader and its enabled surface shaders. A `MeshRenderer` widens its own clone's bounds by it — the clone first gets bound arrays of its own, since a fresh clone shares the template's with every other renderer of the asset — dividing by the entity's world scale per axis; an `InstancedMeshRenderer` sets the cull pad and widens the instance union it publishes. Lite does no CPU frustum culling of ordinary meshes, so a `MeshRenderer` has no culling to fix. The margin is not applied to `Model` material overrides or terrain chunks. A surface shader's `displace` hook does not move thin instances.
- **Warm-up and shadows.** A shader material is its own warm-up family (ADR-0014). Shader materials cast PCF and CSM shadows; Lite has no ESM view for the shader family, so the caster list skips them with one `IGX-0724` warning.
- **Bundle cost.** Lite's shader-material, plugin, thin-instance, storage-buffer and effect-task code lives in adapter chunks reached through dynamic `import()` from the first GPU use, so `hello-cube` pays nothing for any of this (`benchmarks/bundle-size.test.ts`; constitution §2.5).
- **Headless.** A shader material holds its declaration and values and uploads nothing, like PBR (§6).
- The raw Lite injection points stay reachable through `defineMaterialPlugin` (`@beta`); they track Lite's template and carry no stability promise.

### 2.9 `InstancedMeshRenderer`, storage buffers, pixels

- `InstancedMeshRenderer` draws thin instances of one `MeshAsset`: `setMatrices(slab, count)` takes a caller-owned `Float32Array` of 16 floats per instance that Lite reads by reference, `setColors` a 4-float slab, `setCount` a dynamic draw count, `markDirty()` after in-place writes. `gpuCulling` (Lite's compute frustum cull) and `lod: { mesh, distance, band }` (Lite's LOD partner) are fixed when the scene is registered; a later change logs `IGX-0717` and is written back. The LOD partner draws only while `gpuCulling` is on, because Lite picks the far instances in the culling pass; `lod` with culling off logs `IGX-0727` once. Writing past `capacity` is `IGX-0721`. Headless, the component holds the slab and count. Foliage and the particle draw are built on it.
- `createStorageBufferAsset(app, name, data)` / `StorageBufferAsset.update(data, byteOffset?)` (`IGX-0720` past the end): read-only in shaders, bound by `setStorageBuffer`; the asset type has no file format, so an address load rejects with `IGX-05xx` and `unload` frees the GPU allocation.
- `TextureAsset.fromPixels(app, name, rgba, width, height, options)` and `textureAsset.update(...)` (`IGX-0722` on a size mismatch); `MeshAsset.fromData` accepts `uvs2`, `tangents`, `colors`, and `updatePositions/updateNormals/updateUvs/updateColors` re-upload a `fromData` mesh (`IGX-0725` when the range does not fit; a mesh a `MeshRenderer` has already cloned cannot be updated because Lite refuses shared geometry).

### 2.10 Render overlay

`app.renderer.openOverlay()` (`@beta`, ADR-0031) returns a `RenderOverlay` whose `lite.scene` is a second Lite scene drawn over the finished frame, for an editor's gizmos, selection outlines and grids. `lite` has the shape Lite's gizmo constructors take as a `UtilityLayer` (`{ scene, mainScene }`), so Lite code under `src/lite/` passes it straight to `createPositionGizmo` and its siblings. `dispose()` releases it; `app.dispose()` releases any still open. On a headless app, or before `app.start()` has registered the render scene, it throws `IGX-0728`. Once the app is disposed it throws `IGX-0106`, also when the disposal happened while the overlay was opening; the half-opened overlay is disposed first.

- **Why not Lite's utility layer.** `registerUtilityLayer` fixes the layer up against the last registered rendering context (`lib/scene/swapchain-overlay.js`). After `@ignifx/ui` or `@ignifx/2d` registered a text or sprite renderer, that context has no frame graph, so the layer clears the frame to black. With MSAA on, the layer draws only when the base scene resolves straight into the swapchain, which the §2.7 offscreen path never does.
- **What it draws into.** One render task into the swapchain with `clr: false` and `sharedRt: true`, over a single-sample depth target of its own that it clears every frame. It reads whatever the frame's last pass presented (the scene's MSAA resolve, `ignifx:present`, a post-process chain, sprites, text) and touches none of their targets, so it is correct at every `msaaSamples` and on both render paths. Helpers are never hidden by the scene; within the overlay depth testing works as usual. The overlay itself is drawn without MSAA.
- **Why after the frame and not before `ignifx:present`.** Drawing into the scene's own target would put gizmos through bloom and tone mapping, would not exist on the plain path, and would be erased by a `"sprite"`-mode sprite renderer that clears the frame after the render scene.
- **It stays last.** Lite draws contexts in registration order, and the 2D and UI extensions register theirs lazily. Each frame the overlay checks `getRenderingContexts`; when anything other than another overlay follows it, it re-registers itself at the end after the frame. That frame draws no overlay. A move that fails (a lost device, a pipeline that does not compile) is reported through `app.onError` with `source: "system"` and tried again on the next animation frame, three times in all; after that the overlay stays detached until it is disposed.
- **Its scene** follows the render scene's camera every frame and has the hemispheric light (intensity 2) `createUtilityLayer` adds, so Lite's gizmo materials look the same. It is registered with an empty frame graph and its task is added afterwards, so Lite's swapchain fix-up never touches it.
- **Limit.** A Lite scene registered with `registerScene` while an overlay is open is fixed up against the overlay; at MSAA above 1 Lite then disables that scene's default task. ignifx registers no such scene after `app.start()`.
- **Cost.** The module is loaded on the first `openOverlay()`, so a game that never opens one ships none of it (§2.5). An open overlay costs one render pass and one `getRenderingContexts` scan per frame.

### 2.11 Render to texture

`app.renderer.createRenderTexture(width, height)` (`@beta`) returns a `RenderTexture`: an offscreen colour target a second camera renders into, beside the main view. Each side is a whole number from 1 to `RENDER_TEXTURE_MAX_SIZE` (4096), else `IGX-0730`. Two ways fill it: `app.renderer.renderToTexture(camera, texture)` renders it once, on the next frame, and settles once that frame is submitted; `camera.renderTarget = texture` renders it every frame that camera is enabled, and takes the camera out of the main-camera choice whatever its `priority`. `texture.readPixels()` answers RGBA8, top row first, as the last submitted frame left it. A headless app may create a texture but never fill or read one (`IGX-0729`, also before `app.start()` and after `app.stop()`); a disposed or foreign texture is `IGX-0731` and a detached camera `IGX-0732`. `app.dispose()` disposes every texture still open. The editor host's Game panel view and asset thumbnails are built on it (`17-editor-host.md` §6.3). A page that gets no animation frames (a hidden tab, a `visibility: hidden` iframe) never runs the frame a request waits for, so `renderToTexture(camera, texture, { maxWaitMs })` and `app.renderer.nextFrame({ maxWaitMs })` render it themselves (Lite's `renderFrame`, delta zero) when no animation frame has come within `maxWaitMs`, and again every `maxWaitMs` until it is served; a wait that is not a finite number of 0 or more is `IGX-0733`. A `nextFrame` still waiting when the loop stops (`app.stop()`, `app.dispose()`) settles then.

- **The pass.** One Lite `createRenderTask` per texture, appended to the render scene's frame graph, into a fixed-size `createRenderTarget` in the surface's colour format with a depth/stencil attachment of its own, single-sample (`src/lite/gpu/render-texture.ts`). The task auto-mirrors the scene's renderables and owns its own scene UBO, so its camera never disturbs the main pass. The camera's aspect is the texture's. Its camera is `RenderTaskConfig.cam`, which Lite reads on every execute; with no camera the task is switched off with `executionEnabled`. Requests for one texture render one camera per frame, oldest first.
- **What it draws.** The render scene only: no post-process chain, no overlay, and no other rendering context (`@ignifx/2d`'s sprites, `@ignifx/ui` text).
- **Lite gaps.** Lite has no task removal and no texture readback. `dispose()` splices the task out of the frame graph's `_tasks` before disposing it (a disposed render task throws from `record()` on the next rebuild), and `readPixels` copies the target's `_colorTexture` through `engine._device` into a mapped buffer. Both rely on Lite private fields and are pinned by `test/render/render-texture.browser.test.ts` at MSAA 1 and 4.
- **Cost.** The module is loaded on the first render or read, so a game that never uses one ships none of it (§2.5). A texture costs nothing until then; after that, its target, and one render pass in each frame it is filled.

**Editor-only meshes.** A render-scene mesh whose Lite `metadata[EDITOR_ONLY_METADATA_KEY]` is `true` (an editor's grid) draws in the main view but never in a render texture: the pass hides such meshes around its own `execute` and shows them again, after the main pass has drawn, so the main view never flickers.

### 2.12 Scene inputs

Screen-space effects (TAA, GTAO, contact shadows, SSGI) read the scene's depth, normals and motion from one shared geometry pass, `src/lite/gpu/scene-inputs.ts`. It is internal: an effect calls `rendererInternals(app.renderer).acquireSceneInputs()`, gets a lease, and calls its `release()` when it is disposed. The first acquire loads the chunk and adds the pass; the last release removes and disposes it. An app whose effects never ask loads none of it and its frame graph has none of these tasks (`CONSTITUTION.md` §2.5). Under the null engine `acquireSceneInputs()` returns `null`.

```text
[shadow] → geometry ─→ normals copy ─→ velocity copy ─→ depth pyramid → scene → … → effects
```

| Input          | Format         | What it holds                                                                                                        |
| -------------- | -------------- | -------------------------------------------------------------------------------------------------------------------- |
| `depth`        | `depth32float` | Reverse-Z depth (1 near, 0 far), sampled facade; bind with `sampleType: "depth"`                                     |
| `normals`      | `rgba16float`  | World normals stored as `n * 0.5 + 0.5`; 0 where nothing was drawn                                                   |
| `velocity`     | `rgba16float`  | `0.5 * (previousNdc - currentNdc)`: UV units, Y up, from now to last frame; 0 where nothing was drawn                |
| `depthPyramid` | `r32float`     | Full mip chain; each level is the `max` (nearest surface in reverse-Z) of its four children; read with `textureLoad` |

- **One pass, shared.** Leases are counted; two effects get the same textures and one geometry pass. The tasks sit at the start of the frame graph (after `shadow`), so any task appended later reads this frame's values (`SCENE_INPUT_TASK_NAMES` names them).
- **Bridges.** Lite's main pass uses `depth24plus-stencil8`, which compute cannot bind, so the geometry pass draws its own `depth32float` depth. Geometry attachments are task-owned `RenderTarget`s with no `Texture2D`, so normals and velocity are copied into targets that have one (§8, upstream ask "geometry attachments as `Texture2D`").
- **The pyramid** is Lite's `createDepthPyramid` (render passes, one per level, not compute), wrapped so it can be rebuilt.
- **Resize and device loss.** Every target is sized by the surface and reallocated by `frameGraph.build()`. The depth target's resize callback, which also fires when a recovered device reallocates it, rebuilds the pyramid and calls each lease's `onChange` callbacks so effects can rebind; `depthPyramid` is a new object afterwards. A resize is covered by a browser test.
- **Removal.** Lite has no public way to remove a task, and a disposed task left in the graph is recorded again on the next rebuild against freed targets, so the last release splices the tasks out of the graph's private `_tasks` list (`lib/frame-graph/frame-graph-actions.js`) before disposing them.
- **Limit: object motion on PBR.** Lite's PBR geometry view reprojects the current world position through the previous view-projection (`lib/material/pbr/pbr-geometry-output-shader.js`), so a PBR mesh moving under a still camera writes 0. Standard materials track each mesh's previous world matrix. There is no per-object PBR velocity (§8, upstream ask "velocity for moving PBR meshes").
- **Cost.** One geometry draw of every mesh, two full-screen copies and the pyramid's passes per frame while any lease is held.

### 2.13 Temporal anti-aliasing

`rendering.taa` is temporal anti-aliasing in its own chunk, `src/lite/gpu/taa.ts`, which `app.initialize()` loads only when `rendering.taa.enabled` is on (`CONSTITUTION.md` §2.5). It needs `rendering.hdr`: with HDR off the app logs a warning and TAA stays off. It leases the scene inputs (§2.12) and splices five tasks between the scene pass and the HDR output pass, ahead of any linear custom effect:

```text
scene (jittered) → taa-jitter → taa-resolve → resolved ─(copy)→ history
                                             resolved ─ taa-output (sharpen) → HDR scene target → [linear effects] → output pass
                                             depth ─ taa-depth → previous depth (r32float)
```

- **Jitter.** A Halton (2,3) offset, eight points, is added to the scene task's view-projection by writing the first 64 bytes of its scene uniform buffer after the task wrote its own (Lite's private `_sceneUBO` and `_suData`, the trick Lite's own `createTaaPostProcessTask` uses). Only the GPU copy is jittered: Lite's camera caches, picking, `Camera.worldToScreen` and the scene-inputs geometry pass see the clean matrices. The HDR handle exposes `sceneTask` and `sceneTarget` for this.
- **Reprojection.** Where the geometry pass drew, the scene-inputs velocity at the nearest depth of the 3×3 neighbourhood; elsewhere (sky) the pixel goes through the inverse view-projection and the previous one. History is read with a 4×4 Catmull-Rom filter.
- **Clamping and rejection.** History is clipped to the YCoCg variance box (γ 1.25) of the current neighbourhood, on colour compressed by `c / (1 + max(c))`. It is dropped off screen and where the depth stored last frame disagrees by more than 5 % with where the surface would have been (disocclusion).
- **Reset.** On the first frame, a resize or recovered device (the targets' resize callbacks and the lease's `onChange`), a camera cut (a jump over `cutDistance` or a turn over 60° in one frame, read from the clean view matrix) and `renderer.resetTemporalHistory()`.
- **Limits.** Object motion on PBR materials has no velocity (§2.12), so a moving PBR mesh relies on the clip. Floating origin is not handled (the clean matrices are eye-relative). A `PostProcessStack`'s SMAA runs after the output pass, on display colour; SMAA and TAA together are allowed but redundant.
- **Cost.** The scene-inputs pass, plus four full-screen passes (resolve, one copy, output, depth) at the surface size.

### 2.14 Ambient occlusion

`rendering.ambientOcclusion` is ground-truth ambient occlusion on indirect light, `src/lite/gpu/gtao.ts`, its own chunk. Off by default; on, the renderer loads the chunk in `attachHandles`, leases the scene inputs (§2.12), and `app.start()` waits for both before `registerScene`, so the tasks are recorded with the rest. It is read once: a later edit takes a restart. Fields: `enabled`, `quality` (`"half"`: half resolution, 2 slices × 4 steps a side; `"full"`: full resolution, 3 × 6), `radius` (metres, 0.5), `intensity` (exponent on visibility, 1), `falloff` (fraction of the radius over which occluders fade, 0.6). It is a project setting, not a `PostProcessStack` record, because the plugin applies to every material and the pass is per scene, not per camera.

```text
… depth pyramid → gtao-params → gtao (compute: horizons, then a 5×5 depth-aware blur) → scene → …
                                                   └─ AO texture (rgba8unorm) → lit PBR `occlusion`
```

- **The pass.** One compute task with two dispatches. GTAO (after XeGTAO) reconstructs view-space positions from the depth pyramid (level 1 at half resolution, coarser levels for far taps) and rotates the world normals into view space; slice angle and step offset are jittered per pixel. The blur weights taps by view-depth similarity. A tiny task before it writes the camera matrices from inside the frame graph, after Lite's world-matrix update, so the AO does not lag a moving camera.
- **Indirect light only.** A material plugin at `CUSTOM_FRAGMENT_BEFORE_LIGHTS` multiplies Lite's PBR `occlusion` by the AO texture at the fragment's pixel (four loads blended at half resolution). `occlusion` scales environment irradiance and specular occlusion only, so direct lights and emissive are untouched, and a scene with no environment cube map shows nothing. Every lit PBR variant declares it: the template's default, or the reflectance extension's `AT` code (`lib/material/pbr/fragments/reflectance-fragment.js`). Unlit PBR, Standard materials and custom shaders are skipped. The plugin is attached by a per-frame walk, like the HDR plugins, and forces `features.materialPlugins` on.
- **HDR.** Independent: the plugin changes the lighting input, not the output, so it works with and without `rendering.hdr` (browser test `test/render/ambient-occlusion.browser.test.ts`).
- **Resize and device loss.** The scene inputs' `onChange` disables the pass, rebuilds textures, shaders and bindings, swaps them in and rebuilds the patched materials, whose bind groups hold the AO view; the old set is disposed eight frames later.
- **TAA.** With `rendering.taa` on, TAA's resolve filters the final colour, AO included, which smooths the per-pixel jitter; there is no separate AO history, and the GTAO reads the unjittered camera.
- **Limits.** No dedicated AO history; a render-to-texture camera (§2.11) samples the main view's AO, which is wrong for its own view; no bilateral upsampling at half resolution.
- **Cost.** The scene inputs' geometry pass, plus 2 × 4 × 2 depth taps a pixel at quarter area (`"half"`) or 3 × 6 × 2 at full area, and a 25-tap blur.

### 2.15 Quality tiers and baked lighting

`rendering.quality` is `"custom"` (default), `"low"`, `"medium"` or `"high"`, one per row of the GPU budget in coding standards §7. `registerRendering` applies the tier before the renderer is built (`applyRenderingQuality` in `src/render/rendering-settings.ts`), so `renderer.settings` is what runs and `app.settings.section("rendering")` stays what the project wrote. A named tier sets `hdr`, `taa.enabled`, `ambientOcclusion.enabled` and `ambientOcclusion.quality`; a field the project wrote itself is kept, which is why the store exposes the project's raw value (`SettingsStore.declared`): the resolved section cannot tell a written `false` from a default one. The tier also caps a `PostProcessStack`'s screen-space effects (`src/render/screen-space-effects.ts`): contact shadows from `"medium"`, SSGI at `"high"`. Bloom, tone mapping and auto exposure are left as authored; the budget allows bloom and AgX at every tier.

| Tier     | `hdr` | TAA | GTAO | contact shadows | SSGI    | reflection probe size | `everyFrame` probes |
| -------- | ----- | --- | ---- | --------------- | ------- | --------------------- | ------------------- |
| `low`    | off   | off | half | off             | off     | ≤ 64                  | read as `once`      |
| `medium` | on    | on  | half | allowed         | off     | ≤ 128                 | read as `once`      |
| `high`   | on    | on  | full | allowed         | allowed | ≤ 256                 | allowed             |

The reflection-probe columns are read each frame by the probe runtime (`src/render/gpu/reflection-probes.ts`) from `renderer.qualityPreset`: a probe's `size` is clamped to the tier's maximum, and below `"high"` a probe asking for `refreshMode: "everyFrame"` captures as `"once"` (when first ready, and on `refresh()`), with one warning per app. Light probes and lightmaps are not tiered: baked lighting is the low-end path. `"custom"` caps nothing (sizes up to 1024, `everyFrame` allowed). A probe borrows the scene environment's BRDF table and harmonics, so until an environment map is loaded nothing of it runs: the renderer does not load the probe chunk, and if the environment goes the runtime frees every probe's face targets and cube and stops its per-frame mesh walk; a probe's targets are allocated on the first capture that can run (an `"onDemand"` probe's on its first `refresh()`). The 3D templates add one `ReflectionProbe` at `"high"` only (`templates/3d-*/src/quality.ts`); they load no environment map, so it costs nothing until a project adds an `.env`.

**Baked lighting.** Three `@beta` components and one function light a 3D scene from prepared data; the user-facing guide is the skill page `skills/ignifx/references/concepts/baked-lighting.md`. Each GPU path follows `CONSTITUTION.md` §2.5: a host in `src/render/gpu/*-host.ts` reaches its chunk (`src/render/gpu/{reflection-probes,light-probes,lightmaps}.ts` with `src/lite/gpu/{reflection-probe,light-probes,lightmap}.ts`) by a dynamic `import()` only once a world has a component of its kind, so a project with none loads none of it and does no frame work. `RendererImpl.updateBakedLighting`, called by the `PreRender` sync after the environment is applied, drives the probe and volume hosts each frame and flushes the lightmap material copies; on a headless app it returns at once. Edit mode renders, so all three show in an editor's scene view.

- **`ReflectionProbe`.** No file and no bake: the capture is the bake.
  - **Capture.** The chunk renders six 90° faces from the probe's world position through `createRenderTask` + `createBankedFreeCamera` into `rgba16float` targets, copies them into a cube, box-filters a mip chain, and wraps it in `EnvironmentTextures` that share the scene environment's BRDF table and harmonics (diffuse is unchanged). `cullingMask` filters the capture by layer and editor-only meshes are hidden from it, as in §2.11. `refreshMode` is `"once"`, `"onDemand"` or `"everyFrame"`, under the tier rules above; a capture repeats over a few frames so meshes whose pipelines are still compiling are caught. There is no GGX prefilter and no capture to a file.
  - **Selection.** Each lit PBR material gets the nearest enabled, captured probe (`selectReflectionProbe`: a probe whose `boxProjection` box holds the mesh wins, the smallest such box first, then the nearest centre) through `setPbrLocalEnvironment` (box parallax) or `setPbrEnvironment` (no box), and the scene environment again when there is none; a shared material follows the first mesh visited.
  - **Blending** (`ReflectionProbe.blendDistance`). When two or more captured box probes exist and one has a `blendDistance` above 0 (`reflectionProbeBlendLayout`), one `createPbrLocalEnvironmentProbeSet` goes on every lit PBR material instead of the nearest probe: each probe's outer influence box is its projection box and its inner box that less `2·blendDistance`, and the voxel grid spans the boxes at 32 cells along the longest side. Volumes go smallest box first (Lite takes the first inner box that holds a fragment). A material whose nearest probe has no box keeps it.
  - **When blending is off.** An `everyFrame` probe turns blending off. A probe whose binding or `blendDistance` changed within 15 frames takes the nearest-probe choice, so no set is rebuilt per frame while one is dragged. A set Lite refuses (more than four candidates in a voxel) logs once per runtime and falls back to the nearest probe.
  - **Set lifetime.** Lite copies the cubes into the set when it is made and has no dispose for it (its resources go with the scene; §8, upstream ask "probe-set dispose"). So the runtime rebuilds the set after a probe moves, recaptures or changes its box, and destroys a replaced set's `_texture`, `_uniformBuffer` and `_gridBuffer` once the material rebuilds settled. A replaced set's cleanup closure is also taken off `scene._disposables`, so its CPU data does not live until the scene goes; a missing field logs instead of throwing. On device loss the set is dropped with the cubes.
- **`LightProbeVolume` and `.probes.json`.** A `LightProbeAsset` is a grid (`origin`, `cellSize`, `counts`) of first-order harmonics, 12 linear-RGB floats per probe scaled like Lite's environment harmonics, so a white surface with normal `n` receives `c0 + c1·n.y + c2·n.z + c3·n.x`. The file schema is `ignifx/light-probe-file` in `src/render/schemas.ts`, loaded by `createLightProbeLoader` with no device (Node included); a malformed file is `IGX-0709`. The chunk packs the grid into one `rgba16float` 2D texture read with `textureLoad` (probe `(i, j, k)`'s coefficient `c` at texel `(i + countX·c, j + countY·k)`; Lite plugins bind 2D textures only) and gives every lit PBR material one plugin at `CUSTOM_FRAGMENT_BEFORE_FINALCOLORCOMPOSITION` that adds `(probes·intensity − environment)·surfaceAlbedo·occlusion` to `color`, blending the eight surrounding probes per fragment (Lite declares `environmentIrradiance` with `let`, so it cannot be replaced). Grid constants are written into the WGSL (a new grid rebuilds materials); `intensity` is a uniform. With SSGI on, the diffuse term is `P − (1 − environmentDiffuse)·E`. The most recently created enabled volume wins.
- **`MeshRenderer.lightmap` and `.lightmap.json`.** A `LightmapAsset` names a texture by address and per-entity-uid atlas `entries` (`scale`, `offset`); the file schema is `ignifx/lightmap-file`. A renderer whose entity is static and whose material is PBR gets its own material copy and `setPbrLightmap` (`mode` `"add"` or `"shadowmap"`, Lite's `useAsShadowmap`; `level`; `gamma`; UV2 or UV1); anything else draws without it and logs `IGX-0735` once. The chunk calls `enablePbrLightmap` itself when it loads, which is safe after `registerScene` because a material without a lightmap reports no lightmap feature bits, so `rendering.features.lightmaps` only does it earlier.
  - **Atlas placement.** Lite's lightmap fragment samples `input.uv2` raw and ignores the texture's `uScale`/`uOffset`, so a renderer whose entry is not the identity gets a vertex plugin at `CUSTOM_VERTEX_MAIN_END`, which the PBR template runs right after `out.uv2 = uv2;`, rewriting the varying to `uv2·scale + offset` (`lightmapAtlasPlugin` in `src/lite/gpu/lightmap.ts`; Lite's V flip then applies to the placed coordinate, as to the raw one).
  - **Why constants, not a uniform.** The scale and offset are WGSL constants, one shared plugin and one pipeline variant per distinct placement, because a vertex-visible plugin uniform needs `enablePbrMaterialPluginVertexData`, whose bridge injects `CUSTOM_FRAGMENT_BEFORE_FINALCOLORCOMPOSITION` at `NI` only, while the light-probe, HDR-output and SSGI plugins count on the default bridge's `AI` + `NI` double injection (§8, upstream ask "vertex-data plugin bridge").
  - **Limit.** The varying exists only for a UV2 lightmap on a mesh with a `uvs2` buffer (`pbr-compose.js`, `_hasUv2`), so a placement with `uv2: false` (UV1 also maps the material's textures) or on a mesh without `uvs2` (every primitive) logs `IGX-0735` and samples the whole texture. The plugin holds no GPU resources, so device loss needs nothing beyond Lite's pipeline rebuild.
- **`bakeLightProbes`.** A CPU bake in `src/render/light-probe-bake.ts`: per probe, `rays` Fibonacci-sphere directions are traced (Möller–Trumbore) against world-space triangles; a hit is shaded by the material's flat base or diffuse colour times the direct light with a shadow ray, a miss by `sky` plus hemispheric lights. One bounce, deterministic. It yields to the host about every 8 ms, reports `onProgress` per probe, and stops on an aborted `signal`. Bad options are `IGX-0734`. The result is `LightProbeData` the caller passes to `createLightProbeAsset` or saves with `writeLightProbeFile`. Lightmaps are not baked in the engine: that needs a UV2 unwrap and a GPU path tracer, which the engine does not have.
  - **Direct light.** With `directLight: "include"` the directional, point and spot lights the probe sees are added as exact clamped-cosine lobes (spot cones ignored). The default, `"exclude"`, leaves them out, because those lights keep lighting the scene in real time and a baked direct lobe would count their light twice; a probe then holds their bounce, the sky and the hemispheric lights.
  - **Per-light bake modes.** `Light.bakeMode` (`"realtime"` default, `"mixed"`, `"baked"`) decides what a light gives the bake (`lightBakeTerms`): every light bounces; a probe stores a light's direct light when the light is `"baked"`, never when `"mixed"`, and for `"realtime"` only with `directLight: "include"`; a `"baked"` light is dimmed to 0 and casts no shadow at run time, as a disabled one is. A hemispheric light follows the same rule: its direct part (what a miss sees of it) is stored only when the rule says so, its bounce always. Otherwise the probes, which replace the environment's diffuse term and not the light's, would hold it on top of the real-time term and count it about twice.
  - **Sky.** `sky` takes a linear colour, a `{ kind: "gradient", sky, horizon, ground }` or `{ kind: "sh9", coefficients }` (27 numbers of radiance in the real SH basis). The scene's `Environment` is not used as the default sky: its harmonics are in the `.env`, which a headless app does not fetch.
  - **What is traced: meshes.** Every enabled `MeshRenderer` whose mesh came from `MeshAsset.fromData`, and every primitive: a primitive `MeshAsset` remembers its `MeshPrimitiveDefinition`, and `src/render/light-probe-bake-primitives.ts` rebuilds its triangles on the CPU at Lite's sizes and defaults (curved shapes at ≤ 16 segments). Each mesh keeps a world AABB that a ray slab-tests before its triangles.
  - **What is traced: models, headless.** A `Model` is read from its glTF file by `src/render/light-probe-bake-gltf.ts` (GLB chunks or `data:` buffers; `POSITION`, indices, strips and fans, node TRS/matrices down the default scene, then X mirrored as Lite's `__root__` node does; `baseColorFactor × (1 − metallicFactor)`; `Model.materialOverrides` by material name). The file comes from `ModelAsset.sourceBytes`, which only a **headless** load keeps (a device load already holds the container, and keeping the file too would double a game's model memory). Draco and meshopt primitives, sparse accessors and external `.gltf` buffers are skipped.
  - **What is traced: models, under a device.** The bake reads the model's instance instead (`src/render/gpu/light-probe-bake-model.ts`): each mesh of the cloned subtree (`Model.instanceMeshes`, internal) through Lite's `getMeshTriangles` (`src/lite/gpu/mesh.ts` `readMeshBakeSurface`; a glTF load retains positions and indices on every mesh and a clone spreads them), at the mesh's own world matrix. It is coloured by the model's override for its material name, else by that glTF material's `baseColorFactor × (1 − metallicFactor)` as a device load records it (`ModelAsset.bakeAlbedos`, internal: Lite bakes an untextured material's factor into a 1×1 texture, so the drawn material cannot tell it), else by the Lite material's own factor. A model whose instance does not exist yet (not synced by a frame) is skipped. The editor host's `bakeLightProbes` (`17-editor-host.md` §6.4) bakes this way, and derives the default sky from the installed environment's harmonics.
  - **Skips.** Every skip is reported in `LightProbeBakeResult.skips` (`{ entity, uid, component, reason }`); `skipped` counts the components that gave no triangle.

## 3. Picking

- `app.renderer.pickAsync(x, y, options)` → GPU pick (`createGpuPicker` + `pickAsync`), resolves to `{ entity, component, point, normal, distance, meshName, thinInstanceIndex }` using node metadata. Calls are serialized per picker (Lite constraint).
- **Unit.** `x`/`y` are backing-store pixels, like `Camera.worldToScreen`, `screenToRay` and `<Pointer>/position`, so a pointer position or a point from `worldToScreen` picks exactly at every device pixel ratio, `pixelRatio` and `resolutionScale`. Lite's `pickAsync` takes CSS pixels: it multiplies by `canvas.width / (clientWidth || width)` before anything else (`lib/picking/gpu-picker.js`; `index.d.ts`: "CSS-space canvas coordinates"). The adapter divides by the same ratio first (`src/lite/gpu/picker.ts`). Lite renders its 1×1 target at the exact sub-pixel point, so whole-number coordinates are pixel corners; add 0.5 for the centre. DOM code multiplies `offsetX`/`offsetY` by `canvas.width / canvas.clientWidth`.
- **Ownership.** A hit resolves through the nearest node on its way to the root that carries an ignifx tag. A `MeshRenderer` tags its clone, but a `Model` tags only the cloned glTF root, and Lite draws that root's descendants; the walk resolves both, and the entity filter is applied through the same walk. It stops at the first tag, so an entity parented under a model's bone owns its own meshes.
- **Options.** `filter(entity)` and `ignore: (Entity | Component | RenderPick)[]`. Entities and components are folded into the mesh predicate; an earlier hit becomes Lite's `PickOptions.ignore` entry for that mesh, or that thin instance, so passing the previous hit walks through a pixel front to back. Lite reads only the first ignore entry per mesh, so several thin instances of one mesh are merged into a range when contiguous and otherwise only the lowest is skipped and a hit already listed can come back (a Lite limit), so a walk-through loop stops when a hit repeats; the public `ignore` TSDoc and the skill say so. A rejected or ignored mesh neither occludes nor returns.
- **Detail.** `point` comes from Lite's depth readback and is set on every GPU hit; `normal` needs Lite's detailed picking, which ignifx does not turn on, so it is `null` from a GPU pick. `meshName` is the Lite mesh's name (for a glTF file, its node or primitive). `thinInstanceIndex` names the `InstancedMeshRenderer` instance. Lite's `subMeshId` is always `0` and is not exposed.
- `world.raycastRender(ray, options)` → synchronous CPU pick (`pickWithRay`) against renderable meshes, with the same options; an ignored thin instance skips its whole mesh, because a CPU ray has no per-instance discard. Distinct from physics raycasts (`09-physics.md` §5).
- 2D sprite picking is provided by `@ignifx/2d` (`pickSprite2D`).

## 4. Device loss

- `createApp` enables `enableDeviceLostSceneRecovery` when `rendering.features.deviceLostRecovery` is on (every feature is opt-in), and the 2D/UI extensions enable `enableDeviceLostSpriteRecovery` / `enableDeviceLostTextRecovery` **before** creating resources (Lite requirement).
- Reflection probes own a cube texture Lite does not know about. On `app.events.onDeviceLost`, before Lite's recovery rebuilds the materials, the probe runtime points every material back at the scene environment (without a rebuild of its own), drops each probe's passes and cube, and remembers which probes had captured; after recovery they are created again and capture again, an `"onDemand"` probe included. Outside device loss, a removed probe's cube is destroyed once the rebuilds of the materials that reflected it settle and the queue is idle; its face targets go with their render tasks.
- Callbacks fan out to `app.events.onDeviceLost`, `onDeviceRecovered`, `onDeviceRecoveryFailed`. Lite recovers ESM and CSM shadow generators but not PCF ones, and not glTF `EXT_lights_image_based` environments; when those are in use, recovery is expected to fail and templates offer a reload (§8, upstream ask "device-loss recovery of PCF shadows and glTF image-based lights").
- **Test coverage.** `test/render/device-loss.browser.test.ts` and `csm-device-loss.browser.test.ts` force a loss on the base path and with cascaded shadows. No test covers recovery of the HDR target, auto exposure's buffers, the scene inputs, the GTAO targets, the screen-space effects, HDR bloom or reflection probes.

## 5. Diagnostics and tools

- The `render` diagnostics group: `drawCalls` (`engine.drawCallCount`), `gpuFrameTimeMs` (with `setGpuTimingEnabled`), per-task GPU timings (`getRenderTaskGpuTimings`) when `renderer.profileTasks` is on, which switches both `setGpuTimingEnabled` and `setRenderTaskGpuTimingEnabled`.
- `app.renderer.captureScreenshot()` → `captureScreenshot(engine)`; it settles only while the render loop is running (a frame must be presented), so headless apps get `IGX-0707`.
- A development-mode app installs Lite's error decoder through a dynamic import (`packages/core/src/lite/error-decoding.ts`), awaited before the engine is created. The decoder and Lite's 44 KB message table are one reachability set, and `createApp({ mode })` defaults to `"development"` in every build, `vite build` included, so a static import would put the table in every production entry chunk. An app created with `mode: "production"` never fetches it and reports Lite's compact codes. There is no separate `decodeError` path.

## 6. Headless behaviour

Under the null engine, `MeshRenderer`/`Model` skip GPU work: the template mesh has no geometry, `addToScene` is not called, and `visible` toggles are no-ops. Transforms, bounds from asset metadata, and picking by physics still work. Tests assert on component state, not on Lite scene contents.

## 7. Disposal order

`app.dispose()` runs: stop engine → `onStop` hooks → unload scene instances (component `onDestroy`, `removeFromScene`) → extension `dispose` in reverse order (physics disposes its Havok world _before_ the scenes are disposed: Lite's physics documentation warns that the step callback must be removed before the native world is released, which `disposePhysics` does, and ignifx orders it first so no scene callback can fire against a released world; audio disposes its engine independently) → `disposeScene(renderScene)` → release texture handles through Lite's resource pool (`acquireTexture`/`releaseTexture`; `Texture2D` has no dispose of its own) → `disposeEngine`. Lite does not cascade physics or audio disposal from scene disposal; ignifx does.

## 8. Known Lite gaps that shape this document

- **No GUI system.** `@ignifx/ui` uses DOM overlays and Lite text layers (`13-ui.md`).
- **No point-light shadows, area lights, cube capture, light probes or lightmap UV transforms.** Shadows and area lights: schema-level rejection. Probes and lightmaps: built in ignifx (§2.15).
- **No public setter for a scene's environment, and no handle on the skybox it builds.** `installSceneEnvironment` writes `scene._envTextures` (§2.5); the background stays a load-time decision.
- **Single active camera per scene.** `priority` selects; other cameras render into textures through render tasks (§2.11).
- **No layer masks on cameras.** `Camera` has no culling mask; a `ReflectionProbe` filters its own capture by layer (§2.15).
- **Mesh disposal on last-scene removal.** Hide via visibility; only `destroy` removes (§2.3).
- **No frame-graph task removal and no render-target readback.** Tasks are spliced out of the graph's private `_tasks`; `readPixels` copies through `engine._device` (§2.11, §2.12).
- **Frequent breaking changes.** Adapter boundary, exact pin, adapter tests (`00-overview.md` §3).
- **Vertex-visible plugin uniforms and samplers need `enablePbrMaterialPluginVertexData`, whose bridge drops the `AI` injection other plugins rely on.** ignifx does not enable it: surface `displace` is static, time-driven vertex motion uses a shader material (§2.8), lightmap placement is WGSL constants (§2.15).
- **Shader materials receive no lights or shadows and cannot be ESM casters.** Surface shaders for lit looks; `IGX-0724` under ESM.
- **PBR skin and morph fragments register only in a full group build.** `src/lite/pbr-deformers.ts` clears the layout caches when a new kind arrives (§2.4).

Compute is not a gap: Lite has compute tasks, and auto exposure (§2.7) and ambient occlusion (§2.14) use them.

**Upstream asks**

What ignifx would ask Babylon Lite for, each checked against the pinned version's `index.d.ts`. Cite an ask by its name. None has a tracked issue in this repository.

Rendering:

- **Linear HDR output.** A scene or material switch that leaves PBR output linear and unclamped, so one final pass tone maps. Workaround: the save-and-restore plugins of §2.7.
- **Single post-composition plugin point.** `CUSTOM_FRAGMENT_BEFORE_FINALCOLORCOMPOSITION` is injected at both `AI` and `NI`; a single point after all composition and before fog, or documentation of the double injection. Workaround: each plugin guards against running twice (§2.7).
- **Vertex-data plugin bridge.** A bridge for `enablePbrMaterialPluginVertexData` that keeps the `AI` injection, so a plugin can have vertex-visible uniforms, samplers and helpers without breaking the others. Workaround: static `displace`, WGSL constants for lightmap placement (§2.8, §2.15).
- **Geometry attachments as `Texture2D`.** `createGeometryRendererTask` exposes its attachments as `RenderTarget`s only, which compute and effect bindings cannot take. Workaround: two full-screen copies per frame (§2.12).
- **Velocity for moving PBR meshes.** The PBR geometry view writes camera motion only. Workaround: TAA relies on its clamp for a moving PBR mesh (§2.12, §2.13).
- **TAA with reprojection.** `createTaaPostProcessTask` resets on camera motion and reads no velocity. Workaround: ignifx's own TAA (§2.13).
- **Soft shadows.** A PCSS or contact-hardening option; cascaded shadows filter with a fixed PCF kernel.
- **Area lights** and **point-light shadows.** Neither exists; the schema rejects both (§2.2).
- **Probe-set dispose.** `createPbrLocalEnvironmentProbeSet` has no dispose. Workaround: the runtime destroys a replaced set's private GPU objects (§2.15).
- **Light and shadow bindings for shader materials**, and a **`time` system uniform**. Workaround: shader materials are unlit and ignifx uploads `time` itself (§2.8).
- **`composite` slot for Standard materials.** Lite's Standard template has no injection point after composition, so a surface shader's `composite` stage is refused on a Standard host (`src/render/surface-shader-compiler.ts`).
- **Device-loss recovery of PCF shadows and glTF image-based lights** (§4).
- **Mesh removal without disposal.** A mesh leaving its last scene is disposed for good (§2.3).
- **Basis transcoder URL setter.** `loadBasisTexture2D` hard-codes a CDN URL, so ignifx refuses `.basis` (`05-assets-and-loading.md` §5).

Loop and physics:

- **`onBeforeRender` disposer.** `onBeforeRender` returns nothing; ignifx guards its callback with a flag (ADR-0003).
- **Public physics step.** A step function that does not go through a scene's callback list. Workaround: a headless simulation scene stepped with `stepScene` (`09-physics.md` §1, ADR-0003).
- **Per-body damping, gravity factor, sleep thresholds and wake-up.** Lite exposes none of them, so `Rigidbody` has no such fields (`09-physics.md` §2).
