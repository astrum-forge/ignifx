# 15 · Devtools and Diagnostics

**Status:** Design standard (pre-1.0) · **Packages:** `@ignifx/core` (`app.diagnostics`, errors, logging), `@ignifx/devtools`, `@ignifx/vite-plugin` (HMR)

---

## 1. Errors

- `IgnifxError extends Error` with `code: "IGX-####"`, `context` (entity/component/asset identifiers), and `hint`. Development builds format the full message; production builds keep the code and context. Ranges: `01xx` lifecycle, `02xx` components, `03xx` scenes, `04xx` extensions, `05xx` assets, `06xx` serialization, `07xx` rendering, `08xx` input, `09xx` physics, `10xx` audio, `11xx` 2D, `12xx` 3D, `13xx` UI, `14xx` platform, `15xx` devtools, `9xxx` reserved for third parties.
- `app.onError: Signal<ErrorReport>` receives every error thrown from a lifecycle callback, coroutine, system, or asset loader, with the source identified; the default handler logs and, in development, shows an overlay. Babylon Lite coded errors are decoded (`enableErrorDecoding` in dev; lazy `decodeError` in prod).

## 2. Logging

`app.log` (and `ctx.log` per extension) with levels `debug/info/warn/error`, scoped prefixes, rate limiting for per-frame warnings ("warned once" helper), and a pluggable sink (console by default; devtools console panel; file sink in Electron).

## 3. Diagnostics (`app.diagnostics`)

A frame-sampled, allocation-free set of counters grouped by subsystem (`frame`, `render`, `physics`, `assets`, `input`, `audio`, `twoD`, `animation`) plus per-phase CPU timings in development. Consumers read the latest sample; a ring buffer of the last 300 frames supports graphs.

## 4. Devtools overlay (`@ignifx/devtools`)

Toggled with a configurable key or `app.devtools.open()`; DOM-based, and zero cost when closed. `app.devtools` is `{ open, close, toggle, isOpen, panel(name), panels, select, selected, reloadScenes, onOpened, onClosed, onSelectionChanged }`, and the `devtools` settings section carries `toggleKey` (a `KeyboardEvent.code`, default `"Backquote"`), `openOnStart`, `reloadScenes`, `panels` (the tab order, and by omission a filter), `position` and `opacity`. The extension owns `IGX-1550`–`IGX-1599`; `IGX-1501`–`IGX-1549` belong to `@ignifx/core`'s diagnostics and logging.

- **The toggle key is a raw `keydown` on the document**, never an input action: `@ignifx/input` is an optional peer, and an action map a pause menu disables would take the developer's escape hatch with it (`08-input.md` §5).
- **Where it mounts.** In `app.ui.layer("devtools")` when `@ignifx/ui` is registered and its overlay is live; otherwise the overlay builds its own root as the canvas's next sibling, the way `13-ui.md` §1's host does. Every optional peer — `ui`, `input`, `audio`, `physics`, `physics-2d` — is reached structurally, so a game with only `@ignifx/core` opens the same overlay with three of its nine panels saying "not registered".
- **Zero cost when closed** means, precisely: no system is registered until the first `open()`, no signal is subscribed to while it is closed, and no DOM exists while it is closed — `close()` disposes the overlay and its panels and `open()` rebuilds them. The one thing core does not allow is taking the system away again: the scheduler has `registerSystem` and no `unregisterSystem`, so after the first `open()` the sampler stays registered for the app's life and returns on its first line while the overlay is closed.
- **Sampling** runs in `Phase.PreRender` at order 9000 — after every renderer, 2D, UI and audio system, so the sample reports the numbers those systems just wrote. Text panels refresh at 10 Hz; the Timeline graph refreshes every frame. Only the visible panel refreshes at all.
- **Headless** (`07-rendering.md` §6): `open()` is a no-op with one debug line. Everything else — `panel(name)`, `select(entity)`, the signals, the settings — works, so a headless test asserts on the same object a browser drives.

Panels: **Stats** (FPS, frame/CPU/GPU ms, draw calls, fixed steps, entities, components, assets, memory — CPU milliseconds are `0` outside a development build and `performance.memory` is Chromium-only), **Scene tree** (search, select, toggle active, destroy; the list is virtualised over a flattened index that rebuilds on the world's structural signals rather than per frame), **Inspector** (schema-driven editing of any component's fields live; copy component/entity as JSON; "select in world" via GPU pick), **Assets** (handles, refcounts, sizes, force reload), **Input** (live action values, devices, scheme), **Audio** (buses, instances), **Physics** (Lite physics viewer toggle, counts), **Console** (log sink), **Timeline** (phase timings graph over the last 300 frames).

Three of those need a qualification the one-line list cannot carry:

- **Inspector.** A field's editor is chosen from its kind: number, bool, string, enum, vector, quaternion, colour, asset and reference get a control, and `array`, `record`, `map`, `layerMask`, `curve` and `custom` are shown as their encoded JSON and are not editable — a nested editor for them, and a wrong `custom` codec write, would corrupt game state rather than merely look wrong. `hidden` drops a field, `readonly` disables it, `min`/`max`/`step`/`tooltip`/`group` are honoured. A write is `component[name] = value`, which is exactly what the scene loader's `applyProps` does; core has no field-change hook, so the assignment _is_ the documented path. `Transform` declares no schema — the scene format writes it as a first-class record — so the panel builds its position/rotation/scale rows by hand and writes through `transform.localPosition` and friends, which are live views over the Lite node; that is why an inspector edit moves the entity in the same frame.
- **Assets.** `Assets` publishes `get(address)` but no listing of live handles, so the panel walks `app.assets.manifest` and asks for a handle per address: an asset registered at run time under an address the manifest never carried does not appear. Force reload calls the asset service's `reload(address)` — the entry point the Vite plugin's HMR channel uses — which is not on the public `Assets` interface, so the button is disabled and reports `IGX-1555` on a build that has none.
- **Console.** The extension creates a `DevtoolsLogSink` and adds it to `app.log` with `Logger.addSink` (added to core at the Phase 10 integration precisely for this), so every logger in the tree — `ctx.log` included — reaches the panel with no game-side wiring; `devtools({ logSink })` substitutes a shared or differently sized sink. The panel also lists `app.onError` reports and `app.hotReload` reports, newest first.

## 5. Script hot reload

The policy lives in `@ignifx/core` as `app.hotReload`, so it works headlessly with no bundler; the Vite plugin only supplies the channel.

- **The channel.** The Vite plugin generates the script registry as the virtual module `virtual:ignifx/scripts` (from an `import.meta.glob` of the configured pattern — there is no `scripts/index.ts` barrel on disk), and that module self-accepts: a script file is already in Vite's module graph, so script hot reload needs no custom HMR event of its own. The generated module exports `acceptHotReload(app)` alongside `scripts`; a game calls it once, which is the whole hand-off — the module cannot discover the app, and a module-level app reference is what `CONSTITUTION.md` §3.5/§3.6 forbid. In a production build `acceptHotReload` is an empty function and neither the accept handler nor any `import.meta.hot` reference is emitted.
- **The contract.** `app.hotReload` is `{ onApplied: SignalLike<HotReloadReport>, reloadScenes: boolean, apply(modules): HotReloadReport, reloadScene(instance): Promise<SceneInstance> }`, with `HotReloadModule = { types: readonly ConcreteComponentType[] }` and `HotReloadReport = { kind: "patch" | "recreate" | "scene", typeIds, instances, durationMs, errors }`. `apply` matches each class by `typeId`: one the app has never seen is registered, one that is already the registered class is skipped, and the rest are reloaded under their policy. One report per call, emitted on `onApplied` and returned; a call that both patched and re-created reports `"recreate"`.
- **`apply` is a flush-time operation.** Calling it from inside a lifecycle callback is `IGX-0208`, for the reason `destroyImmediate` is `IGX-0102`: a half-swapped world must not be observable. An HMR message and a devtools button both arrive outside callbacks, so this costs nothing in practice.
- Default policy `"patch"`: live instances get their prototype swapped to the new class; state is preserved; no lifecycle callbacks re-run; static fields are re-read (a changed `executionOrder` reorders dispatch, and a changed callback set re-files the dispatch lists). Coroutines keep running, because the instance is the same object. Good for iterating on logic.
- Policy `"recreate"` (`static hotReload = "recreate"`): each live instance is serialized through its schema, destroyed (`onDisable`/`onDestroy`, coroutines cancelled), and re-created with the same uid, the same position in `entity.components`, and its props (`awake`/`onEnable`/`start` run again). Tracked `entityRef`/`componentRef` fields pointing **at** the re-created component are re-pointed at the replacement; plain untracked class fields are not, exactly as for an ordinary destroy. `asset()` fields carry their live handle across rather than their address, so an in-code `memory:` asset survives; `transient` fields take their default again. Required when field layouts change.
- **A `"patch"` class whose schema shape changed is re-created anyway**, with an `IGX-0207` warning naming it. Patching it would hand the new code an instance missing its new fields. "Shape" is field names, declaration order, and kinds, recursively; `min`, `tooltip`, and default values are not part of it.
- `static onHotReload?(previous)` lets a class migrate transient state (PlayCanvas `swap` lesson). It is **class-level**: it runs once on the new class, with the class it replaces, after every live instance has been swapped or re-created. It is deliberately not per instance — under `"patch"` the instances are the very same objects, so there is nothing to copy across, and under `"recreate"` per-instance state is re-derived from the schema by design. Whatever it throws is reported on `app.onError` and collected in the report; the remaining classes still reload.
- Asset hot reload is handled by the assets service (`05-assets-and-loading.md` §7); scene files reload by re-instantiating the affected `SceneInstance` — `app.hotReload.reloadScene(instance)` unloads it and rebuilds it from the asset's current value, honouring the file's instance overrides wherever their paths still resolve, and answers with the new instance (`IGX-1506` when the instance was not built from a scene asset). The toggle that does it automatically on `handle.onReplaced` is `app.hotReload.reloadScenes`, set with `createApp({ hotReload: { reloadScenes: true } })` and surfaced by the devtools overlay; it is off by default, because rebuilding a scene throws away everything the running game has done to it.

## 6. Performance tooling

- `app.diagnostics.profile(name)` scopes in development add `performance.mark/measure` entries visible in browser profilers.
- Benchmark scenes under `benchmarks/` run with Vitest `bench` (headless simulation) and a Playwright GPU job (frame time, draw calls) whose results are compared against committed baselines (`CONSTITUTION.md` §6.4).
