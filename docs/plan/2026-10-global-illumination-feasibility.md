# Plan · Global illumination feasibility ("can ignifx look like Unreal?")

**Status:** Assessment for an owner decision (2026-10-29) · **Owner:** Astrum Forge Studios · **Precedence:** below constitution, standards, architecture docs, ADRs (`CONSTITUTION.md` §10.1) · **Commits to nothing** until the owner picks a path (§6)

The owner asked what it would take to add Lumen-style global illumination (GI) so that lighting and shading look as good as Unreal Engine 5, and whether it is possible at all. This document answers in four parts: what the renderer does today (§1), what Lumen is (§2), the options and what each costs (§3, §4), and a recommended path with the decisions the owner has to make (§5, §6).

Every engine claim cites a file and line in this checkout, or a line in `@babylonjs/lite@1.34.0`'s `index.d.ts` and `lib/` (the pinned version, `pnpm-workspace.yaml` line 16). Run-time costs marked _estimate_ have not been measured on ignifx; they are scaled from the cited references and carry ±50% uncertainty. Agent-days assume one Opus agent per brief and the coordinator reviewing, calibrated against the terrain, particles and shaders plan, which shipped three systems in about eight agent-days (`docs/plan/2026-09-terrain-particles-shaders.md` §7, §11). Rendering work calibrates worse than that, because visual goldens and frame budgets run only locally (`docs/standards/coding-standards.md` line 264).

---

## 0. Short answer

- **Close to Unreal for many scenes: yes, and most of it is not GI.** Unreal's look comes from HDR rendering, stable soft shadows, temporal anti-aliasing, physically based bloom and exposure, ambient occlusion, reflections, and good assets as much as from Lumen. ignifx has gaps in nearly all of these (§1.3), and closing them is roughly 20–28 agent-days. For static or mostly static scenes, baked lighting (lightmaps and probes) then gets close to Unreal's look at almost no run-time cost. Many pre-Lumen Unreal games shipped exactly that way.
- **Lumen parity: no, not on WebGPU in 2026.** Lumen leans on hardware ray tracing, bindless resources, Nanite and a 4–8 ms GPU budget on PlayStation 5-class hardware at 1080p ([Epic, Lumen performance guide](https://dev.epicgames.com/documentation/en-us/unreal-engine/lumen-performance-guide-for-unreal-engine)). WebGPU has no ray tracing and no bindless resources (§2.2), and ignifx's reference machine is an Apple M1, an integrated GPU (ADR-0025 "Validation"; standards line 264).
- **Fully dynamic diffuse GI on desktop is possible** as a probe volume traced against a signed distance field (DDGI-style, option B). It costs 40–60 agent-days after the foundations, about 2–3 ms on a mid-range desktop GPU, and it does not fit phones.

## 1. The renderer as it is

### 1.1 What draws a frame

ignifx does not render; Babylon Lite does (`docs/architecture/07-rendering.md` line 5). The frame is a forward renderer with one Lite frame graph:

- With `rendering.features.postProcessing` on, ignifx builds `[shadow] → scene → sceneColor → present → swapchain` (`packages/core/src/lite/gpu/render-path.ts` lines 29, 109–151). Without it, Lite draws straight into the swapchain.
- `sceneColor` takes the **surface format** (`format: engine.format`, `render-path.ts` lines 111–116), which is an 8-bit `bgra8unorm` or `rgba8unorm` (`07-rendering.md` line 39). There is no floating-point scene buffer.
- Lite's PBR fragment shader applies exposure, the tone-mapping curve, a `pow(color, 1/2.2)` encode, a clamp to [0, 1] and contrast **per fragment**, unconditionally (`lib/material/pbr/pbr-template.js` line 171). So every pixel leaves the main pass display-referred and clamped. This is the single most important fact in this document: bloom, temporal accumulation and any screen-space GI in ignifx today operate on clamped 8-bit colour.
- There is no depth or normal prepass and no G-buffer. Custom post effects get `inputTexture` and `screenSize` only, never depth or normals (`07-rendering.md` line 149; `packages/core/src/render/post-effect.ts` lines 37–43).

Two limits matter:

- **Lite's TAA is a still-camera accumulator.** It jitters the projection with a Halton sequence and resets its history whenever the camera moves (`disableOnCameraMove` defaults to `true`, `lib/post-process/taa.js` lines 76, 105), and it reads no velocity. The SSGI and contact-shadow temporal pass reprojects through the previous view-projection, which handles camera motion but not moving objects (`lib/post-process/screen-space-temporal.js` lines 13–16). A game camera moves every frame, so neither is the TAA that Unreal-class images and GI denoising depend on.
- **No path to change Lite's lighting loop from outside.** A plugin can add a term at fixed points with 2D textures and uniforms; it cannot add an area light, PCSS, or a new BRDF lobe. `CONSTITUTION.md` §1.3 forbids a Babylon fork and §11.2 forbids copying Lite source, so those changes are upstream pull requests to Lite.

### 1.4 Budgets and devices

- Templates must hold 60 fps on the reference machine, with engine CPU time at most 4 ms in 3D (`docs/standards/coding-standards.md` line 152). There is no GPU budget in writing. The reference machine is macOS arm64 (standards line 264), measured on an Apple M1 (ADR-0025 "Validation").
- The 1.0 browser matrix is Chrome, Edge, Safari 26, Firefox on Windows and macOS, Chrome Android, and Electron on three operating systems (`engineering-plan.md` line 234). Phones are in scope.
- GPU timing reads 0 on Metal (`gpuFrameTimeMs`, ADR-0025 "Validation", measured on Lite 1.27). Unless 1.34 fixed it, GI work cannot be measured on the reference machine without a workaround, so measurement is a prerequisite.
- Pay for use (`CONSTITUTION.md` §2.5): a game that does not use GI must ship no GI bytes and do no GI work.

## 2. What Lumen is

### 2.1 The parts

Lumen is Unreal Engine 5's dynamic GI and reflection system ([Wright, Narkowicz, Kelly, SIGGRAPH 2022](https://advances.realtimerendering.com/s2022/index.html); [Epic, Lumen technical details](https://dev.epicgames.com/documentation/en-us/unreal-engine/lumen-technical-details-in-unreal-engine)):

1. **Screen traces first.** Rays march the depth buffer; when they miss or pass behind a surface, Lumen falls back to a world-space method.
2. **Software ray tracing against distance fields.** Every static mesh carries a precomputed signed distance field (SDF). Rays trace the per-mesh fields for the first two metres and a merged, coarser **global distance field** after that.
3. **The surface cache.** Each mesh gets up to 12 offline-placed "cards" (skeletal meshes six) that capture its material and lighting from fixed directions. A ray hit reads lighting from the cards instead of shading the hit, which is what makes multi-bounce affordable.
4. **Final gather.** Screen probes trace from the visible pixels and integrate incoming light; a **world-space radiance cache** stores distant lighting in probes updated a few per frame. Results are accumulated over frames and denoised.
5. **Hardware ray tracing** replaces distance-field tracing on supported GPUs and can shade the real triangles at the hit.

It leans on **Nanite** (fast card capture; foliage and instanced meshes are only supported through Nanite), **Virtual Shadow Maps**, and **Temporal Super Resolution**. The Epic quality level spends about 8 ms on GI and reflections at 1080p internal on current consoles, and the High level 4 ms, with TSR upscaling to 4K ([Epic, Lumen performance guide](https://dev.epicgames.com/documentation/en-us/unreal-engine/lumen-performance-guide-for-unreal-engine)).

## 3. Options

All costs are GPU time at 1080p. "Mid-range desktop" means an RTX 3060 / RX 6600-class GPU; "integrated" means Apple M1 or Intel Iris Xe-class. Anchors: GTAO measures 0.56 ms at 1080p on an RTX 2060 and 2.39 ms on Intel i7-1195G7 integrated graphics ([Intel, XeGTAO](https://github.com/GameTechDev/XeGTAO)), so integrated GPUs run screen-space passes roughly four times slower; a DDGI volume update costs about 1.1–1.5 ms with hardware ray tracing ([Majercik et al. 2019](https://jcgt.org/published/0008/02/01/); measured in [ReSTIR-DDGI, arXiv 2108.05263](https://arxiv.org/abs/2108.05263)); Lumen's budget is in §2.1.

### 3.2 Option A: screen-space GI, SSR and GTAO over TAA

- **Gives:** one bounce of colour bleeding from what is on screen, glossy reflections of on-screen objects, contact darkening. Light from off-screen objects disappears and reappears as the camera turns, and reflections fall back to the global environment at screen edges.
- **Costs (estimate):** Lite SSGI at half resolution plus GTAO, SSR and TAA: about 2.5–4 ms mid-range, 8–12 ms integrated (low presets required), phones: GTAO only.
- **Scope:** 10–15 agent-days on top of §3.1 (SSGI wiring 2–3; SSR on the depth pyramid 5–8; tuning and goldens 3–4).
- **Prerequisites:** HDR path, TAA with velocity, G-buffer pass (an extra geometry pass in a forward renderer).
- **Risks:** SSGI composites additively after shading, which double-counts the environment's diffuse term unless a plugin removes it; screen-space artefacts are visible in exactly the scenes owners show off.
- **Lite 1.34:** allows it, apart from the HDR path.

### 3.3 Option B: probe volume GI (DDGI-style) against a global SDF, plus SSR

- **Gives:** fully dynamic diffuse GI for static geometry with any lighting change (moving sun, lights switching), several bounces through the probes, no off-screen loss. Specular comes from SSR plus reflection probes.
- **How it maps onto Lite 1.34:** build a global SDF or voxel volume from static meshes with `getMeshGeometry` and a compute jump-flood pass into a 3D storage texture; each frame, a compute pass traces rays from a subset of probes through the SDF, shades the hit from an albedo volume, the sun (shadowed by marching the SDF) and the previous probe state, and writes octahedral irradiance and visibility into a 2D atlas; a PBR plugin samples the atlas (`texture_2d` is all plugins allow, and DDGI atlases are 2D by design) and replaces the global spherical-harmonic diffuse term.
- **Costs (estimate):** probe update amortised over frames plus sampling: 1.5–3 ms mid-range, 4–8 ms integrated with fewer rays and slower updates. Not viable on phones. Godot's comparable SDFGI is supported only on its desktop-class Forward+ renderer and called one of its most demanding techniques ([Godot docs, SDFGI](https://docs.godotengine.org/en/stable/tutorials/3d/global_illumination/using_sdfgi.html)).
- **Scope:** 40–60 agent-days: spikes 3; SDF and albedo volumes 10–15; probe tracing and atlas 10–15; plugin integration and environment replacement 5–8; probe placement, relocation and leak fixes 8–12; editor gizmos and settings 4–6.
- **Prerequisites:** §3.1 (HDR, TAA), a sampler slot per material (§1.2), a GPU timing path that works on Metal.
- **Risks:** light leaking through thin walls; moving objects do not occlude or bounce light unless proxies are added; SDF memory on large worlds (cascaded volumes are the fix, more scope); the plugin route may need a Lite change to drop the built-in diffuse term.
- **Lite 1.34:** allows it with no upstream change, as far as `index.d.ts` shows; spike S2 must confirm a render target can feed a compute pass.

### 3.4 Option C: radiance cascades

- **Gives:** in 2D and in screen space, noise-free GI with a fixed cost ([Sannikov, Radiance Cascades](https://github.com/Raikiri/RadianceCascadesPaper)). The 3D world-space form is recent research: Holographic Radiance Cascades (2025) targets 2D ([arXiv 2505.02041](https://arxiv.org/abs/2505.02041)), and the sparse "split" 3D variant appeared in mid-2026. Screen-space versions lose off-screen light like option A ([Chalmers thesis](https://odr.chalmers.se/items/9e42007a-bb60-440f-ba28-04410822758f)).
- **Costs:** no production references to scale from; 3D probe storage is the known bottleneck.
- **Scope:** 50–90 agent-days with a real chance of no shippable result.
- **Recommendation:** use it for **2D lighting** (on the post-1.0 list, `engineering-plan.md` line 310), where it is proven and cheap; revisit 3D in 2027.

### 3.5 Option D: a Lumen-faithful port

- **Would need:** per-mesh SDFs baked at import, a global SDF clipmap, a surface-cache card atlas captured by rendering every mesh from up to 12 directions, screen probes, a world radiance cache, temporal denoisers, and a TSR-class upscaler to pay for it.
- **Why it is not realistic:** the cards are rasterised captures that Nanite makes affordable; without bindless every mesh SDF must live in one atlas; without hardware ray tracing there is no high-quality path; and the budget does not fit. Lumen uses 4–8 ms on a PS5-class GPU (about 10 TFLOPS); the reference M1 has roughly a quarter of that, so the same work lands near 16–30 ms (estimate), the whole frame. Epic built Lumen with a dedicated team over several years.
- **Scope:** 150–300+ agent-days, and continuing maintenance against Lite releases.
- **Verdict:** not a goal. Option B's SDF and probes are the reusable first half of it, so B keeps the door open.

### 3.6 Option E: baked GI (lightmaps, light probes, reflection probes)

- **Gives:** the best image quality per millisecond: multi-bounce diffuse with soft area-light shadows baked in, for static geometry and static lights. Dynamic objects take lighting from baked probes. It does not react to a moving sun or doors opening.
- **Costs:** under 0.3 ms at run time on every device (one texture fetch, and an SH evaluation per object), phones included (estimate). The cost moves to bake time, memory and download size.
- **Scope:** run time 10–14 agent-days (lightmap field on `MaterialAsset` and per-renderer scale/offset, light-probe grid through a plugin, reflection probes through Lite's local probe set). The baker, in the editor, 25–40 agent-days: UV2 unwrap with `xatlas` compiled to WebAssembly ([xatlas](https://github.com/jpcy/xatlas)), a WebGPU compute path tracer over a BVH of static meshes, a denoiser, probe and cube-map bakes, and a bake panel.
- **Prerequisites:** HDR path; a decision that the editor does lighting bakes (it fits the owner's "builds inside the editor, no external tools" rule, but it is not in editor v1 scope, `ignifx-editor/docs/plan/2026-10-editor-plan.md` §2.2–§2.3).
- **Risks:** UV2 quality on imported glTF; bake times on integrated GPUs; lightmap memory on the web.
- **Lite 1.34:** allows it; `enablePbrLightmap` and `uvs2` are already there (§1.2).

## 4. Top blockers

1. **No HDR scene buffer.** Lite's PBR shader tone maps, encodes and clamps every fragment (`lib/material/pbr/pbr-template.js` line 171) into an 8-bit target (`render-path.ts` lines 111–116). Nothing physically based downstream works until this changes.
2. **No temporal anti-aliasing that survives a moving camera.** Lite's TAA resets on camera motion and reads no velocity (`lib/post-process/taa.js` lines 76, 105). Temporal reprojection is what denoises every real-time GI technique.
3. **WebGPU and Lite limits on the lighting itself.** No hardware ray tracing or bindless in WebGPU (§2.2); Lite's lighting loop accepts only 2D-texture plugins within a tight sampler budget (§1.2), and area lights and soft shadows are upstream work under `CONSTITUTION.md` §1.3 and §11.2.

Phase 1 spikes (2 agent-days, before any API is designed):

- **S1** a PBR plugin that carries the linear colour past the encode and clamp into an `rgba16float` target; if it fails, file the upstream ask with a minimal repro.
- **S2** a compute pass reading the scene depth and a G-buffer attachment (`createComputeTextureResource` takes a `Texture2D`, `index.d.ts` 2810; whether a `RenderTarget` converts is unverified).
- **S3** a plugin sampling a screen-sized texture at the fragment's screen position, to apply AO and GI to indirect light only.
- **S4** GPU timing on Metal under Lite 1.34, or a substitute, so budgets can be measured on the reference machine.

## 6. Decisions for the owner

1. **Target devices for dynamic GI.** Accept that options B and later are a desktop quality tier, and that phones and integrated GPUs get baked lighting and AO.
2. **Order.** Phase 1 first (recommended), or baked lighting first for a faster visible win on static scenes.
3. **Upstream.** Who files and follows Lite pull requests for a linear HDR output, soft shadows and area lights; the constitution rules out forking (§1.3, §11.2).
4. **Editor scope.** Whether a lightmap baker joins editor v1 or waits for 0.8+.
5. **Static-world rule.** Accept that dynamic GI covers static geometry only, with moving objects receiving but not bouncing light.
6. **Write a GPU budget.** Standards line 152 sets CPU time only; a GPU budget per quality tier is needed before any of this can pass `pnpm test:frame-budget`.

## 7. Not verified

- Every millisecond figure for ignifx is an estimate; nothing was measured.
- Whether a Lite `RenderTarget` can be bound into a compute pass, and whether a plugin can recover pre-clamp colour (spikes S1, S2).
- Whether Lite 1.34 fixed `gpuFrameTimeMs` on Metal.
- The split radiance cascades paper was found only through secondary summaries; its date and claims are unconfirmed.
- WebGPU feature availability on Safari 26 and Firefox was not tested here; the matrix itself has never run beyond Chromium (`engineering-plan.md` line 239).
